# Introduction

001에서 직렬 CRC16 회로를 봤습니다. 이번에는 **한 클럭에 16비트**를 처리하는 병렬 회로에서 이런 식이 왜 나오는지 풀어 봅니다.

```vhdl
lfsr_c(0) <= lfsr_q(0) xor lfsr_q(4) xor lfsr_q(8) xor lfsr_q(11) xor lfsr_q(12)
             xor data_in(0) xor data_in(4) xor data_in(8) xor data_in(11) xor data_in(12);
```

> 사용한 설정은 001과 같은 **CRC-16/CCITT-FALSE** (G(x) = x^16 + x^12 + x^5 + 1, 초기값 0xFFFF, MSB 먼저)입니다.

---

# 흔히 하는 오해

처음에는 이렇게 생각하기 쉽습니다.

> "0, 4, 8, 11, 12는 **다항식의 탭 위치**이거나, `16 - 차수`로 만든 숫자일 것이다."

그렇지 않습니다. 근거를 보면 이렇습니다.

| 추측 | 확인 |
|------|------|
| 다항식 계수가 1인 위치 | 다항식은 16, 12, 5, 0이라 숫자가 다르다 |
| 16 - 차수 (16-12=4, 16-5=11) | 4와 11은 맞지만 **0, 8, 12는 설명되지 않는다** |

이 숫자는 **탭 위치가 아닙니다.** 1스텝 규칙을 **16번 반복한 결과**가 이런 숫자로 보이는 것입니다.

---

# 핵심: 1스텝 규칙을 N번 적용한다

직렬 회로의 1스텝은 이렇게 쓸 수 있습니다.

$$
s_{next}(x) = x \cdot s(x) \bmod G(x)
$$

(레지스터 내용을 한 칸 밀고, x^16이 생기면 G(x)로 줄이는 것입니다.)

이것을 **N번** 적용하면 다음과 같습니다.

$$
s_{N}(x) = x^{N} \cdot s(x) \bmod G(x)
$$

병렬 회로는 이 식을 **한 번에 계산**하도록 풀어 쓴 것입니다. 여기서 N은 **한 클럭에 처리하는 비트 수**(이 글에서는 16)입니다.

**탭은 1스텝에서만 보이고, 병렬 식의 숫자는 탭이 N번 쌓인 흔적**입니다.

---

# 열 규칙: 비트 j는 어디로 들어가나

현재 상태의 비트 j는 x^j 항입니다. 이것을 x^16배 해서 G로 줄이면 다음 상태의 어느 비트들로 퍼지는지 나옵니다.

> 비트 j → 다음 상태에서 **x^(16+j) mod G(x)에 남는 항들**

계산해 보면 이렇습니다.

| j | x^(16+j) mod G에 남는 차수 (= 이 비트가 들어가는 `lfsr_c` 번호) |
|---|----------------------------------------------------------|
| 0 | **0**, 5, 12 |
| 1 | 1, 6, 13 |
| 2 | 2, 7, 14 |
| 3 | 3, 8, 15 |
| 4 | **0**, 4, 5, 9, 12 |
| 5 | 1, 5, 6, 10, 13 |
| 6 | 2, 6, 7, 11, 14 |
| 7 | 3, 7, 8, 12, 15 |
| 8 | **0**, 4, 5, 8, 9, 12, 13 |
| 9 | 1, 5, 6, 9, 10, 13, 14 |
| 10 | 2, 6, 7, 10, 11, 14, 15 |
| 11 | **0**, 3, 5, 7, 8, 11, 15 |
| 12 | **0**, 1, 4, 5, 6, 8, 9 |
| 13 | 1, 2, 5, 6, 7, 9, 10 |
| 14 | 2, 3, 6, 7, 8, 10, 11 |
| 15 | 3, 4, 7, 8, 9, 11, 12 |

굵게 표시한 **0이 들어 있는 행의 j**를 모으면 `j = 0, 4, 8, 11, 12`입니다. 바로 `lfsr_c(0)`에 들어가는 항들입니다.

**표를 가로로 읽으면** "j번 비트가 다음 상태의 어디로 가나"이고, **세로로 읽으면** "`lfsr_c(i)`에 어떤 j가 들어가나"입니다.

| `lfsr_c(i)` | 들어가는 j (lfsr_q(j), data_in(j) 번호) |
|-------------|----------------------------------------|
| 0 | 0, 4, 8, 11, 12 |
| 1 | 1, 5, 9, 12, 13 |
| 2 | 2, 6, 10, 13, 14 |
| 3 | 3, 7, 11, 14, 15 |
| 4 | 4, 8, 12, 15 |
| 5 | 0, 4, 5, 8, 9, 11, 12, 13 |
| 6 | 1, 5, 6, 9, 10, 12, 13, 14 |
| 7 | 2, 6, 7, 10, 11, 13, 14, 15 |
| 8 | 3, 7, 8, 11, 12, 14, 15 |
| 9 | 4, 8, 9, 12, 13, 15 |
| 10 | 5, 9, 10, 13, 14 |
| 11 | 6, 10, 11, 14, 15 |
| 12 | 0, 4, 7, 8, 15 |
| 13 | 1, 5, 8, 9 |
| 14 | 2, 6, 9, 10 |
| 15 | 3, 7, 10, 11 |

16개 식이 모두 생성기가 만든 원본 코드와 일치합니다. "16 - 12 = 4"는 표의 j=4 행에 **우연히 맞아떨어진 것**이지 규칙이 아니었습니다.

---

# 시프트는 어디로 갔나

"시프트 연산자가 코드에 없는데 어디서 시프트가 되나?"라는 의문이 생길 수 있습니다.

16비트 레지스터를 16번 시프트하면 **원래 있던 비트는 모두 밖으로 밀려나갑니다.** 그래서 병렬 식에는 "그냥 옮겨진 비트"가 하나도 없고, 남은 16비트 전체가 **16번 쌓인 피드백(fb)의 결과**입니다.

- 시프트는 사라진 것이 아니라 **인덱스 선택 안에 녹아** 있습니다.
- `lfsr_q(0)`, `lfsr_q(8)`, `lfsr_q(12)`는 각각 **다른 시점의 fb**가 0번 자리까지 올라와 쌓인 것입니다.
- 그래서 `0, 8, 12`를 지우고 `4, 11`만 남기면 **다른 CRC**가 됩니다.

---

# data_in과 lfsr_q의 번호가 같은 이유

데이터 비트는 매 스텝 `c(15)`와 **같은 자리(fb)** 에서 섞입니다. 데이터 폭과 CRC 폭이 모두 16이면, 이것은 이렇게 된다는 뜻입니다.

> **먼저 `lfsr_q xor data_in`을 하고, 그 값을 데이터 없이 16번 돌린 것**과 같다.

그래서 두 목록이 항상 같은 번호입니다.

```
M · (lfsr_q xor data_in)
```

첫 클럭에서는 `lfsr_q`가 0xFFFF이므로, **0xFFFF xor 첫 16비트 데이터**를 행렬에 통과시키는 것이 첫 계산입니다.

## 데이터 폭과 CRC 폭이 다르면

번호가 같아지는 것은 **데이터 폭 W = CRC 폭 16**일 때뿐입니다. 실무에서는 대부분 다릅니다(64비트 버스에 CRC-32, 512비트 버스에 CRC-32 등). 일반적으로는 이렇게 됩니다.

$$
\text{next} = A^{W} \cdot q \;\oplus\; B \cdot d
$$

- A는 1스텝 행렬, A^W는 W스텝을 한 번에 돌린 행렬입니다. 상태 q는 이것을 지납니다.
- B는 데이터 W비트가 상태에 섞이는 방식을 모은 행렬입니다.
- **W ≠ 16이면 상태 쪽 번호와 데이터 쪽 번호가 달라집니다.** 그래서 생성기 코드에서 `lfsr_q` 목록과 `data_in` 목록이 서로 다르게 나옵니다.

또 하나의 문제는 **마지막 beat**입니다. 64비트 버스에서 패킷 길이가 8의 배수가 아니면 마지막 beat의 일부 바이트만 유효합니다(`tkeep`). 이때는 남은 바이트 수별로 다른 W의 식을 두거나, 마지막 beat를 바이트 단위로 나눠 마무리해야 합니다. Project 02의 64비트 인터페이스에서 CRC를 직접 계산한다면 바로 만나는 문제입니다.

> 참고로 이더넷 FCS인 **CRC-32**는 다항식 0x04C11DB7, 초기값 0xFFFFFFFF, **입출력 반사(LSB 먼저)**, 최종 XOR 0xFFFFFFFF이고 확인값은 **0xCBF43926**입니다. 이 글의 CRC-16/CCITT-FALSE와는 반사와 최종 XOR가 다른, 좋은 비교 대상입니다.

# 더미값으로 직접 따라가기

`lfsr_q = 1011 0011 0101 0101 (0xB355)`, `data_in = 0101 0101 0101 0101 (0x5555)`로 16스텝을 직접 돌립니다. 데이터는 **data_in(15)부터** 들어갑니다.

| 스텝 | 들어가는 비트 | fb = c(15) xor din | 스텝 후 레지스터 |
|------|--------------|--------------------|------------------|
| 1 | d(15)=0 | 1 | 0111 0110 1000 1011 |
| 2 | d(14)=1 | 1 | 1111 1101 0011 0111 |
| 3 | d(13)=0 | 1 | 1110 1010 0100 1111 |
| 4 | d(12)=1 | 0 | 1101 0100 1001 1110 |
| 5 | d(11)=0 | 1 | 1011 1001 0001 1101 |
| 6 | d(10)=1 | 0 | 0111 0010 0011 1010 |
| 7 | d(9)=0 | 0 | 1110 0100 0111 0100 |
| 8 | d(8)=1 | 0 | 1100 1000 1110 1000 |
| 9 | d(7)=0 | 1 | 1000 0001 1111 0001 |
| 10 | d(6)=1 | 0 | 0000 0011 1110 0010 |
| 11 | d(5)=0 | 0 | 0000 0111 1100 0100 |
| 12 | d(4)=1 | 1 | 0001 1111 1010 1001 |
| 13 | d(3)=0 | 0 | 0011 1111 0101 0010 |
| 14 | d(2)=1 | 1 | 0110 1110 1000 0101 |
| 15 | d(1)=0 | 0 | 1101 1101 0000 1010 |
| 16 | d(0)=1 | 0 | **1011 1010 0001 0100 (0xBA14)** |

병렬 식으로는 **한 번에** 계산합니다. 먼저 `q xor d = 1110 0110 0000 0000`이고,

- `lfsr_c(0)` ← 0, 4, 8, 11, 12번 비트가 모두 0 → **0** (직렬 결과의 0번 비트와 일치)
- `lfsr_c(2)` ← 2, 6, 10, 13, 14번 중 10, 13, 14번이 1 → 1 xor 1 xor 1 = **1** (일치)
- `lfsr_c(4)` ← 4, 8, 12, 15번 중 15번만 1 → **1** (일치)
- 16비트 전체: 병렬 결과도 **0xBA14**로 직렬 16스텝과 같습니다.

# 입력 순서: data_in(15)가 먼저다

이 병렬 식을 처음 보면 "`lfsr_q(0)`이 제일 먼저 입력된다고 가정한 것 아닌가?" 하고 생각할 수 있습니다. 직접 전개해 보면 **반대**입니다.

> 이 식은 **data_in(15)가 가장 먼저 들어가는 MSB-first** 직렬 CRC를 푼 것이다.

`data_in(0)`부터 넣는다고 가정하고 풀면 `lfsr_c(0)`의 데이터 항이 **3, 4, 7, 11, 15**로 바뀌어 원본 식과 맞지 않습니다.

실무에서 남는 주의점입니다.

- 초기값 0xFFFF를 쓰면 **CRC-16/CCITT-FALSE**와 같은 정의입니다. 문자열 `"123456789"`를 바이트마다 MSB부터 넣으면 **0x29B1**이 나옵니다.
- 16비트 워드로 넣을 때는 **어느 바이트가 `data_in(15 downto 8)`** 에 들어가는지가 결과를 바꿉니다. 패킷 덤프와 시뮬레이션 데이터의 바이트 순서가 뒤집히면 결과가 달라집니다.
- 대상 규격이 바이트를 **LSB부터** 보낸다면(이더넷 등) 입출력 비트를 뒤집는(reflect) 처리가 필요할 수 있습니다. **상대 장비의 CRC 정의**를 확인해야 합니다.

# 식을 직접 만들어 보기

병렬 식은 생성기에만 의존하지 않고 **직접 만들 수 있습니다.** 위의 열 규칙을 그대로 코드로 옮깁니다.

```python
G = 0x11021                       # x^16 + x^12 + x^5 + 1

def x_mod_g(n):                   # x^n mod G
    v = 1 << n
    for i in range(n, 15, -1):
        if (v >> i) & 1:
            v ^= G << (i - 16)
    return v

# lfsr_c(i)에 들어가는 입력 번호 j 목록
for i in range(16):
    print(i, [j for j in range(16) if (x_mod_g(16 + j) >> i) & 1])
```

출력이 위의 표와 같으면 식이 맞습니다. 직렬 모델과도 비교합니다.

```python
import random
def parallel16(q, d):
    x = q ^ d
    out = 0
    for i in range(16):
        bit = 0
        for j in range(16):
            if (x_mod_g(16 + j) >> i) & 1:
                bit ^= (x >> j) & 1
        out |= bit << i
    return out

q, d = random.getrandbits(16), random.getrandbits(16)
serial = crc16_serial([(d >> (15 - k)) & 1 for k in range(16)], q)   # 001의 직렬 모델
assert serial == parallel16(q, d)
```

# 데이터가 길어도 되나

CRC 계산 자체에는 **길이 제한이 없습니다.** 16비트 워드를 한 클럭씩 넣으면 되고, 바이트 수가 많으면 클럭 수가 늘 뿐입니다 (1000바이트라면 500워드, 500클럭).

다만 CRC의 **오류 검출 강도**는 다항식과 데이터 길이에 따라 다릅니다.

- 상수항(+1)이 있는 차수 16의 CRC는 **길이 16비트 이하의 버스트 오류를 모두 검출**합니다. 다항식과 상관없이 성립하는 성질입니다.
- 흩어진 여러 비트 오류를 몇 개까지 반드시 잡는지(해밍 거리)는 다항식과 데이터 길이에 따라 다르므로, CRC 다항식 성능표(Koopman 등)에서 따로 확인해야 합니다.

## 수신 측 검사: 잔여값(residue)

수신 측에서 CRC를 확인하는 방법은 두 가지입니다.

| 방법 | 동작 |
|------|------|
| 비교 | 데이터만으로 CRC를 다시 계산해 받은 CRC와 비교 |
| **잔여값** | **받은 CRC까지 포함해** 끝까지 계산하고, 결과가 정해진 상수인지 확인 |

오류가 없으면 두 번째 방법의 결과는 **항상 같은 상수**가 나옵니다. CRC-16/CCITT-FALSE처럼 반사와 최종 XOR가 없는 규격에서는 그 값이 **0**입니다. `"123456789"` 뒤에 CRC 0x29B1을 붙여 계산하면 0x0000이 나오는 것으로 확인할 수 있습니다. 하드웨어 체커에서는 받은 CRC를 따로 떼어 비교할 필요가 없어서 이 방식을 많이 씁니다.

# What I Learned

- 병렬 식의 숫자(0, 4, 8, 11, 12)는 **탭 위치가 아니라 1스텝 규칙을 N번 적용한 결과**다.
- 비트 j는 다음 상태에서 **x^(N+j) mod G(x)에 남는 항**으로 들어간다.
- 시프트는 사라진 것이 아니라 **인덱스 선택 안에 녹아 있다.** 0, 8, 12를 지울 수 없다.
- 데이터 폭과 CRC 폭이 같으면 **`lfsr_q xor data_in`** 을 같은 행렬에 통과시킨 것이라 번호가 같다.
- 이 식은 **`data_in(15)`가 먼저 들어가는 MSB-first**다. 입력 순서와 바이트 순서는 직접 확인해야 한다.
- 데이터 폭이 CRC 폭과 다르면 상태와 데이터의 번호가 달라지고, **마지막 beat의 일부 바이트**를 따로 처리해야 한다.
- 수신 측은 CRC까지 포함해 계산한 **잔여값**이 상수인지로 검사할 수 있다(CRC-16/CCITT-FALSE는 0).
- 식은 **직렬 모델과 비교**해서 검증한다.
