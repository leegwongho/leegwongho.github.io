# Introduction

005에서 주소 매핑이 성능을 좌우한다고 했습니다. 이 글은 **직접 만든 테스트 패턴 생성기**로 **주소 매핑 3종 × CAS 설정 2종**의 순차/랜덤 접근 성능을 재고 해석한 결과를 정리합니다.

> 측정은 직접 만든 컨트롤러와 테스트 구조에서 나온 값이고, **IP 설정과 보드에 따라 달라질 수 있습니다.** 수치는 방향을 보여 주는 용도로 읽어 주세요.

---

# 측정 방법

| 항목 | 내용 |
|------|------|
| 인터페이스 | MIG Native UI, **250 MHz UI 클럭 (1 clk = 4 ns)** |
| 데이터 폭 | 256비트, 요청 **1,000회** 전송 |
| 패턴 | **순차 / 랜덤** × **Write / Read** |
| 주소 매핑 | `Bank→Row→Column`, `Row→Bank→Column`, `Row→Column→Bank` (interleave). 상위 비트 → 하위 비트 순서이며, PG150 파라미터 값과의 대응은 **확인 필요**(005) |
| CAS 설정 | CL16/CWL14, CL15/CWL11 |
| 데이터 오류 | 모든 시험에서 **0** |

대역폭은 **측정한 클럭 수**에서 계산합니다.

$$
\text{Gbps} = \frac{256 \times 1000\ \text{bit}}{\text{클럭 수} \times 4\ \text{ns}}
$$

- 이론 최대: **256비트 × 250 MHz = 64 Gbps** (x32 DDR4-2000급)
- 처음에 표를 만들 때 **1000 MHz(1 clk = 1 ns)** 로 계산해서 틀렸고, **"UI는 250 MHz, 256비트"** 로 기준을 잡은 뒤에야 맞았습니다. 메모리 클럭(1000 MHz)과 UI 클럭(250 MHz, 4:1)을 구분하는 것이 계산의 출발점입니다.

---

# 결과

## 순차 접근 (Gbps, 이론 최대 64)

| 매핑 | CAS | Write | Read |
|------|-----|-------|------|
| Bank → Row → Column | CL16/CWL14 | 18.9 | 20.1 |
| Row → Bank → Column | CL16/CWL14 | 20.5 | 20.5 |
| **Row → Column → Bank (interleave)** | CL15/CWL11 | **30.0** | **30.3** |
| Bank → Row → Column | CL15/CWL11 | 18.9 | 19.5 |
| Row → Bank → Column | CL15/CWL11 | 20.6 | 20.7 |

## 랜덤 접근 (Gbps, 0~8 범위)

| 매핑 | CAS | Write | Read |
|------|-----|-------|------|
| Bank → Row → Column | CL16/CWL14 | 3.4 | 5.1 |
| Row → Bank → Column | CL16/CWL14 | 3.7 | 5.3 |
| Row → Column → Bank (interleave) | CL15/CWL11 | 3.6 | 5.1 |
| Bank → Row → Column | CL15/CWL11 | 3.6 | 5.1 |
| Row → Bank → Column | CL15/CWL11 | 3.9 | 5.3 |

> 랜덤 접근은 어떤 매핑에서도 **3.4~5.3 Gbps** 범위입니다. 가장 빠른 랜덤 Read는 1,000회에 12,042클럭이었고, 이는 **회당 약 48 ns, 초당 약 20.8M회**입니다.

---

# 읽는 법

## 1) 순차 접근은 매핑이 결정한다

- `Row → Column → Bank`(interleave) 매핑에서만 **30 Gbps**로 이론 최대(64)의 **절반 가까이** 나왔고, 나머지는 **19~21 Gbps**였습니다.
- 005에서 본 대로 이 매핑에서는 **연속 주소가 매번 다른 bank로** 가서 ACT/PRE가 다른 bank의 작업 뒤에 숨겨집니다. 연속 접근이 **Bank Group을 번갈아** 가면 tCCD_L 대신 짧은 tCCD_S로 이어 보낼 수 있다는 것도 이 매핑이 빠른 이유입니다(005).

## 그래도 30 Gbps에서 멈춘 이유는 아직 모른다

interleave에서도 이론의 47%입니다. 병목이 **MIG 쪽인지, 직접 만든 컨트롤러 쪽인지** 아직 나누지 못했습니다. 다음 두 가지를 따로 세면 구분할 수 있습니다(Project 02 - 002의 카운터 방법).

| 세는 것 | 의미 |
|---------|------|
| `app_en && !app_rdy`인 클럭 수 | **MIG가 받지 못한** 시간 (MIG 쪽 병목) |
| `!app_en`인 클럭 수 | **내 컨트롤러가 요청을 주지 못한** 시간 (내 쪽 병목, FSM 버블 등) |

또 1,000회 시험은 수 µs라서 **리프레시 주기(약 7.8 µs)** 와 비슷하거나 짧습니다. 시험 한 번에 리프레시가 걸리는지에 따라 결과가 흔들릴 수 있으므로, **더 긴 시험**으로 평균을 내야 리프레시 영향까지 포함한 값이 됩니다.

## 2) CAS 변경 효과는 작다

- 같은 매핑끼리 비교하면 **CL16 → CL15**에서 **순차는 거의 그대로**이고 **랜덤은 조금** 오릅니다.
- 다만 interleave 매핑은 CL15에서만 측정해서 **매핑 효과와 CAS 효과를 완전히 분리하지는 못했습니다.** (CL16/CWL14에서도 interleave를 재서 분리하는 것이 남은 일입니다.)

## 3) 랜덤 접근은 매핑과 거의 무관하다

랜덤 접근은 **어떤 매핑을 써도 3.4~5.3 Gbps**입니다. Write가 Read보다 일관되게 느립니다.

---

# 랜덤이 왜 이렇게 느린가: 내 패턴이 최악의 경우였다

랜덤 주소는 이렇게 만들었습니다.

```
addr = { 9'd0, wr_count[0], wr_count[1], ..., wr_count[15], 5'b00000 }
```

카운터를 **비트 순서를 뒤집어** 넣은 것입니다. 그러면:

- 매번 바뀌는 `wr_count[0]`이 **주소의 높은 비트(row 영역)** 로 가고,
- 가장 드물게 바뀌는 `wr_count[15]`가 **낮은 비트(bank 부근)** 로 갑니다.

결과적으로 **매 접근마다 row가 바뀌고 bank 비트는 거의 안 바뀝니다.** (정확한 비트 위치는 매핑마다 다르므로 대략적인 그림입니다.)

- 같은 bank에서 row miss가 매번 일어나는 구조라서 **매핑을 바꿔도 피할 방법이 없었습니다.**

## 숫자가 이 해석을 뒷받침한다: 48 ns ≈ tRC

가장 빠른 랜덤 Read는 **회당 약 48 ns**였습니다. 005에서 본 대로, 같은 bank에서 row를 바꿀 때는 최소 **tRC(= tRAS + tRP)** 를 기다려야 하고, DDR4-2000~2400급에서 tRC는 대략 **45~48 ns**입니다(쓴 칩의 정확한 값은 **데이터시트에서 확인 필요**).

측정값이 tRC와 거의 같다는 것은 **"같은 bank에서 row miss가 하나씩 직렬로 일어났다"** 는 해석의 강한 증거입니다. 요청을 빨리 넣어도 같은 bank라 tRC보다 빨라질 수 없었던 것입니다.

**Write가 Read보다 느린 이유**도 같은 틀로 설명됩니다. 쓰기 후에는 데이터가 셀에 저장될 시간인 **tWR(약 15 ns)** 을 기다린 뒤에야 PRE를 할 수 있어서, row miss 한 번의 주기가 읽기보다 깁니다. 측정한 랜덤 Write는 회당 약 **65 ns**(초당 약 15.3M회)로, 읽기의 48 ns보다 이만큼 깁니다.
- "MIG나 DDR 입장에서는 저게 랜덤으로 보일 것"이라는 직관은 맞았고, 정확히는 **"가장 가혹한 랜덤"** 이었습니다.
- 005의 비용 순서(**column ≪ bank < row**)가 그대로 나타난 것입니다.

# 룩업 테이블 용도로 보면

001에서 "지연이 아니라 **랜덤 접근 처리율**이 한계"라고 했습니다. 이제 숫자로 볼 수 있습니다.

| 항목 | 초당 횟수 |
|------|-----------|
| 10G 최소 패킷(64B, 선로상 84B)당 1회 조회 | **14.88M** |
| 내 테스트의 랜덤 Read (최고 설정) | 약 **20.8M** |
| 내 테스트의 랜덤 Write (최고 설정) | 약 **15.3M** |

- 한 포트, **읽기만, 패킷당 1회**라면 여유가 약 **1.4배**뿐입니다.
- 두 포트를 보거나, 룰 갱신(Write)이 섞이거나, 해시 충돌로 두 번 읽으면 **바로 모자랍니다.**
- 그래서 **"DDR4만으로는 빠듯하다. 캐시나 프리필터가 필요하다"** 는 결론은 맞았고, 이유는 **지연이 아니라 랜덤 처리율**입니다.
- 이 수치는 **내 테스트 구조(단일 요청 스트림, 요청당 1 beat)** 에서 나온 것이라 **상한이 아닙니다.**
- 해시 주소에 **1비트만 저장**하는 구조는 충돌이 곧 **오탐**(정상 패킷 차단)이 됩니다. 실제로는 엔트리에 **키를 같이 넣고 비교**해야 합니다.

---

# 랜덤 성능을 더 올리려면

매핑으로는 거의 끝입니다. 더 올리려면 **컨트롤러가 일을 더 많이, 더 잘 주어야** 합니다.

1. **동시에 날아가는 요청(outstanding)을 늘린다.** AXI라면 B를 기다리지 않고 계속 발행하고, 여러 ID를 쓴다.
2. **한 번에 읽는 양을 늘린다.** 해시 엔트리를 64바이트 이상으로 묶어 짧은 버스트로 읽는다.
3. **해시 결과를 bank 비트에 더 직접 흩어지게** 둔다. 같은 bank에서 row만 바뀌는 요청이 연달아 오지 않게 한다.
4. **테스트를 나눈다.** LFSR 랜덤, row만 랜덤, bank만 랜덤을 따로 재서 병목을 분리한다.

## 목표 상한은 계산할 수 있다

bank를 잘 흩고 outstanding을 늘리면 tRC 한계(같은 bank 직렬)는 사라지고, 다음 한계는 **tRRD와 tFAW**입니다(005). tFAW는 "일정 시간 창 안에 ACT를 최대 4번"이라는 규칙이므로, 랜덤 접근의 대략적인 상한은

$$
\text{초당 최대 ACT 수} \approx \frac{4}{t_{FAW}}
$$

입니다. tFAW는 수십 ns 수준이라 이 상한은 지금 측정한 초당 20.8M회보다 **몇 배 높습니다.** 칩 데이터시트의 tFAW로 계산해 두면 "어디까지 개선할 수 있는가"를 숫자로 정할 수 있습니다(**확인 필요**).

# 남은 일

- 생성된 IP에서 ROW_COLUMN_BANK의 **실제 비트 위치**(BG/BA가 `app_addr` 몇 번인지)를 파라미터로 확인하기
- Native UI에서 **쓰기 명령과 데이터 사이 허용 간격**을 PG150의 Write 타이밍 그림으로 확인하기
- interleave 매핑을 **CL16/CWL14로도** 재서 매핑 효과와 CAS 효과를 분리하기
- 랜덤 테스트를 **LFSR 랜덤, row만 랜덤, bank만 랜덤**으로 나눠 다시 재기
- **outstanding 요청 수를 늘린** 구조에서 목표(초당 14.88M회 조회)를 다시 측정하기
- 순차 30 Gbps의 병목을 `app_en && !app_rdy`와 `!app_en` 클럭 수로 **MIG 쪽 / 내 쪽**으로 나누기
- **더 긴 시험**으로 리프레시 영향을 포함한 값 재기
- 칩 데이터시트에서 **tRC, tWR, tCCD_L, tRRD, tFAW** 확인해 측정값과 대조하기

# What I Learned

- 대역폭은 **측정한 클럭 수**에서 직접 계산하고, **메모리 클럭과 UI 클럭을 구분**한다. (250 MHz UI, 256비트: 이론 64 Gbps)
- **순차 접근은 주소 매핑이 결정한다.** interleave 매핑에서 약 20에서 **30 Gbps**로 올랐다.
- **CAS 변경 효과는 작다.**
- 랜덤 접근은 어떤 매핑에서도 **3.4~5.3 Gbps**이고, 이유는 매 접근마다 같은 bank에서 **row miss**가 나는 패턴이기 때문이다. 회당 48 ns가 **tRC**와 거의 같다는 점이 이를 뒷받침한다.
- Write가 느린 것은 row miss마다 **tWR**을 더 기다리기 때문이다.
- 지연이 아니라 **랜덤 접근 처리율**이 한계이며, 올리려면 **outstanding, 한 번에 읽는 양, bank 분산**을 손봐야 한다.
- 수치는 **내 테스트 구조의 값**이고, IP 설정과 보드에 따라 달라지므로 상한으로 읽지 않는다.
