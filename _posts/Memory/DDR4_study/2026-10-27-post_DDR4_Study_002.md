# Introduction

001에서 Native UI 신호를 봤습니다. 이 글은 그 위에 **Write/Read 요청을 보내는 컨트롤러를 직접 만들면서** 설계가 어떻게 바뀌었는지, 어디서 막혔는지를 정리합니다.

> 이 글의 코드는 개념을 보여 주기 위한 **예시**입니다.

---

# 설계가 바뀐 다섯 단계

처음부터 완성된 구조를 그린 것이 아니라 다섯 단계로 바뀌었습니다.

| 단계 | 구조 | 바뀐 이유 |
|------|------|-----------|
| 1 | **Write만 다루는 단일 FSM** | 일단 복잡한 것은 빼고 addr, data, len을 받아 쓰는 것부터 |
| 2 | **정석 핸드셰이크**로 수정 | `valid`를 올리고 `valid && ready`일 때만 센다 |
| 3 | **요청 FIFO + CMD FSM / DATA FSM 분리** | 요청(`addr`, `len`)을 FIFO 한 워드로 묶어 받고 두 채널을 나눈다 |
| 4 | **Read 추가와 라운드 로빈** | Write와 Read 요청을 번갈아 선택 |
| 5 | **CMD 카운트와 DATA 카운트 분리** | DATA 쪽에 `len` FIFO를 두어 두 FSM이 서로를 기다리지 않게 |

# 버그 두 개

## 1) ready를 보고 valid를 올리면 1클럭 밀린다

첫 코드는 이런 식이었습니다.

```verilog
// 잘못된 예: ready를 한 번 레지스터로 받은 뒤 en을 만든다
always @(posedge ui_clk) app_en_reg <= app_rdy;
```

`app_rdy`가 1이 되어도 `app_en`은 **다음 클럭에야** 1이 되므로 한 클럭 밀립니다. 그 사이에 `app_rdy`가 다시 0이 되면 데이터가 어긋납니다.

**정석 핸드셰이크**로 고칩니다.

> **valid는 내가 정하고, ready는 상대가 정한다. 전송은 둘이 동시에 1인 사이클에만 성립한다.**

```verilog
// valid는 요청이 있는 동안 유지하고, 성립(valid && ready)한 사이클에서만 센다
assign hs = app_en && app_rdy;

always @(posedge ui_clk) begin
  if (hs) begin
    // 이 사이클에 명령이 실제로 전달됨
    cmd_cnt <= cmd_cnt + 1;
  end
end
```

## 2) len = 1이면 FSM이 멈춘다

카운터를 1부터 세고 이렇게 분기했습니다.

```verilog
if (wr_cnt <  len - 1) ...   // 계속
if (wr_cnt == len - 1) ...   // 마지막
```

**len = 1**이면 카운터가 1에서 시작하는데 `len - 1 = 0`이라, **두 조건이 모두 거짓**이 되어 FSM이 어느 쪽으로도 가지 않고 멈춥니다.

카운터를 **0부터** 세고, "**핸드셰이크 성립 && cnt == len - 1**"을 마지막 beat로 보면 모든 길이에서 맞습니다.

```verilog
wire last_beat = hs && (cnt == len - 1);
```

# 가장 오래 붙잡은 쟁점: CMD와 DATA는 같은 트랜잭션을 보고 있나

쓰기의 명령(CMD)과 데이터(DATA)를 **서로 다른 FSM**으로 나누면 이런 지적이 나옵니다.

> "CMD FSM과 DATA FSM이 **같은 요청**을 동시에 시작한다는 보장이 있는가?"

- `app_rdy && app_wdf_rdy`는 **"지금 둘 다 받을 수 있다"** 일 뿐, **"이 주소와 이 데이터가 같은 요청이다"** 를 보장하지 않습니다.
- 두 FSM이 각자 같은 조건만 보고 움직이면, 한쪽이 stall된 사이에 **서로 다른 요청을 처리**할 수 있습니다.
- 필요한 것은 **ready 동기화**가 아니라 **트랜잭션 소유권(어느 요청의 데이터인가)의 동기화**입니다.

제 구조에서는 CMD FSM이 **DATA FSM의 카운트 종료를 기다렸기 때문에** 사실상 하나로 묶여 있었고, 그래서 이 문제가 실제로 생기지 않았습니다. 남은 위험은 IDLE에서 래치한 `data_len_reg`를 **다른 always 블록이 같은 클럭에 읽을 때 이전 값을 보는** 타이밍 문제뿐이었습니다.

## 그래도 분리를 고른 이유

묶인 구조에서는 CMD가 데이터 전송을 기다리느라 **Write와 Read가 뒤섞일 때 느려집니다.** 가장 이상적인 구조는 두 채널을 같은 사이클에 넣는 **단일 FSM**이지만, 요청이 무분별하게 섞여 들어올 때는 분리한 구조가 더 낫다고 판단했고, **CMD 카운트와 DATA 카운트를 나누고 DATA 쪽에 `len` FIFO**를 두었습니다.

> **가장 안전한 방법은 하나의 FSM에서 두 채널을 같은 사이클에 내보내는 것**이고, 분리하는 순간 **트랜잭션 소유권을 어떻게 맞출지**가 설계의 핵심이 됩니다.

# 주소와 데이터는 얼마나 떨어져도 되나

"주소와 데이터를 완전히 분리해서 넣어도 되나? 최소 2클럭까지라고 들었는데"라는 질문을 했습니다.

- Native UI는 주소와 데이터를 **사이클이 아니라 들어온 순서로** 짝짓습니다.
- 다만 **방향에 따라 허용 범위가 다릅니다.**

| 경우 | 허용 여부 |
|------|-----------|
| 데이터가 명령보다 **먼저** | 일반적으로 허용. 데이터는 쓰기 데이터 FIFO에 쌓여 명령을 기다린다 |
| 같은 사이클 | 허용. 가장 안전하다 |
| 데이터가 명령보다 **늦게** | **몇 클럭까지만** 허용 |

7 시리즈 MIG 문서(UG586)에는 "쓰기 데이터는 명령보다 **최대 2클럭** 늦어도 된다"는 설명이 있고, "2클럭"이라는 말은 여기서 온 것으로 보입니다. UltraScale(PG150)에서의 정확한 값은 **Write 타이밍 그림으로 확인 필요**합니다.

이것이 5단계 구조(CMD와 DATA 분리)의 실제 위험입니다. **CMD FSM이 DATA FSM보다 앞서 달리면** 데이터가 명령보다 허용 범위 이상 늦어질 수 있습니다. 그래서 다음을 설계 규칙으로 둡니다.

> **쓰기 데이터는 명령과 같은 사이클이거나 명령보다 먼저 넣는다.** 데이터가 명령을 앞서는 것은 안전하고, 뒤처지는 것은 위험하다.

가장 안전한 방법은 여전히 한 FSM에서 두 채널을 **같은 사이클에** 넣는 것입니다.

# 중재(arbitration)와 1클럭 버블

## 라운드 로빈

Write와 Read를 **우선순위 고정**으로 선택하면 한쪽이 굶습니다(starvation). 그래서 **마지막으로 처리한 쪽을 기억**하고, 다음에는 **반대쪽을 먼저** 보는 라운드 로빈을 넣었습니다.

## 버스트가 끝나고 다음을 고르는 데 1클럭이 꼭 필요한가

> "한 버스트가 끝나고 다음 버스트가 가능한지 확인하려면 무조건 1클럭을 소모해야 하나?"

아닙니다. **마지막 beat 사이클에 다음 상태를 바로 고르면** IDLE을 거치지 않아도 됩니다.

```verilog
if (last_beat)
  next_state = pick_next();     // IDLE을 거치지 않고 바로 다음 요청 선택
```

# 버스트에서 랜덤 접근으로

주소를 연속으로 올리는 버스트만 보면 **조회 용도(해시 테이블 등)** 를 이해하기 어렵습니다.

- 해시 조회는 **시작 주소는 랜덤, 전송은 짧은 버스트**입니다.
- DDR IP는 한 개인데 "파이프라이닝"이란, IP가 여러 개라는 뜻이 아니라 **응답을 기다리지 않고 요청을 계속 넣어 여러 개를 동시에 날려 두는 것(outstanding)** 입니다.
- 병렬 처리라는 말이 "동시에 처리한다"로 들리지만, 실제로는 **요청이 겹쳐서 날아가는 것**입니다.

이 구조의 성능은 **006**에서 측정합니다.

# What I Learned

- 컨트롤러는 **한 번에 완성하지 않고** 단일 FSM에서 시작해 단계별로 나눴다.
- **valid는 내가 정하고 ready는 상대가 정하며, 전송은 둘이 동시에 1인 사이클에만** 성립한다. ready를 레지스터로 받으면 1클럭 밀린다.
- 카운터는 **0부터 세고, "핸드셰이크 성립 && cnt == len-1"** 을 마지막 beat로 본다. 그래야 len=1에서도 멈추지 않는다.
- CMD와 DATA를 나눌 때의 핵심은 ready 동기화가 아니라 **트랜잭션 소유권 동기화**다.
- 쓰기 데이터는 **명령보다 먼저 들어가는 것은 안전하고, 늦게 들어가는 것은 몇 클럭까지만** 허용된다. 분리 구조에서는 CMD가 DATA를 앞서지 않게 한다.
- 라운드 로빈은 **마지막으로 처리한 쪽을 기억**하고, 마지막 beat 사이클에 다음 상태를 골라 **버블**을 없앤다.
- 파이프라이닝은 IP를 늘리는 것이 아니라 **outstanding 요청을 늘리는 것**이다.
