# Introduction

FPGA에서 DDR4를 쓰려고 MIG IP를 열면 `app_addr`, `app_rdy`, `app_wdf_rdy` 같은 신호가 나옵니다. 이 시리즈는 **MIG 위에 직접 컨트롤러를 올리고, 주소 매핑별로 성능을 재 보기까지**의 학습을 여섯 편으로 정리합니다.

| 글 | 내용 |
|----|------|
| **001** | MIG Native UI 구조 (이 글) |
| 002 | Native 컨트롤러 직접 설계 |
| 003 | 시뮬레이션 디버깅 사례 |
| 004 | AXI 인터페이스 |
| 005 | 주소 매핑 (PG150 기준) |
| 006 | 성능 측정과 해석 |

> 이 시리즈는 AMD UltraScale 계열 **DDR4 MIG(PG150)** 를 기준으로 합니다. 신호 이름과 동작은 IP 버전과 설정에 따라 다를 수 있으므로, 사용하는 버전의 문서를 확인해야 합니다. 보드와 부품 정보는 일반화해서 적었습니다.

---

# 1. 누가 무엇을 제어하나

처음 가진 의문은 이것이었습니다.

> "`app_addr`, `app_en` 같은 신호 말고, DDR과 실제로 통신하는 `addr`, `act_n` 같은 신호도 내가 제어해야 하나?"

**아닙니다.** 구조는 이렇습니다.

```
사용자 로직 ──(app_* : Native UI)──▶ MIG (컨트롤러 + PHY) ──(addr, act_n, dq ...)──▶ DDR4
```

- 사용자는 **`app_*` 신호만** 다룹니다.
- **ACT / PRE / REFRESH** 같은 DRAM 명령과 **타이밍 규칙**, 초기화와 보정(calibration)은 IP가 합니다.
- 그래서 사용자 로직이 DRAM의 세부 타이밍을 직접 맞출 필요는 없습니다.

---

# 2. Native UI 신호

자주 쓰는 신호만 정리하면 다음과 같습니다.

| 구분 | 신호 | 의미 |
|------|------|------|
| 클럭/상태 | `ui_clk`, `ui_clk_sync_rst` | 사용자 로직이 쓰는 클럭과 리셋 |
| | `init_calib_complete` | DDR 초기화와 PHY 보정 완료 |
| 명령 | `app_cmd` | 명령 종류 (쓰기/읽기) |
| | `app_en` | 명령 유효 |
| | `app_addr` | 주소 |
| | `app_rdy` | **명령(주소) 큐**가 받을 수 있음 |
| 쓰기 데이터 | `app_wdf_data` | 쓰기 데이터 |
| | `app_wdf_wren` | 쓰기 데이터 유효 |
| | `app_wdf_end` | 버스트의 마지막 데이터 |
| | `app_wdf_mask` | 바이트 마스크 |
| | `app_wdf_rdy` | **쓰기 데이터 FIFO**가 받을 수 있음 |
| 읽기 데이터 | `app_rd_data` | 읽은 데이터 |
| | `app_rd_data_valid` | 읽기 데이터 유효 |

`init_calib_complete`가 1이 되기 **전에는 요청을 넣지 않습니다.**

---

# 3. 쓰기는 두 개의 채널이다

처음에 가장 헷갈렸던 부분입니다.

> "`app_wdf_rdy`랑 `app_rdy`의 차이가 뭐지? 둘 다 rdy인데."

| 신호 | 대상 |
|------|------|
| `app_rdy` | 명령/주소 큐 |
| `app_wdf_rdy` | 쓰기 데이터 FIFO |

- 쓰기는 **명령 채널과 데이터 채널이 따로** 움직입니다. 둘은 서로 다른 큐입니다.
- **읽기는 `app_rdy`만** 봅니다. 읽기에는 쓰기 데이터가 없기 때문입니다. 데이터는 나중에 `app_rd_data_valid`로 돌아옵니다.

## app_wdf_end와 데이터 폭

> "예제에서는 `app_wdf_end`가 `wren`과 항상 같다. 버스트 전송이 아니라는 뜻인가?"

PG150 기준으로 **UI의 데이터 폭은 항상 메모리 데이터 폭의 8배**입니다 (BL8, 4:1 클럭 비). 예를 들어 DQ 폭이 32비트이면 UI 폭은 256비트입니다.

- **256비트 한 번이 곧 BL8 버스트 하나**입니다.
- 그래서 매 beat가 **그 버스트의 마지막 beat**이고, `app_wdf_end`는 매번 `wren`과 같게 됩니다.

## 바이트 마스크

`app_wdf_mask`는 **바이트 단위 쓰기 금지** 신호입니다. 비트가 **1이면 해당 바이트를 쓰지 않습니다.** (1이 "쓴다"가 아니라 "막는다"입니다.)

---

# 4. 읽기 응답은 순서로만 구분된다

> "읽기를 하면 입력한 주소 순서대로 나오는데, 어떤 주소의 데이터인지는 어떻게 아나?"

Native UI의 읽기 데이터에는 **주소나 태그가 붙지 않습니다.** 명령 순서대로 돌아오는 것으로 보고, 사용자가 **보낸 순서를 FIFO로 기억**해 대응시킵니다.

```
요청 보냄:   addr A → addr B → addr C        (FIFO에 A, B, C 저장)
응답 도착:   data(A) → data(B) → data(C)      (도착할 때마다 FIFO에서 하나씩 꺼냄)
```

---

# 5. 오류는 어떻게 알려 주나

> "트랜잭션 중간에 오류가 생겼다면 어떻게 알려 주나?"

**트랜잭션별 오류 응답은 없습니다.** 사용자가 다루는 "실패"는 두 가지입니다.

- **핸드셰이크가 아직 성립하지 않은 것** (`app_rdy` 또는 `app_wdf_rdy`가 0)
- 전체 상태 신호 (`init_calib_complete`, ECC를 켰다면 ECC 상태)

읽은 값이 틀리다면 로직의 문제가 아니라 **타이밍/보정/전원 같은 하드웨어 계층의 문제**일 가능성이 큽니다.

이때 볼 곳이 하나 있습니다. MIG는 Vivado **Hardware Manager**에서 **보정(calibration) 상태와 단계별 결과**를 보여 주는 디버그 기능을 제공합니다. `init_calib_complete`가 올라오지 않거나 데이터가 깨질 때, 보정이 **어느 단계에서 실패했는지** 확인하면 원인을 보드(배선, 전원, 부품 설정) 쪽으로 좁힐 수 있습니다.

---

# 6. 지연이 길어도 처리량은 유지할 수 있다

DDR4 접근 지연은 수십 ns입니다. "지연이 길어서 빠른 처리에는 못 쓰는 것 아닌가?" 하는 의문이 생깁니다.

**지연(latency)과 처리량(throughput)은 다릅니다.** 요청을 **파이프라인으로 계속 넣어 두면** 지연이 길어도 처리량은 깎이지 않습니다. 필요한 것은 "동시에 날아가 있는 요청 수"만큼의 FIFO입니다.

$$
\text{동시에 날아가는 요청 수} = \text{처리율} \times \text{지연}
$$

예를 들어 초당 14.88M회 조회(10G 이더넷 최소 패킷 하나당 1회 조회에 해당)를 지연 100ns로 하면 동시에 약 **1.5개**만 버티면 됩니다. 지연 때문에 불가능한 것은 **아닙니다.**

다만 DDR4의 지연은 **고정이 아닙니다.**

| 지연을 늘리는 것 | 내용 |
|------------------|------|
| **리프레시** | 약 7.8 µs마다 수백 ns 동안 접근할 수 없다 |
| **bank 충돌** | 같은 bank에서 row가 바뀌면 PRE + ACT를 기다린다(005) |
| **방향 전환** | 읽기 ↔ 쓰기를 바꿀 때마다 쉬는 시간이 생긴다(7절) |
| **재정렬** | 컨트롤러가 효율을 위해 명령 순서를 바꿀 수 있다 |

그래서 위 식은 **평균 지연이 아니라 최악 지연** 기준으로 계산해야 합니다. 평균으로 FIFO 깊이를 잡으면, 리프레시가 걸리는 순간 요청이 넘칩니다.

진짜 한계는 지연이 아니라 **랜덤 접근을 초당 몇 번 처리할 수 있는가**입니다. 이 글에서는 결론만 두고, 실측은 **006**에서 다룹니다.

---

# 7. 읽기와 쓰기는 동시에 안 된다

- 명령은 읽기와 쓰기를 섞어 넣을 수 있습니다.
- 그러나 **DQ 신호선은 반이중**이라 같은 순간에 양방향 전송은 안 됩니다.
- 방향을 바꾸는 데 시간이 걸리므로, 컨트롤러는 **같은 종류를 모아서** 처리하려고 합니다.

---

# 8. Native UI와 AXI

| | Native UI | AXI |
|---|-----------|-----|
| 구조 | MIG의 원래 인터페이스 | MIG 앞에 **AXI shim**이 한 층 더 있음 |
| 지연과 자원 | 작다 | 조금 늘어난다 |
| 쓰임 | 직접 컨트롤러를 만들 때 | Vivado IP와 쉽게 연결 (실제로 더 많이 쓰임) |

AXI shim 때문에 지연과 자원이 조금 늘어도, 표준 인터페이스라 Vivado의 다른 IP와 연결하기 쉽습니다. AXI는 **004**에서 다룹니다.

# What I Learned

- 사용자는 **`app_*`만** 다루고, DRAM 명령과 타이밍은 IP가 처리한다.
- 쓰기는 **명령 큐(`app_rdy`)와 데이터 FIFO(`app_wdf_rdy`)** 두 채널이고, 읽기는 `app_rdy`만 본다.
- UI 폭은 메모리 폭의 **8배**이고, 한 beat가 곧 BL8 버스트 하나다.
- 읽기 응답에는 주소가 없고 **순서로만 구분**된다.
- 트랜잭션별 오류 응답은 없고, `init_calib_complete`와 ECC 같은 **상태 신호**만 있다.
- 지연은 **FIFO 깊이(동시에 날아가는 요청 수)** 로 감당하되, DDR4 지연은 리프레시·bank 충돌로 들쭉날쭉하므로 **최악 지연 기준**으로 잡는다. 진짜 한계는 **랜덤 접근 처리율**이다.
- `init_calib_complete`가 안 올라오면 Hardware Manager의 **보정 디버그**로 실패 단계를 본다.
