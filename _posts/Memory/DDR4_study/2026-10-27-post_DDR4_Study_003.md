# Introduction

002에서 만든 컨트롤러를 검증하려고 **테스트벤치와 MIG 동작 모델**을 만들었고, 버그 대부분이 여기서 나왔습니다. 이 글은 그 사례와, 디버깅에서 배운 습관을 정리합니다.

> 이 단계의 교훈은 하나입니다. **증상을 정확히 본 쪽은 항상 나였고, AI는 증상을 읽지 않고 일반론을 늘어놓을 때 틀렸다.** 증상을 값으로 적고, 원인은 확인 가능한 곳(설정, 단위)부터 찾았습니다.

# 검증 환경을 만든 순서

1. **FIFO IP**를 직접 만들고, 테스트벤치가 그 FIFO에 데이터와 요청을 쓰게 했습니다.
2. 리셋 후 대기 시간이 너무 짧아(`#50`) 오류가 났습니다. FIFO IP는 **리셋이 풀린 뒤에도 잠시 쓰기를 받지 않으므로** 대기를 충분히 늘렸습니다(`#3000`).
   - 지금 보면, 고정 시간보다 FIFO Generator가 내 주는 **`wr_rst_busy` / `rd_rst_busy`가 0이 될 때까지** 기다리는 편이 낫습니다. IP 설정(클럭, 깊이)이 바뀌어도 대기 시간을 다시 맞출 필요가 없습니다.
3. "데이터를 왜 띄엄띄엄 쓰나" → 실제에 가까운 **버스트 테스트벤치**를 따로 만들었습니다.
4. MIG IP의 동작을 흉내 내는 **모델**(Native용과 AXI용)을 만들고, **랜덤 백프레셔**와 내부 메모리 배열을 넣었습니다.

## 지금 보면: 마지막에는 실제 IP로 한 번 더

직접 만든 모델은 빠르고 버그를 잡기 좋지만, **모델이 실제 MIG와 다르게 동작하면 그 차이가 그대로 숨습니다.** 아래 2번 버그(주소 단위 불일치)가 바로 "모델과 DUT의 약속이 다른" 경우였습니다.

그래서 직접 만든 모델로 기능을 잡은 뒤, 마지막에 **실제 MIG + DDR4 메모리 모델**(MIG 예제 디자인의 시뮬레이션 환경)로 한 번 돌려 보는 단계를 두는 것이 좋습니다. 보정 과정 때문에 시뮬레이션이 오래 걸리므로, PG150에 시뮬레이션 시간을 줄이는 옵션이 있는지 **확인 필요**합니다.

| 단계 | 모델 | 장점 | 한계 |
|------|------|------|------|
| 1 | 직접 만든 동작 모델 | 빠르다, 백프레셔를 마음대로 넣을 수 있다 | 실제 IP와 약속이 다를 수 있다 |
| 2 | 실제 MIG + DDR4 메모리 모델 | 실제 IP의 동작 그대로 | 느리다 |

# 버그 기록

| 증상 (내가 본 것) | 원인 |
|-------------------|------|
| `rdy`가 토글될 때 데이터가 **1클럭씩 빠짐** | ready를 **레지스터로 한 번 거치면** 그 사이클 데이터가 사라진다 → **register slice**를 추가해 해결 |
| 모델 메모리에 `mem[0..3]`이 **1, 3, 5, 7**만 남음 | **주소 단위 불일치** (아래 상세) |
| 모델에서 Read가 안 나옴 | 같은 always 블록에서 `rd_valid_pipe[0] <= 1` 뒤에 `rd_valid_pipe[0] <= 0`이 있어 **마지막 대입이 이김** |
| FIFO에 1개 썼는데 `empty`가 계속 1 | FIFO IP를 **8비트 입력 / 16비트 출력**으로 설정해서, **두 번 써야** 출력 1개가 찬다 |

## 1) ready 레지스터와 register slice

ready 신호를 한 번 레지스터로 받으면 **그 사이클의 데이터가 사라집니다.** 타이밍을 맞추려는 목적으로 레지스터를 넣을 때는 AXI의 **register slice**처럼 **데이터와 valid/ready를 함께 보관하는 구조**가 필요합니다.

register slice를 직접 만들었을 때 리뷰에서 이런 지적이 있었습니다.

> "`filled = 01`인데 `o_app_en = 0`인 경우가 있다."

`o_app_en = filled[0]`이라 **항상 1**이라고 반박했고 지적은 철회됐습니다. 두 번째 지적(가득 찬 상태에서 동시 push/pop)도, 하위 쪽이 `o_app_rdy = ~filled[1]`이면 상위가 그때 밀어 넣지 않으므로 상위가 ready를 지키는 한 손실은 아니라고 봤습니다 (전체 코드 확인이 필요한 추정입니다).

## 2) mem[0..3] = 1, 3, 5, 7의 진짜 원인

증상은 이랬습니다. 모델 메모리에 **0, 1, 2, 3, ... 7**을 차례로 썼는데 `mem[0..3]`에 **1, 3, 5, 7**만 남았습니다. 처음 AI는 "head/tail 어긋남"을 의심했고 다음엔 "랜덤 백프레셔"를 의심했지만 **둘 다 아니었습니다.**

값으로 적은 증상에서 원인이 바로 보였습니다. **"mem 0번에 데이터 0을 썼다가 다음 클럭에 1이 덮어쓴다."** 원인은 **주소 단위 불일치**입니다.

- 컨트롤러는 BL8 한 beat마다 `app_addr`를 **8씩** 올립니다. `app_addr`는 **바이트 주소가 아니라 메모리 데이터 폭 단위 주소**이고, BL8 한 번이 8칸을 차지하기 때문입니다.
- 모델은 `mem[addr >> 4]`로 `app_addr`를 **16바이트 단위 바이트 주소처럼** 여겨 인덱스를 만들었습니다.
- 그러면 주소 0과 8이 모두 `mem[0]`, 주소 16과 24가 모두 `mem[1]`이 됩니다.
- 데이터 0과 1이 `mem[0]`에 **차례로 쓰여 1이 남고**, 결과는 정확히 **1, 3, 5, 7**입니다.

고치려면 모델의 인덱스를 `addr >> 3`(8칸 = 1 beat)으로 바꿉니다.

> "`app_addr`는 **바이트 주소가 아니다**"라는 사실은 **005의 주소 매핑 수수께끼를 푸는 열쇠**이기도 합니다.

## 3) FIFO의 숨은 설정

"FIFO에 1개를 썼는데 `empty`가 안 내려간다"의 원인은 FWFT 특성이나 리셋 타이밍이 아니라 **IP 설정**이었습니다. 입력 8비트, 출력 16비트로 만들어 두었기 때문에, 출력 1개가 차려면 **두 번 써야** 합니다.

> **디버깅은 내가 만든 IP 설정(FIFO 폭, 메모리 부품 정보)부터 확인한다.** 두 번 모두 설정이 원인이었습니다.

# 증상은 값으로 적는다

디버깅에서 가장 도움이 된 습관입니다.

- 증상은 **값으로** 적는다. "1, 3, 5, 7이 남는다" 같은 패턴에서 원인이 바로 보인다.
- **내가 만든 IP 설정**부터 확인한다 (FIFO 폭, 메모리 설정).
- **모델과 DUT가 같은 약속**(주소 단위, 순서)을 쓰는지 먼저 맞추고, 마지막에는 **실제 IP**로 확인한다.
- AI에게는 증상을 그대로 주고, **일반론이 아니라 내 질문에 대한 답**을 요구한다.

# What I Learned

- 컨트롤러 버그 대부분은 **테스트벤치와 모델**에서 나왔다.
- ready를 레지스터로 받으면 데이터가 빠진다. **register slice**처럼 데이터와 valid/ready를 함께 다룬다.
- `app_addr`는 **바이트 주소가 아니라 메모리 폭 단위 주소**이고, BL8 한 beat마다 8 증가한다. 모델과 DUT의 주소 단위가 달라 **1, 3, 5, 7**이 남았다.
- 같은 always 블록에서 **마지막 대입이 이긴다.** 기본값 대입은 블록 맨 위에 둔다.
- FIFO IP의 **입출력 폭 설정**도 흔한 원인이다. 리셋 대기는 고정 시간보다 **`rst_busy` 신호**를 본다.
- 직접 만든 모델로 버그를 잡은 뒤, **실제 MIG + 메모리 모델**로 한 번 더 확인한다.
- 증상은 **값의 패턴**으로 적고, **내가 만든 설정**부터 의심한다.
