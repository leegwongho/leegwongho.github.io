# Introduction

Native 컨트롤러가 모델에서 정상 동작한 뒤, 같은 구조로 **AXI 인터페이스**를 만들었습니다. 구조는 Native와 같이 **"FIFO 입력 → AXI 신호 변환"** 으로 잡았습니다. AXI-Lite는 만들어 본 적이 있었지만 **AXI Full의 버스트와 응답**은 처음이었습니다.

> AXI 규칙은 AXI 규격(AMBA)을 기준으로 하고, MIG의 AXI 래퍼 동작은 PG150을 기준으로 합니다.

---

# 1. MIG의 AXI는 래퍼다

AXI로 MIG IP를 생성하면 코드가 두 겹으로 나옵니다.

| 모듈 | 역할 |
|------|------|
| 바깥 래퍼 (`..._axi`) | 외부에 **AXI 포트**를 제공하는 최상위 |
| 내부 AXI 컨트롤 모듈 | 그 안에서 **AXI를 Native UI로 바꾸는 부분** |

즉 AXI는 Native UI **위에 얹은 한 겹**입니다. 그래서 001에서 말한 **AXI shim** 때문에 지연과 자원이 조금 늘어납니다.

---

# 2. 다섯 채널

| 채널 | 방향 | 하는 일 |
|------|------|---------|
| **AW** | 주소 → | 쓰기 주소와 길이 |
| **W** | 데이터 → | 쓰기 데이터 (마지막 beat에 `WLAST`) |
| **B** | ← 응답 | 쓰기 **완료 응답** |
| **AR** | 주소 → | 읽기 주소와 길이 |
| **R** | ← 데이터 | 읽기 데이터와 응답 (마지막에 `RLAST`) |

## FSM을 어떻게 나눌까

"AW, W, B, AR, R을 각각 FSM으로 만들까, 하나의 FSM으로 만들까?"

Native를 만들 때 배운 대로, **처음에는 하나의 FSM으로 동작을 확인한 뒤 채널별로 나누는** 쪽이 안전합니다. 처음부터 다섯 개를 만들면 어디서 틀렸는지 찾기 어렵습니다.

---

# 3. B 채널: 버스트당 한 번

> "B는 그냥 write response만 해 주는 건가? 이름을 보면 burst일 것 같은데."

**B는 버스트(트랜잭션) 하나당 한 번** 오는 쓰기 완료 응답입니다. beat마다 오지 않습니다. 읽기에는 데이터와 응답이 **R 채널**로 오므로 B 같은 채널이 없습니다.

## B를 기다려야 다음 쓰기를 할 수 있나

> "AXI write는 B의 wr end를 받고 나서 다음을 작성하는 것 아니었나?"

**아닙니다.** B는 **완료 통지일 뿐 다음 쓰기의 허가가 아닙니다.**

- B를 기다리면 **안전하지만 동시에 날아가는 요청이 1개로 줄어** 느려집니다.
- 속도를 내려면 **B를 기다리지 않고 계속 발행**하고, 여러 개를 동시에 날립니다.

---

# 4. 길이, 크기, ID

## LEN과 beat 수

AXI-Lite와 달리 **길이(`AxLEN`)를 입력**합니다.

> **beat 수 = `LEN + 1`** 이고, `WLAST`는 **마지막 beat**에서 올립니다.

| `AWLEN` | beat 수 | `WLAST`가 1인 beat |
|---------|---------|-------------------|
| 0 | 1 | 첫 번째 |
| 3 | 4 | 네 번째 |

"3으로 작성하면 0, 1, 2, 3, 이렇게 4개"라는 이해가 맞습니다.

## AxSIZE: 비트가 아니라 바이트

> "`awsize`가 2면 2^2해서 비트가 4비트인가? 좀 이상한데?"

**비트가 아니라 바이트입니다.** `SIZE = n`이면 beat당 **2^n 바이트**입니다.

| 데이터 폭 | beat당 바이트 | `AxSIZE` |
|-----------|---------------|----------|
| 32비트 | 4 | 2 |
| 256비트 | 32 | **5** |

## ID

> "`AWID`가 뭐지?"

쓰기 **트랜잭션 번호표**입니다. 여러 요청을 동시에 날릴 때 **`BID`로 어느 요청의 완료인지** 구분합니다. 한 번에 하나만 날린다면 **0으로 고정**해도 됩니다.

ID에는 순서 규칙이 따라옵니다.

- **같은 ID**의 응답(B, R)은 요청한 **순서대로** 돌아옵니다.
- **ID가 다르면** 응답 순서가 **바뀔 수 있습니다.**

006에서 "여러 ID를 써서 동시에 날린다"를 하려면, 응답을 ID로 구분해 받는 로직이 함께 있어야 합니다. Native UI(001)에서 "순서로만 구분"하던 것과 대비되는 점입니다.

## 4KB 경계

AXI 버스트는 **4KB 주소 경계를 넘으면 안 됩니다.** 예를 들어 시작 주소가 4KB 경계 직전이면 그만큼 짧은 버스트로 나눠야 합니다. DDR에 긴 버스트를 내는 마스터를 만들 때 가장 놓치기 쉬운 규칙입니다. 버스트 하나는 최대 256 beat(INCR)까지지만, 이 경계 때문에 실제로는 더 짧아질 수 있습니다.

## WSTRB와 app_wdf_mask는 반대

| 신호 | 단위 | 1의 의미 |
|------|------|----------|
| AXI `WSTRB` | 바이트 | **쓴다** |
| Native `app_wdf_mask` | 바이트 | **막는다**(쓰지 않는다, 001) |

같은 바이트 선택 신호지만 **극성이 반대**입니다. 모든 바이트를 쓰려면 `WSTRB`는 모두 1, `app_wdf_mask`는 모두 0입니다. AXI ↔ Native를 직접 변환하는 로직을 만들 때 그대로 연결하면 모든 쓰기가 막힙니다.

# 5. AW와 W는 독립이다

> "주소를 작성하고 2클럭 이내에 데이터를 보내지 않고 3클럭쯤 기다린 뒤 보내면 어떤 증상이 생기나? 데이터가 깨지지는 않나?"

- AXI는 **AW와 W를 시간적으로 완전히 분리**해도 **순서만 맞으면** 됩니다.
- 늦게 보내면 데이터가 깨지지는 않습니다. **명령 큐가 차서 `AWREADY`가 내려가는 성능 문제**만 생길 수 있습니다.
- "2클럭"은 **Native UI의 약속**이고 AXI 쪽 약속이 아닙니다 (002의 "데이터가 명령보다 늦는 경우"). AXI에서는 그 처리를 MIG 안쪽 변환 로직이 맡습니다.
- AXI 규격상 **W가 AW보다 먼저 와도** 됩니다. 받는 쪽은 둘 중 어느 것이 먼저 와도 처리해야 합니다.
- 그래도 실무에서는 디버깅하기 쉽게 **AW 발행 직후에 그 요청의 W를 보내는 식으로 묶는** 경우가 많습니다.

Native에서 먼저 부딪힌 **"주소와 데이터는 순서로 짝짓는다"** 는 개념이 AXI의 AW/W 분리와 **같은 원리**라는 것을 여기서 확인했습니다.

---

# 6. 생성된 IP 설정 확인

AXI로 생성한 IP의 설정 주석에서 **메모리 부품 설정과 클럭 설정**을 확인해야 합니다. 이 설정은 **실제 보드의 메모리와 같아야** 합니다.

- 부품 정보(Memory Part)가 실제와 다르면 **주소 폭, 속도 등급, 타이밍 파라미터**가 달라집니다.
- 이 차이는 005의 주소 폭 계산(28 vs 29 vs 31비트)에서 그대로 드러납니다.

# What I Learned

- MIG의 AXI는 **Native UI 위의 래퍼**이고, 안쪽에서 AXI를 Native로 바꾼다.
- **B는 버스트당 한 번**의 완료 응답이고 다음 쓰기의 허가가 아니다. 속도를 내려면 **B를 기다리지 않고 계속 발행**한다.
- **beat 수 = `LEN + 1`**, `WLAST`는 마지막 beat, **`AxSIZE`는 바이트 단위**(256비트 = 5)다.
- 버스트는 **4KB 경계를 넘지 않는다.** `WSTRB`(1 = 쓴다)와 `app_wdf_mask`(1 = 막는다)는 **극성이 반대**다.
- 같은 ID의 응답은 순서대로, **다른 ID끼리는 순서가 바뀔 수 있다.**
- **AW와 W는 독립**이고 순서만 맞으면 된다. 늦어도 깨지지 않고 성능만 영향을 받는다.
- 구현은 **하나의 FSM으로 시작해서 채널별로 나눈다.**
- IP 설정(부품 정보)은 실제 메모리와 맞아야 하고, **주소 폭이 그 설정에서 결정**된다.
