# Introduction

앞선 글에서 PCIe의 구조(001~002)와 QDMA의 큐 구조(003~004)를 정리했습니다. 이번 글은 이 지식을 **실제 보드에서 처음 확인했던 과정**을 정리합니다.

- QDMA **예제 디자인**으로 PCIe 링크가 올라오는지 확인
- 호스트에서 `lspci`로 장치가 보이는지 확인
- **오픈소스 NIC 구조(OpenNIC)** 를 활용한 송수신 시험

> 이 글은 일반적으로 공개할 수 있는 범위만 다룹니다. 업무 프로젝트와 관련된 구체적인 설계, 설정, 측정 결과는 포함하지 않습니다.

# Step 1: QDMA Example Design으로 시작

QDMA IP를 처음 사용할 때는 사용자 로직부터 만들지 않고 **예제 디자인(Example Design)** 으로 시작했습니다. Project 01에서 CMAC 예제 디자인으로 구조를 익힌 것(004 글)과 같은 접근입니다.

예제 디자인으로 시작하면 다음과 같은 장점이 있습니다.

- IP를 올바르게 연결한 **기준 디자인**이 있다.
- 문제가 생겼을 때 "내 로직 문제인가, IP·보드 설정 문제인가"를 나누어 볼 수 있다.
- 사용자 로직을 붙이기 전에 **PCIe 링크 자체**를 먼저 확인할 수 있다.

IP 설정과 포트는 **PG302의 인터페이스 부분**을 참고했습니다. 포트 이름과 의미는 IP 버전마다 조금씩 다르므로, 사용하는 버전의 문서에서 확인해야 합니다.

---

# Step 2: 링크 확인은 두 곳에서 한다

PCIe 링크는 **FPGA 쪽**과 **호스트 쪽** 양쪽에서 확인합니다. 한쪽만 보면 놓치는 문제가 있기 때문입니다.

## FPGA 쪽: ILA로 link up 확인

PCIe IP는 링크 상태를 나타내는 **link up 신호**를 냅니다. Project 01에서 `stat_rx_aligned`를 링크 지표로 정한 것(004 글)과 같은 역할입니다.

- ILA에 link up 신호를 연결합니다.
- 이 신호가 1이 되는지, 그리고 **안정적으로 유지되는지** 확인합니다.
- 함께 **클럭과 리셋 신호**도 보면 원인을 좁히기 쉽습니다.

## 호스트 쪽: lspci로 장치 확인

호스트에서는 `lspci`로 장치가 보이는지 확인합니다.

```bash
lspci | grep -i xilinx          # 장치가 보이는가 (벤더 이름은 설정에 따라 다를 수 있음)
sudo lspci -s <BDF> -vv         # 상세 정보
```

`-vv` 출력에서 확인할 항목입니다.

| 항목 | 의미 |
|------|------|
| **Region 0, 1, …** | BAR 할당 여부와 크기 (002 글의 BAR) |
| **LnkCap** | 장치가 지원하는 최대 속도와 Lane 수 |
| **LnkSta** | **실제로 협상된** 속도와 Lane 수 |

`LnkCap`은 x16 Gen3인데 `LnkSta`가 x8이나 Gen1로 나오면 링크가 기대보다 낮게 올라온 것입니다. 001에서 본 **링크 트레이닝이 양쪽이 지원하는 값 중 낮은 쪽으로 협상**한다는 내용이 그대로 보이는 부분입니다. 이 경우 슬롯 배선, 참조 클럭, 리셋 타이밍을 의심합니다.

## 확인 시 주의할 점

- PCIe 장치는 **호스트 부팅 시 Enumeration**으로 인식됩니다. FPGA를 나중에 프로그래밍하면 호스트가 장치를 못 찾을 수 있어서, 보통 호스트 재부팅이나 PCIe rescan이 필요합니다.
- 호스트 전원과 FPGA 프로그래밍 순서가 중요할 수 있습니다.
- 저도 처음에는 **ILA에서는 link up이 보이는데 `lspci`에는 장치가 보이지 않았습니다.** 문의해 보니 서버에 드라이버를 설치해야 한다는 답을 받았고, 설치한 뒤에 장치가 확인되었습니다. 다만 장치가 `lspci`에 나타나는 것은 원래 드라이버와 무관한 Enumeration 단계이므로, 당시 호스트 재부팅 같은 다른 조치가 함께 있었을 가능성이 있습니다. 어느 쪽이었는지는 기록이 남아 있지 않아 확정하지 못했습니다.

---

# 이 단계에서 확인된 것과 아닌 것

`lspci`에 장치가 보인다는 것은 다음까지 확인했다는 뜻입니다.

- Physical Layer: 링크 트레이닝 성공
- Data Link Layer: 링크 정상
- Configuration Space: 호스트가 장치의 설정 공간을 읽음, BAR 할당

하지만 **DMA 데이터 전송이 정상이라는 뜻은 아닙니다.** DMA에는 004에서 본 큐 설정, Descriptor, PIDX 갱신, 완료 처리라는 별도의 단계가 있습니다. 장치가 보이는 것과 데이터가 오가는 것은 **서로 다른 확인 단계**로 나누어 보아야 합니다.

| 단계 | 확인 방법 | 확인되는 것 |
|------|----------|-------------|
| 1 | ILA의 link up | FPGA 쪽 링크 |
| 2 | `lspci` 장치 표시, `LnkSta` | 호스트에서의 인식, 협상된 속도와 Lane 수 |
| 3 | BAR 접근 (레지스터 읽기/쓰기) | MMIO 동작 |
| 4 | DMA 송수신 | 큐, Descriptor, 완료 처리 |

---

# Step 3: 오픈소스 NIC 구조로 송수신 시험

링크와 장치 인식을 확인한 뒤에는 **오픈소스 NIC 구조(OpenNIC)** 를 활용해 실제 데이터 송수신을 시험했습니다.

이 시험은 지금까지 정리한 요소들이 **하나의 경로로 이어져 동작하는지** 확인하는 것이었습니다.

```
네트워크 ⇄ CMAC ⇄ (AXI4-Stream) ⇄ QDMA ⇄ PCIe ⇄ 호스트 메모리 / 드라이버
 Project 01       003~004       001~002
```

- **CMAC**: Project 01에서 다룬 100G Ethernet MAC
- **QDMA**: 003~004에서 본 큐 기반 DMA (C2H는 수신, H2C는 송신)
- **PCIe**: 001~002에서 본 링크와 TLP
- **호스트 드라이버**: 큐와 Descriptor를 관리

네트워크에서 받은 프레임이 CMAC과 QDMA를 지나 호스트 메모리에 도착하고, 호스트가 만든 데이터는 반대 방향으로 나가는 구조입니다.

## 이 글에서 다루지 않는 것

오픈소스 NIC 구조를 활용한 송수신 시험을 했다는 것까지만 정리합니다. 구체적인 설정과 측정 결과는 다루지 않습니다.

# 두 IP를 연결할 때 생각할 점

CMAC과 QDMA처럼 서로 다른 IP를 AXI4-Stream으로 연결할 때, 일반적으로 확인해야 할 것들입니다.

| 항목 | 확인할 것 |
|------|----------|
| **데이터 폭** | 두 IP의 AXI4-Stream 폭이 같은가. 다르면 폭 변환이 필요 |
| **클럭 도메인** | CMAC의 사용자 클럭은 약 322.266MHz다. QDMA의 사용자 클럭은 PCIe 링크 설정에 따라 정해지므로 **같다는 보장이 없다.** 다르면 CDC가 필요 |
| **패킷 경계** | `tlast`와 `tkeep`이 프레임 경계를 올바르게 표현하는가 (006 글) |
| **역압** | CMAC RX에는 `tready`가 없으므로, 받는 쪽이 느리면 어디서 버퍼링할 것인가 (007 글) |
| **큐 선택** | 받은 패킷을 어느 큐로 보낼 것인가 (RSS 등) |

Project 01의 CMAC 안에서는 TX/RX가 같은 클럭이라 CDC가 필요 없었지만, **서로 다른 IP 사이에는 클럭이 다를 수 있다**는 점이 대조적입니다. 이 구간에서는 007의 "FIFO는 필요하지만 CDC는 필요 없었다"는 결론이 그대로 적용되지 않습니다.

# What I Learned

- IP는 **예제 디자인으로 시작**하면 문제를 IP·보드 쪽과 내 로직 쪽으로 나누어 볼 수 있다.
- PCIe 링크는 **FPGA의 link up과 호스트의 `lspci`(`LnkSta`)** 양쪽에서 확인한다.
- `lspci`에 장치가 보이는 것은 링크와 Configuration까지의 확인이고, **DMA 동작은 별도의 단계**다.
- FPGA를 프로그래밍한 뒤에는 호스트가 장치를 다시 인식하도록 **재부팅 또는 rescan**이 필요할 수 있다.
- 송수신 시험은 **CMAC, QDMA, PCIe, 드라이버가 한 경로로 이어진 구조**에서 확인한다.
