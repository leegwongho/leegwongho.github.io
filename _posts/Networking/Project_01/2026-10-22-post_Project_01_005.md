# Packet vs Frame

네트워크에서는 계층마다 데이터 단위를 부르는 이름이 다릅니다.

| Layer | Unit |
|-------|------|
| L2 (Data Link, Ethernet) | **Frame** |
| L3 (IP) | Packet |
| L4 (TCP/UDP) | Segment / Datagram |

CMAC은 Ethernet MAC이므로 **L2, 즉 Frame 단위**로 동작합니다. 그래서 TPG도 임의의 데이터가 아니라 Ethernet Frame 형태로 만들기로 했습니다.

---

# Ethernet Frame Structure

기본 Ethernet II 프레임은 아래와 같이 구성됩니다.

```
| Preamble | SFD | Dest MAC | Src MAC | EtherType | Payload   | FCS  |
|   7 B    | 1 B |   6 B    |   6 B   |   2 B     | 46~1500 B | 4 B  |
```

| Field | Size | Description |
|-------|------|-------------|
| Preamble | 7 B | 수신 측이 비트 타이밍을 맞추기 위한 `1010...` 비트 패턴 (바이트 값 `0x55`) |
| SFD | 1 B | 프레임 시작을 알리는 Start Frame Delimiter. 비트 패턴 `10101011` (바이트 값 `0xD5`) |
| Destination MAC | 6 B | 받는 쪽 주소 |
| Source MAC | 6 B | 보내는 쪽 주소 |
| EtherType | 2 B | Payload의 종류. 예: IPv4 `0x0800`, ARP `0x0806`, IPv6 `0x86DD` |
| Payload | 46 ~ 1500 B | 실제 데이터 (IP 패킷 등) |
| FCS | 4 B | 프레임 오류를 검출하는 CRC-32 |

> Preamble과 SFD는 비트 패턴으로 쓰는 경우와 바이트 값으로 쓰는 경우가 섞여 있어 헷갈리기 쉽습니다. 이더넷은 각 바이트를 **LSB부터** 전송하므로, 선로에 `10101011` 순서로 나가는 SFD는 바이트 값으로 `0xD5`입니다.

## Size

- Destination MAC부터 FCS까지의 길이가 **최소 64 B, 최대 1518 B**입니다. (VLAN 태그가 붙으면 4 B가 늘어납니다.)
- Payload가 46 B보다 짧으면 Padding으로 채워 최소 길이를 맞춥니다.
- 프레임 사이에는 최소 **12 B의 IPG(Inter-Packet Gap, IFG라고도 함)** 가 필요합니다.
- Preamble과 SFD는 프레임 길이에 포함하지 않는 것이 일반적입니다.

**64 B** 라는 최소 길이는 이 프로젝트에서 중요한 기준이 됩니다. 다음 글에서 이 숫자와 다시 만납니다. **12 B IPG**는 008에서 다시 나옵니다.

# IPv4 Frame의 쌓임

가장 흔한 IPv4/UDP 프레임은 다음과 같이 헤더가 쌓입니다.

```
[ Ethernet Header 14 B ][ IPv4 Header 20 B ][ UDP Header 8 B ][ Data ][ FCS 4 B ]
```

EtherType이 `0x0800`이면 그 뒤를 IPv4로 해석합니다. 이 구조는 이후 RSS나 패킷 분배를 다룰 때 **필드를 어느 위치에서 읽는지**의 기준이 되므로 알아 두어야 합니다.

# AXI4-Stream으로 Frame 보내기

CMAC의 사용자 인터페이스는 IP 생성 시 **LBUS(segmented local bus)** 와 **AXI4-Stream** 중에서 고를 수 있고, 이번에는 AXI4-Stream을 선택했습니다. 데이터 폭은 **512비트(64 Byte)** 였기 때문에, 64 B 프레임은 **한 번의 beat** 로 전송할 수 있습니다.

AXI4-Stream에서 아래 신호가 프레임을 표현합니다.

| Signal | Width | Meaning |
|--------|-------|---------|
| `tdata` | 512 bit | 프레임 데이터 |
| `tvalid` | 1 bit | 데이터가 유효함 |
| `tready` | 1 bit | 받는 쪽이 받을 준비가 됨 (TX에만 있음, RX에는 없음) |
| `tlast` | 1 bit | 프레임의 마지막 beat |
| `tkeep` | **64 bit** | 각 Byte가 유효한지 표시 (Byte당 1비트) |
| `tuser` | 1 bit | 에러 표시 |

여기서 **`tkeep`** 은 Byte마다 1비트이므로 512비트 버스에서는 **64비트**입니다. 64 B를 보낸다면 64비트가 모두 1이어야 합니다. 이 폭은 다음 글의 핵심이 됩니다.

## 바이트 순서

AXI4-Stream에서는 **`tdata[7:0]`이 프레임의 첫 바이트**(Destination MAC의 첫 바이트)이고, 위로 갈수록 뒤의 바이트입니다. `tkeep[0]`이 `tdata[7:0]`에 대응합니다. 프레임을 사람이 읽는 순서대로 `tdata[511:504]`부터 채우면 순서가 뒤집히므로 주의해야 합니다.

## TX의 연속성

CMAC TX에 프레임을 넣을 때는 **한 프레임이 시작되면 `tlast`까지 `tvalid`를 끊지 않는 것**이 원칙입니다. 64 B 프레임은 한 beat라 문제가 되지 않지만, 여러 beat짜리 프레임을 다른 경로(FIFO 등)에서 가져올 때 중요해집니다(007).

# 직접 만든 TPG

처음부터 Ethernet Frame 형태에 맞춰 TPG를 직접 작성했습니다.

## Frame 구성 (당시)

| Field | Value |
|-------|-------|
| Destination MAC | `55:44:33:22:11:00` |
| Source MAC | `00:11:22:33:44:55` |
| EtherType | `0x0800` (IPv4) |
| Payload | 46 B |
| FCS 위치 | `DEADBEEF` 로 채움 |
| TPG가 보낸 길이 | 14 + 46 + 4 = **64 B** |

512비트 1 beat로 한 번에 전송하며, `tkeep`은 `64'hFFFF_FFFF_FFFF_FFFF`, `tuser`는 0으로 두었습니다.

## 상태 머신

```
IDLE → WAIT_READY → SEND → DONE
```

- `tpg_start` 입력이 들어오면 패킷 **한 개**를 전송합니다.
- `tready`를 확인한 뒤 `tvalid`와 데이터를 내보냅니다.

## IP 쪽 설정

TPG와 함께 CMAC의 다음 옵션을 설정했습니다.

- FCS 삽입(TX) / 제거(RX): 켬
- Preamble/SFD 검사: 끔
- 최소 패킷 길이: 64

즉 CMAC이 받아들이는 최소 길이도 **64 B**로 정해 두었습니다.

## 지금 보면: FCS를 두 번 넣었다

CMAC의 **FCS 삽입이 켜져 있으면, CMAC이 사용자 데이터 뒤에 FCS 4 B를 직접 계산해 붙입니다.** 따라서 TPG는 FCS를 빼고 보내야 합니다.

| | TPG가 보낸 데이터 | CMAC이 붙인 FCS | 선로의 프레임 길이 |
|---|---|---|---|
| 당시 | 60 B + `DEADBEEF` 4 B = 64 B | 4 B | **68 B** |
| 의도대로 하려면 | 60 B (Header 14 + Payload 46) | 4 B | **64 B** |

당시 구성에서는 선로에 68 B 프레임이 나갔고, RX에서 FCS 제거가 켜져 있으므로 받는 쪽에는 `DEADBEEF`가 **데이터의 마지막 4 B로** 보였을 것입니다. 동작에는 문제가 없었지만 "64 B 최소 프레임을 보낸다"는 의도와는 달랐습니다.

반대로 FCS를 TPG가 직접 계산해 넣고 싶다면 CMAC의 FCS 삽입을 꺼야 합니다. 이때 `DEADBEEF` 같은 임의 값을 넣으면 수신 측에서 FCS 에러가 납니다.

# What I Learned

- "패킷을 만든다"는 말은 먼저 **어떤 계층의 단위인지**를 정해야 한다.
- Ethernet Frame은 Destination MAC, Source MAC, EtherType, Payload, FCS로 구성되며 최소 64 B, 최대 1518 B이다.
- SFD처럼 비트 패턴과 바이트 값이 다르게 보이는 필드는 전송 순서(LSB first)를 생각해야 한다.
- AXI4-Stream 폭이 512비트이면 `tkeep`은 64비트이고, 첫 바이트는 `tdata[7:0]`이다.
- **FCS 삽입을 IP에 맡겼으면 사용자 데이터에 FCS를 넣지 않는다.**
- 이후 RSS, 패킷 분배처럼 헤더 필드를 읽는 작업의 출발점도 이 프레임 구조다.
