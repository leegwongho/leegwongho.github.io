# Introduction

앞선 글에서 100G Ethernet의 구조와 개발 환경을 살펴보았습니다. 이번 글부터는 VCU128 보드에 CMAC IP를 올리고 **링크가 올라오는 것까지** 확인한 과정을 정리합니다.

> 이 시리즈는 2025년 1~3월에 진행한 작업을 당시 기록을 바탕으로 2026년에 다시 정리한 회고입니다. Vivado 프로젝트와 화면 캡처는 남아 있지 않아, 설정 값 중 기억에 의존한 부분은 그렇게 표시했습니다.

---

# Goal

프로젝트의 최종 목표는 CMAC을 통해 100G 데이터를 주고받는 것이었고, 첫 단계 과제는 다음과 같았습니다.

- FPGA 내부 로직에서 **TPG(Test Pattern Generator)** 로 패킷을 생성한다.
- 이 패킷을 CMAC을 통해 **Loopback** 시켜 다시 수신한다.

그 전에 먼저 해결해야 할 것은 "CMAC이 보드 위에서 정상적으로 링크를 맺는가"였습니다.

---

# Step 1: Example Design으로 구조 익히기

IP를 처음 다루는 단계라, Vivado에서 CMAC IP를 생성하고 **Example Design** 을 열어 구조부터 파악했습니다.

- TX와 RX를 연결한 시뮬레이션을 돌려 보며 예제 신호를 하나씩 확인했습니다.
- `gt_rxp_in`, `gt_ref_clk_p`, `init_clk`, `send_continuous_pkts`, `tx_done_led`, `tx_busy_led`처럼 처음 보는 신호가 많아서, 각 신호가 **왜 있는지**를 먼저 이해하려고 했습니다.
- 예제의 CDC 동기화 모듈과 `(* ASYNC_REG *)` 속성, 322.266MHz 클럭을 쓰는 이유도 이때 공부했습니다.

시뮬레이션에서는 콘솔이 `GT LOCKED` → `AXI4-Lite 설정 완료` → `WAITING FOR CMAC RX_ALIGNED`에서 오래 머물렀고, 시뮬레이션 시간이 너무 길었습니다. 그래서 시뮬레이션을 더 붙잡기보다 **보드에서 바로 실험**하는 쪽으로 방향을 바꿨습니다.

> 지금 보면: RX 정렬을 기다리는 단계가 긴 것은 PCS가 20개 PCS lane의 정렬 마커를 모두 찾아야 하기 때문입니다. PG203에는 시뮬레이션에서 정렬 마커 간격을 줄이는 **Simulation Speed Up** 방법이 설명되어 있어, 이를 적용했다면 시뮬레이션을 더 이어 갈 수 있었을 것입니다. (006에서 이 선택의 대가를 다시 이야기합니다.)

# Step 2: CMAC IP Configuration

처음 IP를 생성하면서 가장 당황했던 점은 **설정해야 할 항목이 생각보다 훨씬 많다**는 것이었습니다. 10G, 25G, 100G 같은 속도만 고르면 끝날 것이라고 생각했는데, Lane 구성, 클럭, FEC 같은 Physical 쪽 설정까지 함께 결정해야 했습니다. 003에서 정리한 것처럼 CMAC이 MAC뿐 아니라 **PCS와 RS-FEC까지 포함**하기 때문입니다.

당시 선택한 주요 설정은 아래와 같습니다.

| Item | Setting | Note |
|------|---------|------|
| Line Interface | CAUI-4 | 25.78125G × 4 Lane |
| User Interface | AXI4-Stream (512 bit) | LBUS와 AXI4-Stream 중 선택 |
| User Clock (`txusrclk2`) | 322.266 MHz | CAUI-4에서 고정 값 |
| GT Reference Clock | **확인 필요** | 보통 156.25 / 161.1328125 / 322.265625 MHz 중 선택. VCU128 QSFP 클럭 소스(UG1302)와 맞춰야 함 |
| Init Clock (`init_clk`) | 100 MHz | 기억 기준 |
| RS-FEC | 사용 안 함 | |
| GT / CMAC 위치 | VCU128 QSFP28 연결에 맞춰 선택 | 보드 문서와 XDC 참고 |

> 처음 정리할 때는 "Reference Clock 100 MHz"로 적었습니다. 하지만 CMAC 예제에는 GT 참조 클럭(`gt_ref_clk_p/n`)과 별도로 GT 초기화용 free-running 클럭(`init_clk`)이 있고, 100 MHz는 보통 `init_clk` 값입니다. 기억이 두 클럭을 섞었을 가능성이 커서 표를 나누었습니다.

GT 선택과 CMAC 위치는 IP 옵션이라기보다 **보드가 정해 주는 값**에 가깝습니다. QSFP28 포트가 어떤 GT에 연결되어 있는지는 VCU128 보드 문서와 XDC를 보고 결정했습니다.

## CAUI-4

CAUI-4는 25.78125 Gbps Lane 4개로 100Gb Link를 구성하는 방식입니다. 003 글에서 설명한 QSFP28의 4 Lane 구조와 같습니다.

## Clock

CMAC에는 역할이 다른 클럭이 세 종류 있습니다. 처음에는 역할이 구분되지 않아 어느 클럭이 어디에 연결되는지 이해하는 데 시간이 걸렸습니다.

| 클럭 | 역할 |
|------|------|
| GT 참조 클럭 (`gt_ref_clk`) | GT PLL의 기준. 보드의 클럭 소스에서 들어옴 |
| `txusrclk2` (322.266 MHz) | GT에서 만들어져 CMAC TX, **사용자 AXI4-Stream 인터페이스**, 제어/상태 포트를 구동 |
| `init_clk` | GT 초기화와 리셋 로직용 free-running 클럭 |

RX 쪽 사용자 인터페이스 클럭은 007에서 다룹니다(이 구성에서는 TX와 같은 클럭).

## RS-FEC

이번 프로젝트에서는 RS-FEC를 사용하지 않도록 설정했습니다. RS-FEC는 **양쪽 장비가 같은 설정**이어야 링크가 올라오므로, 계측기 설정과도 맞춰야 합니다.

# Step 3: 링크 확인 기준 정하기

기능을 검증하기 전에, 먼저 **"연결되었다"를 판단할 단일 지표**를 정했습니다. 데이터시트에서 찾아 고른 신호는 `stat_rx_aligned`입니다.

- 이 신호가 1이면 RX 쪽 PCS가 **20개 PCS lane의 정렬과 deskew를 모두 끝낸** 상태입니다(003 참고).
- ILA와 보드 LED에 연결해서 눈으로 바로 확인할 수 있게 했습니다.

이렇게 **링크 상태와 데이터 경로를 분리**해 둔 것이 이후에 도움이 되었습니다. 나중에 RX 데이터가 나오지 않았을 때도 "링크는 정상"이라는 전제로 의심할 범위를 좁힐 수 있었기 때문입니다.

## 링크가 올라온 뒤 TX를 켜는 순서

`stat_rx_aligned`는 RX 쪽 지표입니다. TX가 데이터를 내보내려면 제어 신호도 순서대로 켜야 합니다. 예제 시뮬레이션의 "AXI4-Lite 설정 완료" 단계가 이 과정이었습니다.

1. `ctl_rx_enable = 1`, 그리고 `ctl_tx_send_rfi = 1` (아직 수신 정렬 전이므로 상대에게 Remote Fault를 알림)
2. `stat_rx_aligned = 1` 확인
3. `ctl_tx_send_rfi = 0`, `ctl_tx_enable = 1`

AXI4-Lite 인터페이스를 포함한 구성에서는 이 값들이 레지스터(PG203 기준 `0x000C`의 `ctl_tx_enable`, `ctl_tx_send_lfi`, `ctl_tx_send_rfi` 등)로 제어됩니다.

## QSFP 광모듈 초기화

링크를 올리는 과정에서 알게 된 점이 하나 더 있습니다. **광모듈(QSFP)은 제어 핀이 올바른 레벨이어야 하고, 그렇지 않으면 링크가 올라오지 않습니다.** FPGA 설계에서 모듈의 제어 핀을 최상위 모듈이 직접 구동하도록 했습니다.

| 핀 (SFF-8679 표준명) | 방향 | 동작 레벨 | 의미 |
|---------------------|------|-----------|------|
| `ResetL` | FPGA → 모듈 | 1 (해제) | Low면 모듈 리셋 상태 |
| `LPMode` | FPGA → 모듈 | 0 | High면 저전력 모드라 고출력 광모듈이 동작하지 않을 수 있음 |
| `ModSelL` | FPGA → 모듈 | 0 | Low일 때 모듈이 I2C(관리 인터페이스)에 응답 |
| `ModPrsL` | 모듈 → FPGA | 0이면 장착 | 모듈 장착 여부 |
| `IntL` | 모듈 → FPGA | 0이면 인터럽트 | 모듈 상태 알림 |

> 당시 각 핀을 어떤 값으로 고정했는지는 기록 확인이 필요합니다. 위 표는 표준 기준의 일반적인 동작 레벨입니다.

CMAC 설정이 맞더라도 보드 쪽 신호가 준비되지 않으면 `stat_rx_aligned`가 올라오지 않습니다.

# 루프백 방식

이후 글(005, 006)의 TPG 루프백에서 쓸 수 있는 방식은 두 가지입니다.

| 방식 | 설정 | 확인 범위 |
|------|------|-----------|
| GT 내부 루프백 (near-end PMA) | `gt_loopback_in` 포트 또는 AXI4-Lite `0x0090`의 `ctl_gt_loopback` | CMAC + GT까지. 광모듈과 케이블은 제외 |
| 외부 루프백 | `ctl_gt_loopback = 0`(일반 동작) + 루프백 모듈 또는 광 케이블로 TX↔RX 연결 | 광모듈까지 포함한 전체 경로 |

> 당시 TPG 루프백을 어느 방식으로 했는지는 기록 확인이 필요합니다.

참고로 OpenNIC 드라이버가 루프백을 켤 때 쓰는 레지스터 `0x8090`은, CMAC0 레지스터 영역 베이스 `0x8000`에 이 `0x0090`을 더한 값으로 보입니다(OpenNIC 소스로 확인한 것은 아님). 같은 CMAC 기능을 다른 프로젝트가 그대로 노출하고 있는 셈입니다.

# 참조 문서 버전 주의

처음 학습할 때 올려 둔 문서는 **PG165(UltraScale용)** 이었습니다. VCU128에서 쓰는 `cmac_usplus` IP는 UltraScale+용이므로 맞는 문서는 **PG203** 입니다.

IP 이름이 `cmac_usplus`라면 `usplus`에 대응하는 문서를 보는 것이 맞습니다. 세부 동작을 확인할 때는 문서 버전부터 확인하는 습관이 필요했습니다.

# What I Learned

- CMAC은 속도만 고르는 IP가 아니라, MAC과 PCS를 함께 가진 IP라서 Lane 구성, 클럭, FEC까지 함께 정해야 한다.
- GT와 CMAC 위치는 IP가 아니라 **보드 문서와 XDC** 가 정한다.
- CMAC의 클럭은 **GT 참조 클럭, `txusrclk2`, `init_clk`** 세 가지로 역할이 다르다.
- 기능을 검증하기 전에 "연결되었는가"를 판단할 지표(`stat_rx_aligned`)를 먼저 정한다. 이는 20개 PCS lane의 정렬 완료를 뜻한다.
- 링크가 올라와도 TX는 `ctl_tx_enable` 등 제어 순서를 거쳐야 데이터를 내보낸다.
- 광모듈은 FPGA 로직이 제어 핀을 올바른 레벨로 구동해 주어야 한다.
- 참조 문서가 내가 쓰는 IP와 같은 세대·버전인지 먼저 확인한다.
