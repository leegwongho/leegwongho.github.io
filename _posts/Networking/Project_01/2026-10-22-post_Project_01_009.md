# 이 프로젝트에서 배운 것

## 1. 측정하는 신호가 실제 신호인지 의심한다

가장 오래 걸린 두 문제(`tkeep` 1비트 wire, FIFO 카운트 불일치)는 모두 **"내가 보는 신호가 IP가 실제로 받는 신호인가", "내가 세는 값이 실제 이벤트인가"** 를 늦게 의심해서 길어졌습니다. ILA는 IP 포트에 연결된 네트에, 카운터는 유효 beat 기준에 맞춰야 합니다.

## 2. 가설이 계속 틀리면 공통 전제를 의심한다

006의 가설 1~6은 모두 "TPG가 보내는 데이터가 틀렸다"는 전제 위에 있었습니다. 가설을 하나 더 만들기 전에, 이미 틀린 가설들이 무엇을 함께 가정하는지를 보는 것이 더 빨랐습니다.

## 3. 목적이 앞서면 구조를 과하게 만든다

"클럭을 분리해 보자"는 목적이 먼저여서 CDC 구조를 만들었지만, CMAC은 TX/RX가 같은 클럭이라 CDC는 필요하지 않았습니다. 필요했던 것은 역압이 없는 RX를 받아 줄 FIFO였습니다. 무엇이 필요한지 먼저 따져 보는 습관이 필요했습니다.

## 4. 외부 답변과 문서를 확인한다

- AI가 제시한 수정 코드와 설명 중에는 틀린 것이 있었습니다(66바이트 `tdata`, 항상 1이 되는 `tvalid`, TX/RX가 다른 클럭이라는 답).
- 참조 문서가 내 IP와 같은 세대인지부터 확인해야 합니다(PG165와 PG203).

## 5. 기록을 남긴다

이 시리즈를 정리하면서 가장 아쉬웠던 것은 기억과 기록이 달랐던 점입니다. 문제가 풀린 시점에 **증상 / 원인 / 수정 / 근거**를 한 줄씩 남겨 두었다면 회고가 훨씬 정확했을 것입니다.

## 6. 풀리지 않은 문제도 나중에 다시 보인다

0.0001% 미수신은 당시에는 풀지 못했습니다. 이후 다른 프로젝트에서 TX IPG를 줄여 100% 부하로 장기간 시험해 보니 큰 문제가 없었고, 그 경험으로 원인을 **클럭 ppm 차이와 TX IPG 여유 부족**으로 다시 보게 되었습니다. 다만 같은 시험을 다시 할 수 없어 가설로 남겨 둡니다.

# 남아 있는 것

- 0.0001% 미수신의 원인은 확정하지 못했습니다. (008)
- 당시 FPGA 내부 프레임 카운터의 신뢰성에는 한계가 있습니다. (007)
- FIFO 카운트 불일치의 원인 분석은 코드를 다시 읽고 내린 가설이며, 시험으로 확인하지 않았습니다. (007)
- IP 설정의 일부 값(클럭, GT 쿼드 등)은 기억에 의존했습니다. (004)

# 시리즈 체크리스트

시리즈 전체에서 모은 항목입니다.

**코드와 합성**
- [ ] RTL 파일 상단에 `` `default_nettype none ``
- [ ] 합성 후 포트 폭 불일치와 미연결 경고 확인

**CMAC 디버깅**
- [ ] ILA 프로브는 IP 포트에 연결된 네트에
- [ ] TX는 `tvalid`, `tready`, `tlast`, `tkeep`, `tuser`를 함께 보고 트리거
- [ ] 통계 신호는 증가분인지 누적인지 먼저 확인
- [ ] RX가 안 나오면 패킷 길이(64 B 이상)부터 확인

**FIFO와 클럭**
- [ ] CDC가 필요한지, rate matching FIFO가 필요한지 구분
- [ ] 쓰기는 유효 beat에서만, 읽기 유효는 `rd_en && ~empty`를 1클럭 지연
- [ ] CMAC RX는 역압이 없으므로 RX FIFO는 최악의 버스트 기준으로 설계

**외부 장비 시험**
- [ ] 100% 부하에서 극소량 손실이 나면 클럭 ppm 차이와 TX IPG 여유부터 의심
- [ ] 시험 조건(IPG, 부하율, 시간)을 기록

**기록**
- [ ] 문제가 풀린 시점에 증상 / 원인 / 수정 / 근거를 한 줄씩 남기기
- [ ] 외부 답변은 데이터시트 문장으로 확인한 뒤 반영
