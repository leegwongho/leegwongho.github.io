# Introduction

TPG 루프백이 성공한 뒤에는 CMAC과 사용자 로직 사이에 **FIFO를 두는 작업**이 이어졌습니다. 이번 글은 그 과정을 두 시점으로 나누어 정리합니다.

- **당시**: 기록에 남은 설계 결정과 겪은 문제
- **지금 보면**: 다른 프로젝트를 거치고 난 뒤 다시 본 해석

> 2025년 2월 작업을 기록을 바탕으로 정리한 회고입니다. "지금 보면"으로 표시한 부분은 **당시 확인된 결론이 아니라** 이번에 다시 읽고 내린 분석입니다.

# 당시: 클럭을 분리해 보기

CMAC은 `txusrclk2`(약 322.266MHz)로 동작합니다. 첫 루프백에서는 TPG도 CMAC에서 나오는 `txusrclk2`로 동작시킨 것으로 기억합니다(확실하지는 않습니다).

이후에는 **실제 시스템처럼 CMAC 클럭과 사용자 로직의 클럭을 분리**해 보기로 하고, TPG를 다른 클럭에서 돌린 뒤 FIFO를 거쳐 CMAC에 입력하는 구조를 만들었습니다.

## 설계 결정

| 결정 | 이유 |
|------|------|
| TPG를 다른 클럭에서 돌리고 FIFO로 CMAC에 입력, RX도 FIFO로 받아 ILA 확인 | 실제 시스템처럼 CMAC 클럭과 사용자 로직을 분리 |
| 클럭이 다른 단일 비트는 2단 FF만으로는 안 된다고 확인 | 빠른 쪽의 짧은 펄스를 느린 쪽이 놓칠 수 있음 |
| data용 FIFO와 제어용 FIFO를 따로 두지 않고 **578비트 FIFO 하나**로 묶음 (`{tvalid, tlast, tkeep, tdata}` = 1+1+64+512) | 두 FIFO의 읽기 시점이 어긋나면 data와 `tlast`/`tkeep`의 정렬이 깨짐 |
| `tx_axis_tvalid`는 FIFO에서 **실제로 데이터가 나올 때만** 1 | `empty`만 보고 올리면 항상 1이 됨 (AI가 제시한 코드의 이 문제를 직접 짚음) |
| AXI4-Lite 마스터를 직접 만들어 통계 레지스터를 읽고 `pm_tick`으로 갱신 | CMAC의 AXI4-Lite는 슬레이브라 읽으려면 마스터가 필요 |
| FIFO 깊이를 늘리는 대신 다른 방법을 모색 | 깊이를 늘리면 BRAM 배치 거리 때문에 타이밍 슬랙이 나빠짐 |

# 당시: FIFO 앞뒤 프레임 수가 맞지 않았다

가장 오래 걸린 것은 FIFO 앞뒤에서 센 `tlast` 개수가 일치하지 않는 문제였습니다(2/19~2/21).

1. 같은 클럭일 때는 앞뒤 `tlast` 개수가 같았습니다.
2. 읽기 클럭을 더 빠르게 하자 **뒤쪽 카운터가 더 많아졌습니다.** Standard 모드 FIFO는 읽지 않는 동안 마지막 출력을 유지하는데, 그 출력의 `tlast`를 매 클럭 세면서 같은 프레임을 여러 번 센 것으로 보았습니다.
3. 에지 검출로 바꾸자 이번에는 **뒤쪽이 줄었습니다.** 연속된 두 프레임의 `tlast`가 붙어 나오면 에지가 하나로 합쳐지기 때문으로 보았습니다.
4. `rd_en`/`wr_en` 때문에 1클럭 데이터가 사라지는 것 같다고 판단하고, `full`을 보고 일정 시간 기다리는 `rd_en`, 같은 시간을 기다리는 `wr_en`, `rd_en`을 1·0·1로 두는 방식까지 시도했습니다.

이 시기의 접근은 앞뒤에 카운터를 두고 **숫자로 손실을 재는 것**이었습니다. 좋은 방법이었지만, 카운터 자체가 틀릴 수 있다는 가능성은 늦게 의심했고, 증상에 맞춰 보정(에지 검출, 대기 시간)을 더하는 쪽으로 흘렀습니다. 006의 1비트 wire 때와 같은 패턴입니다.

---

# 지금 보면 ①: 카운트 불일치의 원인

당시 코드(`rx_data_cdc_ff`)를 다시 읽어 보면, 원인은 FIFO보다 **"언제가 유효한 beat인가"를 정의하는 방식**에 있었을 가능성이 큽니다.

- **쓰기 쪽**: `wr_en = ~full && buf_rd_en`으로 되어 있어, `rx_axis_tvalid = 0`인 빈 사이클도 함께 적재될 수 있었습니다. 쓰기는 `rx_axis_tvalid`일 때만 하는 것이 기본입니다.
- **읽기 쪽**: Standard 모드는 `rd_en` 다음 클럭에 데이터가 나옵니다. 따라서 유효 신호는 `rd_en && ~empty`를 **한 클럭 늦춘 값**이고, 카운터와 다음 단은 출력 레벨이 아니라 이 신호에 맞춰 `tlast`를 세야 합니다.

이렇게 정의하면 클럭 비율과 상관없이 앞뒤 개수가 맞아야 하고, 에지 검출이나 1·0·1 읽기 패턴 같은 보정은 필요 없습니다. 다만 이것은 코드를 다시 읽고 내린 분석이며 **다시 시험해 확인한 것은 아닙니다.**

---

# 지금 보면 ②: CDC는 필요했을까

돌아보니 이 구성에서 **CDC는 크게 필요하지 않았습니다.**

- 이 CMAC 구성에서는 TX와 RX가 사실상 **같은 클럭 하나**로 동작합니다. 최상위에서 `rx_clk`에 TX 클럭(`txusrclk2`)을 그대로 넣었고, 사용자 쪽 `tx_axis_*`와 `rx_axis_*`도 같은 `txusrclk2` 도메인입니다.
- 수신 데이터는 원래 상대 장비의 복원 클럭으로 들어오지만, 그 차이는 GT의 RX 버퍼가 흡수해서 CMAC에는 TX 클럭 기준으로 넘겨줍니다. (RX 버퍼를 끄는 설정에서는 달라질 수 있고, 이 경우는 확인하지 않았습니다.)
- 그렇다면 사용자 로직도 `txusrclk2`에 두면 클럭 분리용 CDC FIFO는 필요 없었습니다.

반대로 **FIFO 자체는 필요했습니다.** CMAC RX에는 `tready`(역압)가 없어서, RX에서 받은 데이터를 TX로 넘길 때 TX 쪽 `tready`가 내려가는 구간을 받아 줄 버퍼가 있어야 하기 때문입니다.

| | 필요했나 | 이유 |
|---|---|---|
| CDC (클럭 분리) | 크게 필요 없었음 | TX/RX가 같은 `txusrclk2`로 동작 |
| FIFO (rate matching) | 필요 | RX에는 역압이 없음 |

이 차이를 구분하지 못한 채 "FIFO = CDC"로 묶어 생각한 것이 설계를 복잡하게 만든 이유 중 하나였을 수 있습니다. 클럭 분리라는 목적이 먼저 있었기 때문에, 정말 필요한 것이 무엇인지 따져 보기 전에 CDC 구조부터 만들었습니다.

## AI 답변 검증 사례

2/19에 ChatGPT가 "TX_CLK와 RX_CLK는 별도의 클럭 도메인"이라고 답했습니다. 직후에 붙여 넣은 PG203 설명에는 RX_CLK가 TX_CLK와 같아야 한다고 되어 있어 **이 구성에서는 맞지 않는 답**이었습니다. 10G/25G 같은 다른 IP 사례가 섞였던 것으로 보입니다. 외부 답변은 데이터시트 문장으로 확인한 뒤 반영해야 한다는 것을 다시 확인한 사례입니다.

# Checklist

- [ ] 클럭을 분리하기 전에 **분리해야 하는 이유**를 먼저 확인한다 (이 IP의 TX/RX 클럭 관계는 데이터시트로 확인)
- [ ] FIFO의 필요성(rate matching)과 CDC의 필요성(클럭 분리)을 구분한다
- [ ] 쓰기는 유효 beat에서만 한다 (`wr_en = tvalid && ~full`)
- [ ] Standard 모드 읽기의 유효 신호는 `rd_en && ~empty`를 1클럭 지연한 값이다
- [ ] 프레임 카운터는 출력 레벨이 아니라 **유효 beat 기준**으로 센다
- [ ] CMAC RX는 역압이 없으므로 RX FIFO는 최악의 버스트 기준으로 설계한다

# What I Learned

- 목적(클럭 분리)이 앞서면 필요한 구조(rate matching FIFO)와 불필요한 구조(CDC)를 구분하지 못할 수 있다.
- 카운터로 손실을 재려면 **카운터가 센다는 "이벤트의 정의"** 부터 맞아야 한다.
- 증상에 맞춰 보정을 더하기 전에 "무엇이 유효한 beat인가"를 먼저 정의한다.
- 외부 답변은 데이터시트와 대조한다.
