# Introduction

FIFO 경로까지 만든 뒤에는 외부 **트래픽 계측기**를 연결해 실제 트래픽으로 시험했습니다. 이 프로젝트에서 끝내 풀지 못한 문제가 여기서 나왔습니다.

이번 글은 두 시점으로 나누어 정리합니다.

- **당시**: 기록에 남은 시험 구성과 고민, 그리고 미해결로 끝난 결과
- **지금 보면**: 이후 다른 프로젝트 경험을 거친 뒤 다시 세운 가설

> 2025년 2월 작업을 기록을 바탕으로 정리한 회고입니다. "지금 보면"은 **당시 확인된 결론이 아니라** 시간이 지난 뒤의 해석이며, 같은 시험을 다시 할 수 없어 원인을 확정하지는 못했습니다.

---

# 당시: 시험 구성과 결과

계측기에서 보낸 트래픽을 CMAC RX로 받아 FIFO를 거쳐 CMAC TX로 되돌려 보내는 구성이었습니다.

```
Traffic Generator → CMAC RX → FIFO → FIFO → CMAC TX → Traffic Generator
```

| 시험 | 결과 |
|------|------|
| 패스스루 (RX를 그대로 TX로) | 100% 수신, 프레임 에러 존재 |
| FIFO 경유 (RX → FIFO → FIFO → TX) | 100% 수신, 프레임 에러 존재 |
| 2/27 기록 | FPGA에서는 100% 재전송하는데 계측기에서는 **약 0.0001%** 미수신 |

당시 TX IPG는 **기본값**으로 두었습니다.

---

# 당시: 부딪힌 문제와 판단

| 문제 | 당시 고민 | 정리 |
|------|-----------|------|
| FIFO `full`로 프레임 손실 | 깊이를 늘리면 BRAM 때문에 타이밍 슬랙이 나빠짐. `full`일 때 CMAC을 멈추면 되나? | CMAC RX에는 `tready`가 없어 멈출 수 없다. 멈추는 쪽은 상대(계측기)이고, pause 프레임을 보내도 계측기가 따라 줘야만 손실이 없다 |
| `stat_tx_pause`가 보이지 않음 | 어떻게 해야 나오나 | IP 생성 시 **Flow Control**을 켜야 pause 관련 포트가 생긴다. 생긴 것은 `ctl_tx_pause_*` 였다 |
| 64B 프레임 송출 | 계측기에서 TCP가 붙어 64B를 못 보냄 | 계측기를 L2(Raw Ethernet) 모드로 두면 해결 |
| 0.0001% 미수신 | 계측기 버퍼, 광 링크, pause, IPG 등을 후보로 검토 | **기록상 미해결** |

pause 논의에서는 "계측기가 10만 개를 그대로 다 보내 버리면 어떻게 되나?"를 세 번 되물었습니다. CMAC이 멈추라고 해도 상대가 따르지 않으면 소용없다는, 흐름 제어의 한계를 끝까지 확인한 과정이었습니다.

# 지금 보면: 클럭 오차(ppm)가 원인이었을 가능성

이후 다른 프로젝트를 하면서 이 문제가 다르게 보였습니다. **원인은 FIFO 깊이나 pause가 아니라, 두 장비의 클럭 오차와 TX IPG의 여유 부족이었을 가능성이 큽니다.**

## 왜 그런가

1. CMAC의 TX와 RX는 FPGA 기준 클럭 하나(`txusrclk2`)로 동작하지만, **들어오는 데이터의 속도는 계측기의 클럭이 정합니다.** Ethernet은 ±100ppm의 클럭 오차를 허용하므로, 두 장비의 실제 라인 속도는 거의 항상 조금씩 다릅니다.
2. RX 쪽은 이 차이를 PCS와 GT RX 버퍼가 idle을 빼거나 넣어서 맞추므로, RX에서는 프레임이 빠지지 않고 들어옵니다.
3. TX 쪽은 FPGA 클럭 기준으로 **최소 IPG를 지키며** 내보내야 합니다. 당시에는 IPG를 기본값(12)으로 두었습니다.
4. 계측기가 **100% 부하(최소 IPG)** 로 보내고 계측기 클럭이 FPGA보다 조금이라도 빠르면, 들어오는 속도가 나가는 속도보다 ppm만큼 빠릅니다. 그러면 TX의 `tready`가 내려가는 구간이 생기고, TX 앞 FIFO가 조금씩 차오르다가 `full`이 되어 넘친 만큼 버려집니다.
5. 0.0001%는 **1ppm** 수준입니다. 장시간 시험에서는 FIFO 깊이와 상관없이 결국 이 속도 차이만큼 넘치게 되고, 짧은 시험에서는 FIFO가 그만큼 늦게 드러나게 할 뿐입니다.

이 설명대로라면 당시 "FIFO 깊이를 늘리면 슬랙이 나빠지는데 어떻게 하나"는 고민은, **깊이로는 해결되지 않는 문제**를 깊이로 풀려던 것이었습니다.

## 근거와 한계

근거로 볼 수 있는 것은 다음과 같습니다.

- "FPGA 내부는 100%, 외부 계측기 왕복에서만 극소량 손실, 큐가 `full`"이라는 증상 조합이 위 설명과 잘 맞습니다.
- 이후 **다른 프로젝트에서 TX IPG를 11로 설정하고 계측기 부하율 100%로 장기간 시험했을 때 큰 문제가 없었습니다.** 작년 연말에는 일주일 내내 돌려 보기도 했습니다. IPG를 줄이면 TX에 여유가 생겨 ppm 차이를 흡수하기 때문입니다.

하지만 확정 증거는 아닙니다.

- 다른 프로젝트는 **설계와 조건이 다릅니다.** IPG 하나만 바꾼 비교가 아닙니다.
- IPG 11은 표준 최소값(12)보다 짧습니다. 지금 쓰는 계측기가 받아 주는 것이지, 모든 장비에서 통한다는 뜻은 아닙니다.
- 당시 "FPGA 내부 100%"라는 값 자체가 믿을 만한지도 한계로 남습니다. 007에서 본 것처럼 그 시기의 프레임 카운터가 불안정했습니다.

그래서 이 글의 결론은 "원인이 이것이었다"가 아니라 **"가능성이 높다고 본다"** 입니다.

# 다시 한다면: 확인 방법

같은 환경이 있다면 다음 순서로 확인하겠습니다.

1. **부하율 낮추기**: 계측기 부하를 99.9% 정도로 낮추거나 IPG를 늘렸을 때 손실이 사라지면 이 원인이 맞습니다.
2. **FIFO 레벨 관찰**: ILA로 TX 앞 FIFO의 `data_count`를 길게 보면서 일정한 기울기로 계속 차오르는지 확인합니다. 클럭 차이가 원인이라면 선형으로 증가합니다.
3. **주파수 오프셋**: 계측기에 ppm 오프셋 표시나 조정 기능이 있으면, 오프셋을 바꿨을 때 손실이 사라지는지 봅니다.

## 해결 방향

- **TX IPG 줄이기**: PG203의 TX IPG 설정(`CTL_TX_IPG_VALUE`)으로 TX 쪽에 여유를 줍니다. 다만 표준 최소값보다 짧아지므로 상대 장비가 받아 주는지 확인해야 합니다.
- **클럭 동기화**: 계측기와 FPGA가 같은 기준 클럭을 쓰도록 합니다.
- **부하율 조정**: 실무 시험에서는 100%가 아니라 99.x%로 돌리는 경우가 많습니다. 스위치도 클럭 차이가 있는 상태에서 100% 부하를 걸면 같은 이유로 손실이 납니다.

# Checklist

- [ ] 100% 부하 시험에서 손실이 나면 **클럭 ppm 차이와 TX IPG 여유**를 먼저 의심한다
- [ ] FIFO 깊이를 늘려도 장시간 시험에서 손실이 같으면 깊이 문제가 아니다
- [ ] 외부 장비와 시험할 때는 상대 장비의 pause 지원 여부와 설정을 확인한다
- [ ] 손실률을 ppm으로 환산해 보면(0.0001% = 1ppm) 원인 후보를 좁힐 수 있다
- [ ] 시험 조건(IPG, 부하율, 시간)을 기록으로 남긴다

# What I Learned

- 극소량 손실은 설계 버그가 아니라 **장비 간 클럭 오차** 때문일 수 있다.
- 풀지 못한 문제도 이후 경험으로 다시 보면 설명이 생길 수 있고, 그럴수록 "당시"와 "지금 해석"을 분리해서 기록해야 한다.
- 가설은 가능한 한 **확인 방법과 함께** 남긴다.
- 흐름 제어(pause)는 상대 장비가 따라야만 의미가 있다.
