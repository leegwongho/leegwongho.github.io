# Introduction

Project 01에서 100G CMAC을, PCIe / QDMA Study와 OpenNIC Study에서 PCIe, QDMA, OpenNIC 구조를 정리했습니다. Project 02는 **OpenNIC 구조를 10G Ethernet 환경에 적용한 프로젝트**에서 배운 것을, 방법과 판단 기준 중심으로 정리합니다.

> **공개 범위**: 회사 보안상 보드명, 칩 이름, 사내 설계의 구체적인 구조와 수치는 쓰지 않습니다. 대신 **공개 표준(IEEE 802.3 등)과 공개 저장소(OpenNIC)로 설명할 수 있는 범위**의 숫자와 예시를 사용합니다. 글에 나오는 수치는 표준에서 계산한 값이거나 설명을 위한 예시입니다.

# 1. 데이터 폭이 바뀌면 무엇이 달라지나

OpenNIC은 100G CMAC 기준으로 만들어져 있어서, Shell 내부의 QDMA 쪽 데이터 경로는 **512비트 @ 250MHz**입니다. 10G MAC은 일반적으로 **64비트 @ 156.25MHz** 인터페이스를 씁니다.

| | OpenNIC (100G 기준) | 10G MAC (일반적인 구성) |
|---|---|---|
| 선로 속도 | 25.78125 Gb/s × 4 | 10.3125 Gb/s × 1 (10GBASE-R) |
| 사용자 인터페이스 | 512 bit | 64 bit |
| 클럭 | 322.266 MHz (CMAC) / 250 MHz (QDMA) | 156.25 MHz |
| 처리 가능량 | 512 × 250M = 128 Gb/s | 64 × 156.25M = **정확히 10 Gb/s** |
| `tkeep` 폭 | 64 bit | 8 bit |

512비트 한 beat에 들어 있던 64 B가, 64비트에서는 **8 beat**로 나뉩니다. 그래서 "폭만 바꾸면 된다"가 아니라 다음 세 가지를 **나누어서** 봐야 했습니다.

1. **인터페이스 변경**: 폭과 클럭에 맞춰 AXI4-Stream 연결을 수정한다.
2. **프로토콜 처리 변경**: 여러 beat에 걸친 패킷의 필드와 마지막 beat를 정확히 처리한다.
3. **타이밍 변경**: 바뀐 로직이 목표 클럭에서 동작하도록 경로를 정리한다.

특히 두 번째가 놓치기 쉽습니다. 512비트에서는 한 beat에 들어 있던 헤더 필드가, 64비트에서는 **여러 beat에 나뉘어** 들어옵니다. 패킷 파서는 beat 번호를 세면서 필드의 위치를 추적해야 합니다. 이 내용은 004에서 프레임 구조와 함께 자세히 다룹니다.

## 인터페이스 의미도 함께 바뀐다

폭과 클럭만이 아니라 **신호의 의미와 규칙**도 확인해야 했습니다.

- OpenNIC의 250MHz 박스는 `tuser_size`(패킷 길이)가 `tvalid` 동안 유효해야 합니다. 즉 **첫 beat에서 이미 전체 길이를 알아야** 합니다. MAC을 바꾸면 이 값을 누가, 언제 계산하는지가 확인 항목이 됩니다.
- MAC TX는 한 패킷이 시작되면 **`tlast`까지 `tvalid`를 끊으면 안 됩니다**(Project 01 007). 10G MAC도 마찬가지이며, AMD의 10G/25G MAC 문서는 TX underflow가 나면 현재 패킷이 깨지고 **복구하려면 TX 리셋이 필요하다**고 설명합니다.
- MAC RX에는 역압(`tready`)이 없습니다. RX 쪽의 막힘은 정지가 아니라 **손실**로 나타납니다.

이때 확인할 항목입니다.

- 데이터가 올바른 순서로 전달되는가 (`tdata[7:0]`이 첫 바이트)
- 마지막 beat에서 `tlast`가 유지되는가
- 마지막 beat의 유효 바이트(`tkeep`)가 정확한가
- `tvalid`/`tready` 핸드셰이크가 정상인가
- 패킷 길이 정보(`tuser_size` 등)가 실제 바이트 수와 같은가
- 서로 다른 클럭 도메인에서 데이터가 유실되거나 중복되지 않는가

# 2. 파서와 해시는 단계별로 비교한다

패킷 헤더에서 필드를 뽑아 해시(RSS)를 계산하는 로직은, 결과가 틀렸을 때 **어디가 틀렸는지** 알기 어렵습니다. 최종 큐 번호만 보지 말고 **중간 값을 단계별로** 소프트웨어 결과와 비교하는 것이 가장 확실했습니다.

```
① Ethernet 헤더 추출
② VLAN/MPLS 유무에 따른 L3 시작 위치
③ IPv4/IPv6 헤더 추출
④ 주소와 포트로 해시 입력(tuple) 구성
⑤ 해시 계산
⑥ 해시에서 큐 번호로 변환 (Indirection Table)
```

- **헤더 위치를 계산하는 로직**과 **해시 입력을 구성하는 로직**은 분리해서 이해해야 합니다. VLAN이 없는 패킷은 정상인데 VLAN이 있는 패킷만 틀린다면 ②를 먼저 의심합니다.
- 알고리즘이 같아도 **입력의 바이트 순서와 필드 순서**가 다르면 결과가 달라집니다. (PCIe / QDMA Study 006에서 본 대로입니다.)
- 단계마다 소프트웨어(Python, C)와 하드웨어(RTL 시뮬레이션) 값을 같은 입력으로 비교하면 파서 오류와 해시 오류를 구분할 수 있습니다.
- 비교 기준(골든 모델)은 **하드웨어와 같은 규칙으로 만든 소프트웨어 모델**이어야 합니다. 이 설계는 해시 입력에 Protocol까지 넣고 비트 순서도 기준 해시 모듈을 따르기 때문에, Microsoft의 RSS 검증 예제 값과는 그대로 맞지 않습니다. 공개 검증 값은 알고리즘을 이해했는지 확인하는 데 쓰고, RTL은 기준 모델과 비교합니다(PCIe / QDMA Study 006).

## 시험 입력은 "형태별로" 준비한다

파서 버그는 대부분 **특정 형태의 패킷에서만** 납니다. 004에서 다루는 프레임 형태를 시험 입력 목록으로 그대로 씁니다.

| 입력 | 확인하는 것 |
|------|-------------|
| VLAN 없음 / VLAN 1개 / QinQ | L3 시작 위치가 4 B씩 밀리는 처리 |
| MPLS 라벨 1개 / 여러 개 | 라벨 스택 끝(S 비트) 찾기 |
| IPv4 옵션 있음 (IHL > 5) | L4 시작 위치가 밀리는 처리 |
| IPv6 | 16 B 주소, 다른 오프셋 |
| IP 단편(fragment) | 첫 단편에만 포트가 있다 |
| TCP / UDP / 기타 프로토콜 | 포트를 쓸지 말지 |
| ARP 등 비IP | 기본 큐로 보내는지 |

# 3. 기능이 맞아도 타이밍이 안 맞을 때

기능 검증은 통과했는데 **목표 클럭에서 타이밍을 만족하지 못하는** 경우가 있었습니다. 리포트를 읽는 방법은 003에서 자세히 다루고, 여기서는 배운 점만 정리합니다.

- **메모리 종류를 바꿔도 해결되지 않을 수 있다.** 병목이 메모리 접근이 아니라 메모리에서 읽은 값을 **비교하고 선택하는 조합 로직**에 있다면, 메모리 구현만 바꿔서는 경로가 그대로 남습니다. 문제가 발생했다고 짐작하는 블록과 **실제 Critical Path에 있는 로직이 같은지** 먼저 확인해야 합니다.
- **파이프라인을 추가하면** 지연 시간과 제어 신호의 정렬이 달라집니다. Slack이 좋아졌다고 수정이 끝난 것이 아니라, 기능이 그대로인지 다시 확인해야 합니다.
- **디바이스를 바꾸면** 논리는 같아도 배치와 배선 혼잡이 달라져서 타이밍과 **구현 시간**이 크게 달라질 수 있습니다. 두 디바이스의 Worst Path와 혼잡 결과를 비교해야 무엇이 달라졌는지 알 수 있습니다.

# 4. 여러 큐 사이의 부하 분산과 버퍼

큐가 여러 개이면 **어떤 큐로 보낼지**와 **버퍼가 넘치지 않게 할지**가 함께 문제가 됩니다. 구조는 005에서 자세히 다루고, 여기서는 배운 점만 정리합니다.

- **큐 번호는 해시와 Indirection Table로 정한다.** 5-tuple(주소, 포트, IP Protocol) 해시의 하위 7비트로 128칸 테이블을 찾고, 테이블 값이 큐 번호가 됩니다. 같은 흐름은 항상 같은 큐로 갑니다.
- **흐름 단위 분산의 한계를 안다.** 흐름이 적으면(극단적으로 1개) 큐가 여러 개여도 한 큐로만 갑니다. 단일 흐름과 다중 흐름 시험을 나누어야 합니다.
- **가득 찬 큐를 피해 다른 큐로 보내면 순서가 바뀔 수 있다.** 같은 흐름이 서로 다른 큐로 갈라지면 호스트에서 패킷 순서가 뒤바뀝니다. RSS의 목적이 흐름별로 같은 큐를 유지하는 것이라는 점을 기억해야 합니다.
- **혼잡은 버퍼에 남은 공간으로 판단한다.** 버퍼가 차는 원인은 대부분 호스트가 패킷을 제때 가져가지 못하는 것이었고, 그 결과는 결국 버퍼 점유로 나타납니다. 그래서 패킷 수나 입력 속도보다 **버퍼에 실제로 남은 공간**을 보는 것이 가장 정확했습니다. 새 패킷을 받을지는 남은 공간이 **최대 패킷 크기 + α** 이상인지로 정했습니다.
- **조건을 나누어 시험한다.** 단일 흐름과 다중 흐름, 작은 패킷과 큰 패킷, Burst 크기, 큐 수에 따라 동작이 달라집니다. 특히 **패킷 길이가 바뀌는 구간**이 있는 시험이 필요합니다(006). 전체 처리량만 보면 원인을 놓칩니다.
- **Burst가 크다고 항상 좋은 것은 아니다.** 순간적으로 버퍼에 들어오는 양이 늘어서, 소비 속도가 못 따라가면 오히려 넘침이 늘 수 있습니다.
- **Descriptor 수와 실제 데이터 버퍼 용량은 다르다.** Descriptor가 많다고 같은 수의 패킷을 동시에 버퍼링할 수 있다는 뜻이 아닙니다. 두 자원을 분리해서 계산해야 합니다.
- **전체 카운터만 보지 않는다.** 어느 큐로 몰리는지, 큐별 버퍼가 얼마나 찼는지를 함께 봅니다.

# 5. DMA 시험과 다른 FPGA로의 포팅

DMA와 포팅에서 실제로 만난 문제는 006에서 자세히 다룹니다. 여기서는 접근 방법만 정리합니다.

## 장치가 보이는 것과 데이터가 오가는 것

PCIe / QDMA Study 005, 007에서도 다룬 내용이지만 이 작업에서 다시 확인했습니다. **PCIe 장치가 인식되고 드라이버가 붙어도 데이터 전송이 정상이라는 보장은 없습니다.** 다른 FPGA로 포팅했을 때 인식은 정상인데 전송이 일찍 멈추거나 시스템이 멈추는 증상이 나타날 수 있고, 이때는 아래 단계를 나누어 봅니다.

- BAR 접근과 레지스터 읽기/쓰기 (**모든 주소에 응답하는가**)
- DMA 엔진의 초기화, 큐 컨텍스트와 함수-큐 매핑
- Descriptor 처리와 완료, 완료 링이 가득 차지 않는가
- 사용자 로직의 리셋과 클럭
- MAC과 DMA 사이의 AXI4-Stream 전달 (**선언한 길이와 실제 길이가 같은가**. 고정 길이 시험만으로는 확인되지 않는다)

## 관측 지점을 연결한다

패킷이 어디까지 갔는지 알려면 **여러 지점의 카운터를 한 줄로 이어서** 봅니다(002에서 자세히).

| 관찰 결과 | 확인해야 할 영역 |
|-----------|------------------|
| MAC 수신은 증가, 파서 출력은 정지 | 파서 상태, 패킷 형식, 입력 핸드셰이크 |
| 파서 출력은 증가, 큐 입력은 정지 | 선택 로직, 크레딧, 큐 선택 |
| 큐 입력은 증가, DMA 전달은 정지 | 버퍼 상태, AXI4-Stream 핸드셰이크 |
| FPGA 전달은 증가, 호스트 수신은 정지 | Descriptor, 완료 처리, 드라이버 |
| 특정 큐만 증가 | 해시, 큐 매핑, 분산 상태 |

**카운터가 멈췄다는 것은 현상이지 원인이 아닙니다.** 어느 신호의 핸드셰이크가 마지막으로 일어났는지를 확인해야 원인의 범위가 좁혀집니다.

## 디바이스를 바꿀 때 비교할 것

GT 기반 인터페이스가 있는 설계를 다른 디바이스로 옮길 때는 다음을 같이 비교합니다.

- GT 참조 클럭과 PLL 선택 (10GBASE-R은 보통 156.25 MHz 참조 클럭)
- GT 리셋 순서
- 사용자 클럭과 MAC 초기화 상태
- 링크 정렬(블록 락) 상태
- 광모듈 제어 핀 (Project 01 004)
- Shell의 클럭과 리셋 연결

한 디바이스에서 동작하던 설정을 그대로 옮겨도, 자원 배치와 클럭 연결이 다르면 결과가 달라집니다.

## ILA와 도구의 문제는 따로 본다

디버그 코어가 예상보다 적게 보이거나 아예 보이지 않으면 설계가 틀렸다고 단정하기 전에 다음을 구분합니다.

- **비트스트림에 실제로 들어간 코어**와 **디버그 프로브 파일(.ltx)** 이 일치하는가
- **하드웨어 매니저 연결 상태**가 정상인가
- **ILA 클럭이 실제로 돌고 있는가.** ILA 클럭이 GT 사용자 클럭처럼 링크가 올라와야 생기는 클럭이면, 링크가 안 올라온 상태에서는 코어가 아예 보이지 않습니다. 포팅 초기에 특히 자주 만납니다.

# 6. 해결한 것과 확인 중인 것을 구분한다

프로젝트에서 여러 증상이 있었지만, 모든 문제가 **원인까지 확정**된 것은 아닙니다.

| 상태 | 쓰는 표현 |
|------|-----------|
| 원인을 확인하고 수정까지 검증 | "원인은 ~였고 ~로 수정해 확인했다" |
| 원인 후보만 좁힘 | "~일 가능성이 높다고 봤다" |
| 증상은 재현되지만 원인 미확정 | "~ 증상이 있었고 원인은 확정하지 못했다" |

이 구분은 기록에도 그대로 남겨야 합니다. 시간이 지나면 후보가 확정된 것처럼 기억되기 때문입니다. Project 01의 회고(009)에서도 같은 이유로 "남아 있는 것"을 따로 적었습니다.

# 7. 변경 범위를 제한하는 습관

레지스터 맵과 제어 로직을 수정할 때, **기존 주소와 읽기 동작을 유지하면서 필요한 부분만** 바꾸는 방식을 유지했습니다. 드라이버와 소프트웨어가 기존 주소와 의미를 그대로 쓰고 있기 때문에, 내부가 정상이어도 인터페이스가 바뀌면 소프트웨어가 다르게 해석할 수 있습니다.

- 변경 전후의 레지스터 맵과 읽기 결과가 같은지 검증한다.
- 레지스터 값의 의미(단위, 허용 범위)는 문서에 명시한다.
- **정의되지 않은 주소도 반드시 응답한다.** 응답하지 않으면 호스트 전체가 멈출 수 있다(006).

# What I Learned

- 데이터 폭이 바뀌면 **인터페이스, 프로토콜 처리, 타이밍**을 따로 확인해야 한다. 512비트 한 beat는 64비트 8 beat가 된다.
- 폭과 클럭만이 아니라 **신호의 의미와 규칙**(길이 정보, TX `tvalid` 연속성, RX 역압 부재)도 바뀐다.
- 파서와 해시는 **단계별 중간 값**을 소프트웨어와 비교하고, 시험 입력은 **프레임 형태별로** 준비한다.
- 타이밍 문제는 짐작한 블록이 아니라 **Worst Path의 실제 로직**을 봐야 한다.
- 분산은 **흐름 단위**라는 한계가 있고, 혼잡은 **버퍼에 남은 공간**으로 판단한다. 대부분의 혼잡은 느린 호스트에서 온다.
- 장치 인식과 데이터 전송은 다른 단계이고, **관측 지점을 한 줄로 이어서** 어디까지 갔는지 본다.
- 확정한 것과 후보인 것을 **구분해서 기록**한다.
