# Introduction

004에서 패킷마다 5-tuple을 꺼냈습니다. 이번 글은 그 5-tuple로 **어느 큐에 보낼지 정하는 방법(RSS)** 과, 큐로 보내기 전 **버퍼 크기와 백프레셔를 어떻게 정했는지**를 정리합니다.

> 공개 범위는 001과 같습니다. 구조는 OpenNIC과 일반적인 NIC의 RSS 방식으로 설명하고, 사내 설계의 구체적인 수치는 쓰지 않습니다.

---

# 1. 큐 번호가 정해지는 과정

전체 흐름은 OpenNIC과 같은 방식을 따랐습니다.

```
 5-tuple ──▶ 해시 계산 ──▶ 해시 하위 비트 ──▶ Indirection Table ──▶ 큐 번호
 (004)       (32 bit)       (테이블 인덱스)     (128칸)
```

1. 004에서 추출한 5-tuple로 **해시**를 계산합니다. 입력에는 출발지/목적지 IP, 출발지/목적지 포트, 그리고 **IP Protocol(IPv6는 Next Header)** 이 모두 들어갑니다. 해시는 Toeplitz 방식처럼 **입력의 1인 비트마다 키의 일부 구간을 XOR**하는 구조이고, 비트를 이어 붙이는 순서는 기준이 되는 해시 모듈을 따랐습니다. 입력 쪽(5-tuple 추출)은 64비트에 맞게 새로 만들었습니다.
2. 해시 값의 **하위 비트**를 꺼내 테이블의 인덱스로 씁니다. 테이블이 128칸이므로 인덱스는 7비트입니다.
3. **Indirection Table**에서 그 칸에 적힌 값을 읽으면, 그것이 이 패킷의 **큐 번호**입니다.

이 구조는 일반적인 NIC의 RSS 구현과 같습니다. 리눅스 커널 문서도 가장 흔한 하드웨어 RSS 구현으로 128칸 Indirection Table을 들고, 해시의 하위 7비트로 칸을 찾아 큐 번호를 읽는다고 설명합니다.

## 표준 RSS와 다른 점

| | Microsoft RSS 규격 | 이 설계 |
|---|---|---|
| 해시 입력 | 주소, 포트 (Protocol은 입력 조합을 고르는 기준) | 주소, 포트, **Protocol까지** |
| 비트 순서 | 네트워크 순서, 최상위 비트부터 | 기준 해시 모듈의 순서 |
| 검증 기준 | 공개된 검증 키와 기대 해시값 | **같은 규칙으로 만든 소프트웨어 모델** |

Protocol까지 넣으면 주소와 포트가 같아도 TCP와 UDP 흐름이 서로 다른 해시를 갖게 됩니다. 대신 공개 검증 값과는 결과가 다르므로, 비교 기준을 처음부터 기준 모듈의 소프트웨어 모델로 정해 두어야 합니다(PCIe / QDMA Study 006).

## 같은 흐름은 항상 같은 큐로

같은 5-tuple은 항상 같은 해시 → 같은 칸 → **같은 큐**가 됩니다. 004에서 본 것처럼 TCP는 순서가 바뀌면 성능이 떨어지므로, 흐름 단위로 큐를 고정하는 것이 RSS의 핵심입니다.

# 2. Indirection Table

## 구조

| 항목 | 값 |
|------|-----|
| 칸 수 | 128 |
| 칸 하나의 폭 | 16 bit (큐 번호) |
| 인덱스 | 해시 하위 7비트 |

## 채우는 방법

칸마다 **사용할 큐 번호를 0부터 차례로 반복**해서 채웁니다.

| 사용 큐 수 | 테이블 내용 (128칸) | 큐 하나가 차지하는 칸 |
|-----------|---------------------|------------------------|
| 4 | 0, 1, 2, 3, 0, 1, 2, 3, … | 32칸 |
| 8 | 0, 1, …, 7, 0, 1, …, 7, … | 16칸 |
| 16 | 0 ~ 15 반복 | 8칸 |

즉 `table[i] = i mod (큐 수)` 입니다. 해시가 고르게 퍼진다면 각 큐가 같은 비율로 패킷을 받습니다.

## 큐 수가 2의 거듭제곱이 아니면

128은 3이나 6으로 나누어떨어지지 않아서 약간의 불균형이 생깁니다.

| 큐 수 | 칸 배분 | 가장 많은 큐와 적은 큐의 차이 |
|-------|---------|-------------------------------|
| 3 | 43, 43, 42 | 1칸 (약 0.8%) |
| 6 | 22, 22, 21, 21, 21, 21 | 1칸 (약 0.8%) |

실제 영향은 작지만, 시험 결과를 해석할 때 "왜 큐 0이 조금 더 많이 받나"의 이유가 될 수 있습니다.

## 왜 해시를 큐 수로 바로 나누지 않나

`해시 mod 큐 수`로 바로 큐를 정할 수도 있지만, 테이블을 두는 이유가 있습니다.

- **하드웨어 비용**: 2의 거듭제곱이 아닌 수로 나누는 연산은 하드웨어에서 비쌉니다. 테이블은 7비트 인덱스로 읽기만 하면 됩니다.
- **소프트웨어가 바꿀 수 있다**: 드라이버가 테이블 내용을 바꾸면 큐 수를 줄이거나, 특정 큐에 **가중치**를 주거나, 특정 큐를 비울 수 있습니다. 리눅스에서는 `ethtool -X`(`--set-rxfh-indir`)가 이 역할입니다.
- **큐 수가 바뀌어도 해시 로직은 그대로**입니다.

> 운영 중에 테이블을 바꾸면, 바뀐 칸에 해당하는 흐름은 **다른 큐로 옮겨 가면서 잠시 순서가 바뀔 수** 있습니다. 시험 중에 테이블을 바꿀 때는 이 점을 감안합니다.

# 3. 흐름 단위 분산의 한계

RSS는 **패킷 단위가 아니라 흐름 단위**로 나눕니다. 그래서 시험 조건에 따라 결과가 크게 달라집니다.

| 시험 조건 | 결과 |
|-----------|------|
| 흐름 1개 | 큐가 여러 개여도 **한 큐로만** 간다 (정상 동작) |
| 흐름 수가 큐 수와 비슷 | 해시 충돌로 일부 큐에 몰릴 수 있다 |
| 흐름이 충분히 많음 | 거의 고르게 나뉜다 |

트래픽 발생기로 시험할 때 **IP나 포트를 바꿔 가며 흐름 수를 충분히** 만들어야 분산이 제대로 보입니다. 흐름이 적은 상태에서 "분산이 안 된다"고 판단하면 정상 동작을 버그로 오해하게 됩니다.

또 **가득 찬 큐를 피해 다른 큐로 보내는 방식**은 같은 흐름이 여러 큐로 갈라져 순서가 바뀔 수 있으므로, 쓰더라도 그 영향을 알고 써야 합니다(001의 4번 절).

# 4. 버퍼: 큐 번호가 나올 때까지 기다리는 곳

004에서 본 것처럼, 64비트 인터페이스에서는 5-tuple이 **패킷의 5~9번째 beat**가 되어야 다 모입니다. 그 뒤에 해시와 테이블 읽기까지 몇 클럭이 더 걸립니다. 반면 다음 단(DMA 쪽)에서는 **패킷의 첫 beat부터 큐 번호가 필요**합니다.

그래서 큐 번호가 나올 때까지 패킷을 담아 둘 **버퍼**가 필요합니다. 패킷 길이도 같은 이유로 버퍼에서 패킷이 끝까지 들어와야 확정됩니다(001의 1번 절, `tuser_size`).

## 크기: 최대 패킷의 1.5배

버퍼 크기는 **사용할 최대 패킷 크기의 1.5배**로 정했습니다.

- 최소 **최대 패킷 하나**는 통째로 담을 수 있어야 합니다. 패킷 전체가 들어와야 큐 번호와 길이가 확정되고 내보낼 수 있기 때문입니다.
- 여기에 0.5배의 여유를 두어, 앞 패킷을 내보내는 동안 **다음 패킷이 들어오기 시작할 자리**를 남겼습니다.
- 출력 쪽 데이터 경로(512비트 @ 250MHz, 128 Gb/s)는 입력(10 Gb/s)보다 훨씬 넓어서, **호스트가 제때 가져가는 동안에는** 버퍼가 금방 비워집니다.

## 혼잡은 어디서 오는가: 느린 호스트

버퍼가 차는 원인은 FPGA 내부가 아니라 대부분 **호스트**였습니다. 데이터 경로는 충분히 넓어도, 호스트가 패킷을 가져가는 속도(드라이버, CPU, 디스크립터 공급)가 따라가지 못하면 DMA 쪽에서 `tready`가 내려가고, 그 결과 버퍼가 차오릅니다.

그래서 "혼잡한가"는 패킷 수나 입력 속도가 아니라 **버퍼에 실제로 남은 공간**으로 판단하는 것이 가장 정확했습니다. 원인(느린 호스트)이 어디에 있든, 그 결과는 결국 버퍼 점유로 나타나기 때문입니다.

## 백프레셔: 최대 패킷 + α

버퍼의 남은 공간이 **최대 패킷 크기 + α**보다 작아지면, 상류로 `tready`를 내려 **새 패킷을 받지 않도록** 했습니다.

```
 남은 공간 ≥ 최대 패킷 + α  → 새 패킷 받음
 남은 공간 <  최대 패킷 + α  → 새 패킷의 시작을 막음 (tready = 0)
```

이렇게 정한 이유는 세 가지입니다.

1. **패킷 길이는 끝까지 받아야 안다.** 새 패킷이 시작될 때는 그 패킷이 얼마나 길지 모르므로, **가장 긴 경우(최대 패킷)** 가 들어갈 자리가 있을 때만 받습니다. 그러면 한번 받기 시작한 패킷은 **반드시 끝까지 들어갈 자리가 있습니다.**
2. **α는 멈추는 데 걸리는 시간이다.** `tready`를 내려도 파이프라인 때문에 상류가 실제로 멈출 때까지 몇 클럭 동안 데이터가 더 들어올 수 있습니다. 그 클럭 수 × 8 B(64비트 기준)만큼, 그리고 약간의 여유를 α로 더했습니다.
3. **"가득 찼을 때" 막으면 늦다.** 버퍼가 완전히 찬 뒤에 막으면, 들어오던 패킷이 중간에 잘리거나 반쯤 들어간 채로 멈춥니다. 패킷 경계에서 미리 판단해야 버퍼 안에서 패킷이 잘리는 일이 없습니다.

이 규칙으로 FPGA 내부 경로에서 **버퍼 넘침으로 인한 패킷 손실이 없도록** 했습니다.

## 백프레셔가 닿지 않는 곳

다만 백프레셔는 **`tready`가 있는 구간까지만** 전달됩니다. Project 01에서 본 것처럼 MAC RX에는 `tready`가 없으므로, 호스트가 오래 데이터를 가져가지 않아 역압이 MAC 앞까지 쌓이면 그 지점에서는 멈출 수 없습니다. 호스트가 느린 상태가 길게 이어지면 결국 어딘가에서는 넘칠 수밖에 없고, 그래서 **MAC 바로 뒤 버퍼가 마지막 방어선**이 됩니다. 이 백프레셔 규칙이 막아 주는 것은 "버퍼 안에서 패킷이 잘리는 것"이고, 호스트가 장시간 따라오지 못하는 상황 자체는 호스트 쪽 처리 성능의 문제로 따로 봐야 합니다.

## 백프레셔를 잘못 주면

백프레셔는 단순해 보이지만, 잘못 구현하면 손실보다 더 찾기 어려운 문제를 만듭니다. `tready`를 내린 클럭에 데이터를 함께 넘겨 버리거나, 반대로 같은 데이터를 두 번 받으면 **패킷 길이가 실제와 달라집니다.** 이 프로젝트에서 실제로 이 때문에 DMA 쪽이 멈춘 일이 있었고, 006에서 다룹니다.

# 5. 확인 방법

| 확인할 것 | 방법 |
|-----------|------|
| 해시가 맞는가 | 004의 프레임 목록으로 **기준 해시 모듈과 같은 규칙의 소프트웨어 모델**과 단계별 비교 (추출 필드 → 해시 입력 → 해시 → 인덱스) |
| 테이블이 맞게 채워졌는가 | 레지스터로 128칸을 읽어 `i mod N`인지 확인 |
| 분산이 고른가 | 흐름 수를 충분히 늘린 시험에서 큐별 패킷 카운터 비교 |
| 같은 흐름이 같은 큐로 가는가 | 흐름 1개 시험에서 한 큐만 증가하는지 확인 |
| 버퍼가 넘치지 않는가 | 버퍼 최대 점유량(high-water mark) 레지스터를 두고 최대 패킷 연속 입력 시험 |
| 백프레셔가 패킷 경계에서만 걸리는가 | ILA로 `tready`가 내려가는 시점이 패킷 시작 전인지 확인 |

# What I Learned

- 큐 번호는 **5-tuple → 해시 → 하위 7비트 → 128칸 Indirection Table** 순서로 정해진다. 같은 흐름은 항상 같은 큐로 간다.
- 이 설계의 해시는 **Protocol까지 입력에 넣어** 표준 RSS와 결과가 다르므로, 같은 규칙의 소프트웨어 모델로 검증한다.
- 테이블은 `i mod 큐 수`로 채우고, 큐 수가 2의 거듭제곱이 아니면 약간의 불균형이 생긴다.
- 테이블을 두면 나눗셈 없이 큐를 고를 수 있고, 소프트웨어가 분산을 조정할 수 있다.
- RSS는 흐름 단위라서 **흐름 수가 충분해야** 분산이 보인다.
- 큐 번호와 패킷 길이가 확정될 때까지 패킷을 담아 둘 **버퍼**가 필요하다. 크기는 최대 패킷의 1.5배로 했다.
- 혼잡은 대부분 **느린 호스트**에서 오고, 그 결과가 버퍼 점유로 나타나므로 **버퍼에 남은 공간**으로 판단하는 것이 가장 정확하다.
- 백프레셔는 **남은 공간이 최대 패킷 + α보다 작을 때 새 패킷을 막는** 방식으로, 받기 시작한 패킷은 반드시 끝까지 들어가게 했다.
