# Introduction

Project 02의 마지막 글입니다. DMA로 호스트와 데이터를 주고받는 시험, 그리고 설계를 **다른 FPGA로 포팅**하면서 실제로 만난 문제를 정리합니다.

미리 밝혀 두면, 저는 **드라이버 쪽은 깊이 알지 못합니다.** 그래서 이 글은 드라이버 내부가 아니라, **FPGA 쪽에서 무엇이 잘못되면 호스트에서 어떤 증상이 나오는지**, 그리고 그것을 어떻게 FPGA 쪽 문제로 좁혀 고쳤는지를 중심으로 씁니다.

> 공개 범위는 001과 같습니다. 보드, 칩, 사내 드라이버의 이름과 구조는 쓰지 않습니다.

# 1. 시험 환경: DPDK로 시작해 자체 드라이버로

| 시기 | 호스트 소프트웨어 | 이유 |
|------|-------------------|------|
| 초기 | **OpenNIC DPDK** 드라이버 + `testpmd` | 공개된 패치가 있어 바로 쓸 수 있고, 큐별 통계를 쉽게 볼 수 있음 |
| 이후 | 사내에서 개발한 드라이버 | 드라이버 개발이 끝난 뒤 같은 시험을 반복 |

DPDK로 시작하면 이런 점이 좋습니다.

- **하드웨어를 먼저 검증할 수 있다.** 공개되어 여러 사람이 써 온 드라이버로 시험하면, 문제가 생겼을 때 "드라이버가 아직 덜 됐다"는 변수를 줄이고 FPGA 쪽부터 의심할 수 있습니다.
- **큐별 통계가 바로 보인다.** `testpmd`는 큐마다 받은 패킷 수를 보여 주므로, 005의 RSS 분산을 확인하기 좋습니다.
- **드라이버를 바꿀 때 기준이 생긴다.** 자체 드라이버로 바꾼 뒤 같은 시험을 돌려 결과가 다르면, 그 차이부터 볼 수 있습니다.

드라이버를 잘 모르는 입장에서 쓸 수 있는 기준은 단순합니다. **DMA 경계의 FPGA 카운터(002)를 먼저 본다.** FPGA가 DMA로 넘긴 수가 정상인데 호스트에서 안 보이면 드라이버 쪽을, FPGA 쪽에서 이미 멈췄으면 하드웨어를 봅니다.

# 2. 문제 1: 백프레셔 오류로 패킷 길이가 달라져 DMA가 멈춤

## 증상

트래픽을 보내던 중 **DMA 경로가 멈추고(hang)** 더 이상 패킷이 호스트로 올라오지 않았습니다.

## 배경: DMA는 패킷 길이를 미리 듣는다

QDMA의 스트림 모드(C2H, 카드 → 호스트)에서는 사용자 로직이 데이터와 함께 **패킷 길이**를 제어 신호로 알려 줍니다. OpenNIC에서는 250MHz 박스 인터페이스의 `tuser_size`가 이 역할을 하고, 패킷 첫 beat부터 유효해야 합니다(001의 1번 절, 005의 4번 절).

DMA 엔진은 이 길이를 믿고 호스트 버퍼와 완료 정보를 준비합니다. 그런데 **실제로 들어온 바이트 수가 알려 준 길이와 다르면**, DMA는 오지 않을 데이터를 기다리거나 다음 패킷의 데이터를 이전 패킷의 일부로 해석하게 되고, 결국 경로가 멈춥니다.

## 찾은 과정: 길이를 바꾸는 순간 깨졌다

처음에는 어디서 멈추는지 짐작이 가지 않아, **ILA를 경로 전 구간에 걸고** 패킷이 어디까지 정상으로 가는지 하나씩 확인했습니다.

결정적인 단서는 **패킷 길이를 바꾸는 시험**에서 나왔습니다.

1. **78 B 패킷만** 계속 보낸다 → 정상
2. 이어서 **128 B 패킷만** 보내도록 바꾼다 → 이 시점에 패킷이 깨짐
3. ILA로 확인해 보니, **128 B의 첫 패킷이 78 B 길이로 나가는** 경우가 있었다

길이가 바뀐 첫 패킷에 **앞 패킷의 길이가 그대로 붙어 나간 셈**입니다. 데이터는 128 B인데 DMA에 알려 준 길이는 78 B이니, 앞에서 본 것처럼 DMA가 패킷 경계를 잘못 읽고 멈춥니다.

```
 78 B 연속     :  [78 B 데이터, 길이 78] [78 B 데이터, 길이 78] ...   → 정상
 128 B로 전환  :  [128 B 데이터, 길이 78] ← 앞 패킷의 길이          → 깨짐
```

## 원인

원인은 큐 앞단의 **백프레셔 처리**였습니다. `tready`가 내려가는 구간에서 데이터와 길이 정보가 같은 시점에 함께 진행하지 않아, **데이터와 길이가 서로 다른 패킷의 것**이 되는 경우가 있었습니다. 패킷 데이터는 새 패킷인데, 길이는 직전 패킷의 값이 남아 있었던 것입니다.

```
 정상:  선언 길이 = 실제 바이트 수       → DMA 정상 완료
 오류:  선언 길이 ≠ 실제 바이트 수       → DMA가 기다리거나 경계를 잘못 읽음 → 정지
```

## 왜 고정 길이 시험에서는 보이지 않았나

이 버그의 핵심은 **같은 길이의 패킷만 보내면 드러나지 않는다**는 점입니다. 78 B만 계속 보내면 길이가 한 패킷 밀려도 앞 패킷의 길이 역시 78 B이므로 결과가 같습니다. **연속된 두 패킷의 길이가 다를 때만** 어긋남이 보입니다.

| 시험 | 길이가 한 패킷 밀렸을 때 |
|------|---------------------------|
| 고정 길이 (78 B만, 128 B만) | 앞 패킷과 길이가 같아서 **티가 나지 않음** |
| 길이 전환 (78 B → 128 B) | 전환 직후 첫 패킷에서 **불일치 발생** |
| 길이가 섞인 트래픽 (IMIX 등) | 거의 매 패킷 불일치 → 금방 정지 |

그래서 시험 패턴에 **길이가 바뀌는 구간**을 일부러 넣는 것이 중요했습니다. 고정 길이 시험만 통과했다고 길이 처리가 맞다고 볼 수 없습니다.

## 다시 한다면: 길이 비교기

ILA를 전 구간에 거는 방식으로 찾기는 했지만, 시간이 많이 들었습니다. DMA 직전에 **패킷마다 실제 바이트 수와 선언 길이를 비교하는 로직**을 처음부터 두었다면 훨씬 빨리 찾았을 것입니다. 다르면 **에러 플래그와 그때의 패킷 번호를 래치**하고, 그 플래그를 ILA 트리거로 쓰면 길이가 어긋난 바로 그 패킷의 파형을 볼 수 있습니다.

```verilog
// DMA 직전: 패킷마다 실제 길이와 선언 길이를 비교
always @(posedge clk) begin
  if (rst) begin
    byte_cnt <= 0; len_err <= 0;
  end else if (tvalid && tready) begin
    if (tlast) begin
      if (byte_cnt + popcount(tkeep) != tuser_size && !len_err) begin
        len_err     <= 1'b1;          // 한번 걸리면 유지 (sticky)
        err_pkt_num <= pkt_cnt;       // 몇 번째 패킷인지 기록
      end
      byte_cnt <= 0;
    end else begin
      byte_cnt <= byte_cnt + popcount(tkeep);
    end
  end
end
```

## 수정

백프레셔 처리를 바로잡아, 데이터와 길이 정보가 **같은 `tvalid && tready` 시점에 함께** 다음으로 넘어가도록 했습니다. 그 뒤 78 B → 128 B 전환 시험에서도 길이가 어긋나지 않았고, DMA가 멈추지 않았습니다.

같은 종류의 실수를 피하려면 다음을 기억해 둘 만합니다.

- **데이터와 그 데이터에 딸린 정보(길이, 큐 번호 등)는 같은 조건으로 함께 움직여야** 합니다. 한쪽만 `tready`를 보고 진행하면 둘이 서로 다른 패킷을 가리키게 됩니다.
- `tready`를 타이밍 때문에 레지스터로 끊으면, `tready`가 내려간 뒤에도 한 클럭 동안 데이터가 더 올 수 있습니다. 이 데이터를 받아 둘 **스키드 버퍼**가 없으면 beat가 빠집니다.
- 005의 백프레셔 규칙(남은 공간이 최대 패킷 + α보다 작으면 새 패킷을 막음)에서 α가 바로 이 "멈추는 데 걸리는 클럭"을 감안한 값입니다.

## 배운 점

- 백프레셔 버그는 **손실이 아니라 "길이 불일치"** 로 나타날 수 있고, 그 결과는 엉뚱하게 **DMA 정지**로 보입니다.
- 한 패킷씩 밀리는 버그는 **고정 길이 시험으로는 보이지 않습니다.** 길이가 바뀌는 구간이 있는 시험 패턴을 꼭 넣습니다.
- 길이 정보를 따로 전달하는 인터페이스에서는 **선언 길이와 실제 길이가 같은지 상시 검사**하는 로직이 디버깅 비용을 크게 줄입니다.

# 3. 문제 2: 정의되지 않은 레지스터를 읽으면 시스템이 재부팅됨

## 증상

포팅한 설계에서 특정 레지스터를 읽자 **호스트 전체가 멈추고 재부팅**되었습니다. FPGA 로직의 문제가 서버 전체를 내려 버린 경우입니다.

## 배경: 레지스터 읽기는 응답을 기다린다

호스트가 BAR 영역의 레지스터를 읽으면 다음 경로로 요청이 갑니다.

```
 CPU ──(MMIO 읽기)──▶ PCIe ──▶ QDMA ──▶ AXI4-Lite 마스터 ──▶ 사용자 레지스터 블록
     ◀──(Completion)──      ◀──      ◀──(RVALID, RDATA)──◀
```

CPU는 읽기 결과가 돌아올 때까지 **그 명령에서 기다립니다.** 사용자 레지스터 블록이 응답(`RVALID`)을 주지 않으면 PCIe Completion도 돌아가지 않고, 결국 **PCIe Completion Timeout** 같은 오류가 납니다. 서버에 따라 이 오류를 치명적 오류로 처리해 시스템을 재부팅합니다.

## 원인

레지스터 블록의 주소 디코드에서 **정의되지 않은 주소에 대한 처리(default)가 없었습니다.** 정의된 주소에만 응답하고, 나머지 주소는 아무 응답도 하지 않게 되어 있었습니다.

정의되지 않은 주소는 생각보다 자주 읽힙니다.

- 레지스터 영역을 통째로 덤프하는 도구나 스크립트
- 주소 맵이 바뀌기 전 버전을 기준으로 한 드라이버나 시험 코드
- 단순한 주소 오타

## 수정

**어떤 주소를 읽어도 반드시 응답하도록** 바꿨습니다.

| 요청 | 정의된 주소 | 정의되지 않은 주소 |
|------|-------------|-------------------|
| 읽기 | 레지스터 값, `RRESP = OKAY` | **고정값**(`0x0000_0000` 또는 `0xDEAD_BEEF`), `RRESP = OKAY` |
| 쓰기 | 레지스터에 기록, `BRESP = OKAY` | **무시**, `BRESP = OKAY` |

```verilog
always @(*) begin
  case (rd_addr)
    ADDR_CTRL   : rd_data = ctrl_reg;
    ADDR_STATUS : rd_data = status_reg;
    // ...
    default     : rd_data = 32'hDEAD_BEEF;   // 정의되지 않은 주소도 반드시 응답
  endcase
end
```

- `0xDEADBEEF`는 디버깅 중에 **"정의되지 않은 주소를 읽었다"** 는 것이 값만 보고 바로 드러난다는 장점이 있습니다.
- `0x00000000`은 드라이버가 비트를 검사할 때 **엉뚱한 기능이 켜진 것으로 해석될 위험이 적습니다.**

> AXI 규격은 정의되지 않은 주소에 오류 응답(`SLVERR`, `DECERR`)을 주는 것도 허용합니다. 다만 이 오류가 PCIe 쪽에서 어떤 응답으로 바뀌고 호스트가 그것을 어떻게 처리하는지는 브리지 설정과 플랫폼에 따라 달라서, 이번에는 **정상 응답 + 고정값**을 택했습니다. 오류 응답을 쓰려면 호스트까지의 동작을 따로 확인해야 합니다.

## 함께 확인한 AXI4-Lite 규칙

- **모든 요청에는 정확히 하나의 응답**이 있어야 한다.
- 쓰기는 주소(`AW`)와 데이터(`W`)가 **어느 순서로 와도** 받아야 한다. 한쪽만 기다리면 마스터와 서로 기다리며 멈출 수 있다.
- AXI Crossbar는 **자기 주소 맵 밖**의 요청에는 스스로 오류 응답을 주지만, 어떤 블록에 할당된 범위 **안의 빈 주소**는 그 블록이 응답해야 한다. OpenNIC처럼 박스별로 주소 범위를 나눈 구조에서는 각 블록의 default 처리가 필요하다.

## 배운 점

- FPGA 레지스터 블록의 작은 누락이 **호스트 전체의 재부팅**으로 이어질 수 있다.
- 시스템이 재부팅되면 증상을 관찰할 시간이 없어 원인을 찾기 어렵다. 레지스터 블록에는 처음부터 **default 응답**을 넣는 것을 기본 규칙으로 한다.
- 001의 7번 절("기존 주소와 읽기 동작을 유지")과 함께, **정의되지 않은 주소의 동작도 레지스터 맵 문서에 적어 둔다.**

# 5. 정리: 호스트 증상과 FPGA 원인

이 프로젝트에서 본 것을 "호스트에서 보이는 증상"을 기준으로 정리하면 다음과 같습니다.

| 호스트에서 보이는 증상 | FPGA 쪽 원인이었던 것 |
|------------------------|----------------------|
| 장치는 보이는데 패킷 길이를 바꾸는 순간 데이터가 안 올라옴 | 백프레셔 오류로 길이 정보가 한 패킷 밀림 → 선언 길이 ≠ 실제 길이 → DMA 정지 |
| 레지스터를 읽자 서버가 멈추고 재부팅 | 정의되지 않은 주소에 응답하지 않음 → PCIe Completion Timeout |

둘 다 **호스트에서 보면 드라이버나 시스템 문제처럼** 보였지만, 원인은 FPGA의 기본 규칙(핸드셰이크, 응답)이었습니다. 드라이버를 잘 모르더라도 **FPGA 쪽 경계에서 규칙이 지켜지는지**를 먼저 확인하면 많은 문제를 스스로 좁힐 수 있었습니다.

# What I Learned

- 드라이버를 잘 모를 때는 **검증된 공개 드라이버(DPDK)로 하드웨어부터 확인**하고, 그 결과를 이후 자체 드라이버의 기준으로 쓴다.
- **DMA 경계의 FPGA 카운터**가 하드웨어 문제와 소프트웨어 문제를 가르는 기준이 된다.
- 백프레셔 버그는 **길이 불일치**로, 길이 불일치는 **DMA 정지**로 나타날 수 있다. 선언 길이와 실제 길이를 상시 비교한다.
- 길이가 한 패킷 밀리는 버그는 **고정 길이 시험에서는 보이지 않는다.** 78 B → 128 B처럼 길이를 바꾸는 시험이 필요하다.
- 레지스터 블록은 **모든 주소에 응답**해야 한다. 응답하지 않으면 호스트 전체가 재부팅될 수 있다.
- 호스트에서 보이는 큰 증상의 원인이 FPGA의 **작은 규칙 위반**일 수 있다.
