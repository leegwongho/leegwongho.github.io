# Introduction

큐 분배(005)를 하려면 먼저 패킷에서 **5-tuple**을 꺼내야 합니다. OpenNIC에는 512비트 인터페이스 기준으로 헤더를 추출하는 코드가 있는데, 10G 환경의 **64비트 인터페이스**에 맞게 고치면서 "헤더 필드가 프레임의 몇 번째 바이트에 있는가"를 다시 공부해야 했습니다.

이 글은 그때 정리한 **프레임 형태(VLAN, MPLS, IPv4, IPv6)에 따라 필드 위치가 어떻게 바뀌는지**, **TCP와 UDP 헤더**, 그리고 **64비트에서 필드를 추출하는 방법**을 다룹니다.

> 공개 범위는 001과 같습니다. 프레임 구조와 오프셋은 공개 표준의 내용이고, 설계 방법은 일반화해서 설명합니다.

---

# 5-tuple이란

하나의 통신 흐름(flow)을 구분하는 다섯 가지 값입니다.

| 필드 | 위치 | 크기 |
|------|------|------|
| 출발지 IP | L3 헤더 | IPv4 4 B / IPv6 16 B |
| 목적지 IP | L3 헤더 | IPv4 4 B / IPv6 16 B |
| 프로토콜 | IPv4 Protocol / IPv6 Next Header | 1 B |
| 출발지 포트 | L4 헤더 (TCP/UDP) | 2 B |
| 목적지 포트 | L4 헤더 (TCP/UDP) | 2 B |

같은 5-tuple을 가진 패킷은 같은 흐름이므로, 해시를 계산하면 **항상 같은 값**이 나오고 **같은 큐**로 갑니다(005).

여기서 **프로토콜**은 이더넷의 EtherType이 아니라 **IP 헤더 안의 Protocol 필드(IPv4) / Next Header 필드(IPv6)** 입니다. TCP는 `6`, UDP는 `17`입니다. EtherType은 "IPv4인지 IPv6인지"를, IP Protocol은 "그 안이 TCP인지 UDP인지"를 알려 줍니다.

> 이 설계는 다섯 값을 **모두 해시 입력에 넣습니다.** Microsoft의 RSS 규격은 Protocol을 입력에 넣지 않고 입력 조합을 고르는 기준으로만 쓰는데(PCIe / QDMA Study 006), 하드웨어 구현에 따라서는 이처럼 Protocol까지 넣기도 합니다.

문제는 이 필드들의 **위치가 고정되어 있지 않다**는 것입니다. 앞에 무엇이 붙느냐에 따라 L3, L4의 시작 위치가 밀립니다.

# 1. 기본 Ethernet 헤더

Project 01 005에서 정리한 Ethernet II 헤더입니다. (Preamble/SFD는 MAC이 처리하므로 사용자 인터페이스에는 나오지 않습니다.)

```
 0        6        12   14
 ├────────┼────────┼────┼──────────────
 │ Dst MAC│ Src MAC│Type│ Payload (L3)
 └────────┴────────┴────┴──────────────
```

**EtherType(12~13번 바이트)** 이 그 뒤가 무엇인지 알려 줍니다.

| EtherType | 뒤에 오는 것 |
|-----------|--------------|
| `0x0800` | IPv4 |
| `0x86DD` | IPv6 |
| `0x8100` | VLAN 태그 (802.1Q) |
| `0x88A8` | 외부 VLAN 태그 (802.1ad, QinQ) |
| `0x9100` | 외부 VLAN 태그 (표준 이전에 쓰이던 QinQ 값. 장비에 따라 아직 쓰임) |
| `0x8847` / `0x8848` | MPLS (유니캐스트 / 멀티캐스트) |
| `0x0806` | ARP |

파서는 **EtherType을 보고 다음 헤더가 어디서 시작하는지** 정하는 일을 반복합니다.

# 2. 프레임 앞부분을 바꾸는 것들

## VLAN (802.1Q)

VLAN 태그는 **Src MAC과 EtherType 사이에 4 B가 끼어드는** 구조입니다.

```
기본:  │ Dst │ Src │ 0x0800 │ IPv4 ...
VLAN:  │ Dst │ Src │ 0x8100 │ TCI │ 0x0800 │ IPv4 ...
                    └─ TPID ─┘ 2 B   └ 진짜 EtherType
```

| 필드 | 크기 | 의미 |
|------|------|------|
| TPID | 2 B | `0x8100`. 원래 EtherType 자리에 들어가 "VLAN 태그가 있다"고 알림 |
| PCP | 3 bit | 우선순위 |
| DEI | 1 bit | 혼잡 시 버려도 되는지 |
| VID | 12 bit | VLAN 번호 (0~4095) |

결과적으로 **L3 시작 위치가 14에서 18로** 밀립니다. 최대 프레임 길이도 1518 B에서 1522 B로 늘어납니다.

## QinQ (802.1ad)

VLAN 태그를 **두 겹** 붙이는 방식입니다. 외부 태그는 TPID `0x88A8`, 내부 태그는 `0x8100`을 씁니다. L3 시작 위치는 **22**가 됩니다. 802.1ad 이전에 쓰이던 `0x9100`을 외부 태그로 쓰는 장비도 있어서, 파서는 이 값도 VLAN 태그로 인식하는 것이 안전합니다.

```
│ Dst │ Src │ 0x88A8 │ TCI │ 0x8100 │ TCI │ 0x0800 │ IPv4 ...
```

## MPLS

MPLS는 EtherType `0x8847` 뒤에 **4 B짜리 라벨이 하나 이상** 쌓이는 구조입니다.

```
│ Dst │ Src │ 0x8847 │ Label │ Label │ ... │ Label(S=1) │ IP ...
```

| 필드 | 크기 | 의미 |
|------|------|------|
| Label | 20 bit | 경로를 정하는 라벨 값 |
| TC | 3 bit | 트래픽 클래스 |
| **S** | 1 bit | **Bottom of Stack**. 1이면 마지막 라벨 |
| TTL | 8 bit | 수명 |

MPLS가 VLAN과 다른 점이 두 가지 있습니다.

- 라벨이 **몇 개인지 미리 알 수 없습니다.** S 비트가 1인 라벨을 만날 때까지 4 B씩 넘어가야 합니다.
- 라벨 스택 뒤에 무엇이 오는지 알려 주는 **EtherType 같은 필드가 없습니다.** 그래서 보통 다음 바이트의 상위 4비트(IP Version)를 보고 `4`면 IPv4, `6`이면 IPv6로 판단합니다. (의사회선(pseudowire)처럼 다른 것이 올 수도 있어서 완전한 방법은 아닙니다.)

# 3. L3 헤더

## IPv4

```
 0         4         8              16                      32 bit
 ├─────────┼─────────┼──────────────┼───────────────────────┤
 │ Version │  IHL    │  DSCP/ECN    │     Total Length      │  0~3
 ├─────────┴─────────┴──────────────┼──┬────────────────────┤
 │          Identification          │Fl│  Fragment Offset   │  4~7
 ├───────────────────┬──────────────┼──┴────────────────────┤
 │        TTL        │ **Protocol** │    Header Checksum    │  8~11
 ├───────────────────┴──────────────┴───────────────────────┤
 │                   **Source Address**                     │  12~15
 ├──────────────────────────────────────────────────────────┤
 │                **Destination Address**                   │  16~19
 ├──────────────────────────────────────────────────────────┤
 │                 Options (IHL > 5일 때)                    │  20~
 └──────────────────────────────────────────────────────────┘
```

5-tuple과 관련된 필드입니다.

| 필드 | L3 기준 오프셋 | 주의 |
|------|----------------|------|
| Protocol | 9 | TCP `6`, UDP `17` |
| Src IP | 12~15 | |
| Dst IP | 16~19 | |
| **IHL** | 0 (하위 4비트) | 헤더 길이 ÷ 4. 기본 5(=20 B). **옵션이 있으면 L4 시작 위치가 밀린다** |
| Flags / Fragment Offset | 6~7 | 단편인지 판단 |

**L4 시작 위치 = L3 시작 + IHL × 4** 입니다. IHL을 항상 5로 가정하면 옵션이 있는 패킷에서 포트를 엉뚱한 곳에서 읽습니다.

### 단편(fragment)

큰 IP 패킷이 여러 조각으로 나뉘면 **첫 조각에만 L4 헤더(포트)가 있습니다.** 두 번째 조각부터는 그 자리에 데이터가 있습니다.

- 단편 판단: MF(More Fragments) 비트가 1이거나 Fragment Offset이 0이 아님
- 단편에서 포트를 읽어 해시하면, **같은 패킷의 조각들이 서로 다른 큐로** 갈라집니다.
- 그래서 단편은 **IP 주소만(2-tuple)** 으로 해시하는 것이 일반적입니다.

## IPv6

IPv6 기본 헤더는 **항상 40 B**입니다.

```
 0~3   │ Version │ Traffic Class │        Flow Label          │
 4~7   │      Payload Length      │ **Next Header** │ Hop Limit│
 8~23  │                **Source Address (16 B)**              │
 24~39 │             **Destination Address (16 B)**            │
```

| 필드 | L3 기준 오프셋 | 주의 |
|------|----------------|------|
| Next Header | 6 | 프로토콜에 해당. TCP `6`, UDP `17` |
| Src IP | 8~23 | 16 B |
| Dst IP | 24~39 | 16 B |
| L4 시작 | 40 | **확장 헤더가 없을 때만** |

IPv6는 IPv4의 옵션 대신 **확장 헤더**를 Next Header로 줄줄이 연결합니다(Hop-by-Hop `0`, Routing `43`, Fragment `44`, Destination Options `60` 등). 확장 헤더가 있으면 L4 위치를 알기 위해 체인을 따라가야 하므로, 하드웨어 파서는 지원 범위를 정해 두는 경우가 많습니다.

# 4. L4 헤더: TCP와 UDP

## 둘의 차이

| | TCP | UDP |
|---|---|---|
| 연결 | 연결 설정 후 통신 (3-way handshake) | 연결 없이 바로 전송 |
| 신뢰성 | 재전송, 순서 보장, 흐름·혼잡 제어 | 없음 (필요하면 응용이 처리) |
| 헤더 길이 | 20~60 B (Data Offset 필드) | **8 B 고정** |
| 쓰임 | 웹, 파일 전송, 대부분의 연결형 서비스 | DNS, 스트리밍, 실시간 통신, QUIC |

## 헤더 구조

```
TCP
 0~1   Src Port      2~3   Dst Port
 4~7   Sequence Number
 8~11  Acknowledgment Number
 12    Data Offset(상위 4비트)    13  Flags (SYN, ACK, FIN ...)
 14~15 Window        16~17 Checksum      18~19 Urgent Pointer
 20~   Options (Data Offset > 5일 때)

UDP
 0~1   Src Port      2~3   Dst Port
 4~5   Length        6~7   Checksum
```

5-tuple 추출 관점에서 중요한 점은, **TCP와 UDP 모두 포트가 L4 시작에서 0~3번 바이트**라는 것입니다. 그래서 프로토콜이 TCP나 UDP이기만 하면 같은 위치에서 포트를 읽을 수 있습니다. TCP의 옵션 길이는 페이로드 위치에는 영향을 주지만 포트 위치에는 영향을 주지 않습니다.

## 순서가 왜 중요한가

TCP는 순서가 뒤바뀐 패킷을 받으면 **손실로 오해**해 중복 ACK를 보내고, 송신 측이 불필요한 재전송을 하거나 전송 속도를 줄일 수 있습니다. 같은 흐름의 패킷을 **같은 큐**로 보내야 하는 이유가 여기에 있습니다(005).

# 5. 경우별 필드 위치

위 내용을 합치면, 프레임 앞부분에 따라 5-tuple의 위치가 이렇게 달라집니다. (Dst MAC 첫 바이트를 0으로 한 바이트 오프셋, IPv4는 IHL = 5 기준)

| 형태 | L3 시작 | 프로토콜 | Src IP | Dst IP | 포트 (Src, Dst) |
|------|---------|----------|--------|--------|-----------------|
| IPv4 | 14 | 23 | 26~29 | 30~33 | 34~37 |
| VLAN + IPv4 | 18 | 27 | 30~33 | 34~37 | 38~41 |
| QinQ + IPv4 | 22 | 31 | 34~37 | 38~41 | 42~45 |
| MPLS 1개 + IPv4 | 18 | 27 | 30~33 | 34~37 | 38~41 |
| IPv6 | 14 | 20 | 22~37 | 38~53 | 54~57 |
| VLAN + IPv6 | 18 | 24 | 26~41 | 42~57 | 58~61 |
| QinQ + IPv6 | 22 | 28 | 30~45 | 46~61 | **62~65** |

512비트 인터페이스에서는 한 beat가 0~63번 바이트를 담으므로 대부분의 경우 **첫 beat 안에** 5-tuple이 다 들어옵니다. 하지만 마지막 줄처럼 **QinQ + IPv6의 포트(64~65번 바이트)는 두 번째 beat로 넘어갑니다.** 512비트 코드라도 모든 경우가 한 beat에 끝난다고 가정하면 안 된다는 뜻입니다.

---

# 6. 64비트에서 필드 추출하기

## 바이트 오프셋을 beat와 lane으로

64비트(8 B) 인터페이스에서는 바이트 오프셋 `n`이 다음 위치에 있습니다.

$$
\text{beat} = \lfloor n / 8 \rfloor, \qquad \text{lane} = n \bmod 8
$$

AXI4-Stream에서 lane 0은 `tdata[7:0]`, lane 7은 `tdata[63:56]`입니다.

기본 IPv4 패킷을 64비트로 보면 다음과 같습니다.

```
beat 0 : │ Dst MAC 0~5             │ Src MAC 0~1 │
beat 1 : │ Src MAC 2~5     │ Type  │ L3 0~1      │   ← EtherType: lane 4~5
beat 2 : │ L3 2~9 (… TTL, Protocol)              │   ← Protocol: lane 7
beat 3 : │ Checksum │ Src IP 0~3    │ Dst IP 0~1 │   ← Src IP: lane 2~5
beat 4 : │ Dst IP 2~3 │ Src Port │ Dst Port │ ... │   ← Dst IP가 beat 3~4에 걸침
```

| 형태 | 5-tuple이 모두 모이는 beat | 걸쳐 있는 필드 |
|------|---------------------------|----------------|
| IPv4 | beat 4 (5번째) | Dst IP (beat 3~4) |
| VLAN + IPv4 | beat 5 (6번째) | Src IP (beat 3~4), 포트 (beat 4~5) |
| IPv6 | beat 7 (8번째) | 주소 전부, 포트 (beat 6~7) |
| QinQ + IPv6 | beat 8 (9번째) | 포트 (beat 7~8) |

512비트에서 "첫 beat에서 위치만 골라 뽑던" 코드가, 64비트에서는 **여러 beat에 걸쳐 조각을 모으는** 코드로 바뀌어야 하는 이유입니다.

## 추출 구조: 헤더를 모은 뒤 파이프라인으로 해석

필드가 여러 beat에 흩어지는 문제를, 이 설계는 **"beat마다 필드를 골라 담기"가 아니라 "헤더를 먼저 모아 두고 한꺼번에 해석하기"** 로 풀었습니다.

```
 64비트 beat ──▶ [헤더 버퍼] ──▶ ① L2 해석 ──▶ ② L3/L4 해석 ──▶ ③ 필드 추출 ──▶ ④ 해시 ──▶ ⑤ 출력
                 (앞쪽 수십 B)    VLAN/QinQ/MPLS   IP 버전, IHL      필요한 바이트가     XOR 트리   하위 7비트
                                  → L3 위치        → L4 위치,         모이면 시작
                                                    Protocol
```

1. **헤더 버퍼**: 패킷의 앞쪽 beat들을 순서대로 버퍼에 쌓습니다. 버퍼 전체를 하나의 긴 바이트 배열로 보면, 512비트 코드처럼 "프레임의 n번째 바이트"로 필드를 가리킬 수 있습니다. 함께 "지금까지 들어온 바이트 수"를 셉니다.
2. **L2 해석**: EtherType과 VLAN/QinQ 태그를 보고 L3 시작 위치를 정합니다. MPLS면 Bottom of Stack 비트로 라벨 스택의 끝을 찾습니다(지원하는 라벨 수에는 상한을 두었습니다).
3. **L3/L4 해석**: IP 버전을 확인하고, IPv4면 IHL로 L4 시작 위치를 계산합니다. Protocol(Next Header)을 읽어 TCP/UDP인지 판단합니다.
4. **필드 추출**: 해시에 필요한 마지막 바이트(TCP/UDP면 포트 끝, 아니면 IP 주소 끝)까지 **들어온 바이트 수가 충분해지는 순간** 한 번만 추출합니다. 형태마다 필요한 바이트 수가 다르므로, 시작 시점도 패킷마다 다릅니다.
5. **해시와 출력**: 추출한 값을 해시(005)로 넘기고, 결과의 하위 7비트를 큐 선택에 씁니다.

예외 처리도 이 구조 안에 넣었습니다.

- **IP가 아니거나**, IP라도 TCP/UDP가 아니면 포트를 0으로 두거나 해시 결과를 기본값으로 둡니다.
- 필요한 바이트가 다 오기 **전에 패킷이 끝나면**(짧은 패킷), 그 시점에 기본값으로 결과를 냅니다.
- **한 beat짜리 패킷**도 따로 처리해 결과가 빠지지 않게 했습니다.
- EtherType이 IPv4라도 **IP 헤더의 Version이 4인지 다시 확인**하고, IHL이 5보다 작으면 잘못된 헤더로 봅니다. EtherType만 믿으면 깨진 패킷에서 엉뚱한 위치를 읽기 때문입니다.

## 바이트 순서와 비트 순서 주의

네트워크 필드는 **빅엔디언**(앞 바이트가 상위)이지만, AXI4-Stream에서는 **앞 바이트가 하위 비트**(`tdata[7:0]`)에 있습니다. 그래서 IP 주소나 포트를 하나의 값으로 조립할 때 **어느 바이트를 상위에 둘지**를 정해야 합니다.

| 조립 방식 | 예: Src IP (바이트 26~29) | 특징 |
|-----------|---------------------------|------|
| 네트워크 순서 | `{b26, b27, b28, b29}` | 사람이 읽는 주소 값과 같다. Microsoft RSS 규격의 입력 순서 |
| 패킷 도착 순서를 하위부터 | `{b29, b28, b27, b26}` | AXI4-Stream의 바이트 배치와 같아서 조립이 단순하다 |

어느 쪽이 "맞다"기보다, **해시를 정의한 기준과 정확히 같아야** 합니다. 이 설계는 기준이 되는 해시 모듈을 따라 **앞 바이트를 하위에 두는** 방식으로 입력을 조립하고, 해시도 그 비트 순서에 맞춰 계산합니다. 그래서 검증도 Microsoft 규격 값이 아니라 **같은 규칙으로 만든 소프트웨어 모델**과 비교했습니다.

알고리즘이 같아도 **바이트 순서, 비트 순서, 들어가는 필드 중 하나만 달라도 해시가 완전히 다르게** 나옵니다(001의 2번 절, PCIe / QDMA Study 006).

## 왜 파이프라인으로 나누었나

헤더 버퍼에서 "오프셋이 가리키는 바이트"를 고르는 로직은 **변수 인덱스**라서, 버퍼가 클수록 큰 MUX가 됩니다. 여기에 L3 위치 계산, IHL 계산, L4 위치 계산까지 한 클럭에 이어 붙이면 Critical Path가 되기 쉽습니다(003의 6번 절).

그래서 **L2 위치 → L3/L4 위치 → 필드 추출 → 해시** 를 각각 레지스터로 끊어 여러 단계로 나누었습니다. 대신 패킷 시작 표시, 마지막 beat 표시, 들어온 바이트 수 같은 **제어 신호도 같은 단계 수만큼 함께 지연**시켜야 결과가 올바른 패킷에 붙습니다. 이것이 003에서 말한 "파이프라인을 추가하면 제어 신호 정렬을 다시 확인한다"의 실제 예입니다.

L3 시작 위치가 14/18/22처럼 몇 가지뿐이라면, 오프셋을 계산하는 대신 **형태별로 위치를 미리 정한 표**에서 고르는 방법도 타이밍에 유리합니다.

# 7. 시험할 프레임 목록

추출 로직은 **프레임 형태별로** 시험해야 합니다. 이 목록을 그대로 시뮬레이션 입력으로 썼습니다.

| # | 입력 | 확인할 것 |
|---|------|-----------|
| 1 | IPv4 / TCP, UDP | 기본 위치 |
| 2 | VLAN + IPv4 | 4 B 밀림, 필드가 beat에 걸치는 처리 |
| 3 | QinQ + IPv4 (`0x88A8`, `0x9100`) | 8 B 밀림, 두 TPID 값 모두 인식 |
| 4 | MPLS 1개 / 여러 개 + IPv4 | S 비트로 스택 끝 찾기 |
| 5 | IPv4 옵션 (IHL = 6~15) | IHL로 L4 위치 계산 |
| 6 | IPv4 단편 (첫 조각, 중간 조각) | 포트를 쓰지 않는 처리 |
| 7 | IPv6 / TCP, UDP | 16 B 주소, 여러 beat |
| 8 | VLAN/QinQ + IPv6 | 포트가 512비트에서도 두 번째 beat로 넘어가는 경우 |
| 9 | IPv6 확장 헤더 | 지원 범위 밖일 때의 기본 처리 |
| 10 | ARP 등 비IP, 매우 짧은 패킷, 한 beat짜리 패킷 | 필드가 다 오기 전에 `tlast`가 오는 경우 |
| 11 | EtherType은 IPv4인데 Version이 4가 아니거나 IHL < 5 | 깨진 헤더를 IP로 오인하지 않는지 |
| 12 | 길이가 서로 다른 패킷을 연속으로 | 패킷마다 결과가 섞이지 않는지 (006) |

각 입력에 대해 **추출된 5-tuple → 해시 → 큐 번호**를 소프트웨어 모델과 단계별로 비교합니다.

# What I Learned

- 5-tuple의 프로토콜은 EtherType이 아니라 **IP 헤더의 Protocol/Next Header**이고, 이 설계는 이것까지 해시 입력에 넣는다.
- 5-tuple의 위치는 고정되어 있지 않다. **VLAN/QinQ/MPLS는 L3를, IPv4 옵션은 L4를** 밀어낸다.
- 파서의 핵심은 **EtherType과 IHL로 다음 헤더의 시작 위치를 정하는 것**이다.
- MPLS는 라벨 수가 가변이고 다음 프로토콜 필드가 없다. IP 단편은 첫 조각에만 포트가 있다.
- TCP와 UDP는 헤더 길이는 달라도 **포트는 같은 위치(L4 0~3)** 에 있다.
- 64비트에서는 필드가 여러 beat에 흩어진다. 이 설계는 **헤더를 버퍼에 모은 뒤 파이프라인으로 해석**하는 방식으로 풀었다. 512비트에서도 QinQ + IPv6는 두 번째 beat로 넘어간다.
- 변수 인덱스와 위치 계산은 큰 조합 로직이 되므로 **단계를 나누고, 제어 신호도 같은 단계만큼 지연**시킨다.
- 바이트 순서, 비트 순서, 입력 필드는 **해시를 정의한 기준과 정확히 같아야** 하고, 검증도 같은 규칙의 소프트웨어 모델과 한다.
