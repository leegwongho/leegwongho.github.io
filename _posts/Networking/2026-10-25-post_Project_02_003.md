# Introduction

기능 시뮬레이션은 통과했는데 구현 결과에서 **타이밍을 만족하지 못하는** 경우가 있습니다. 이때 리포트를 어디서부터 읽어야 하는지, Worst Path에서 무엇을 확인하는지를 일반 원칙 중심으로 정리합니다.

> 이 글의 숫자와 경로 이름은 설명을 위한 **예시**입니다. 실제 값은 사용하는 도구 버전과 설계에 따라 달라집니다.

---

# 1. 클럭 주기와 Slack

클럭 주파수에서 **한 주기의 시간**이 정해지고, 그 시간 안에 신호가 도착해야 합니다.

$$
T = \frac{1}{f}, \qquad f = 250\,\text{MHz} \Rightarrow T = 4\,\text{ns}
$$

**Slack**은 요구된 시간과 실제 도착한 시간의 차이입니다.

$$
\text{Slack}_{setup} = \text{Required Time} - \text{Arrival Time}
$$

| Slack | 의미 |
|-------|------|
| **양수** | 요구사항을 만족하고 여유가 있다 |
| **0 근처** | 겨우 만족한다 |
| **음수** | 요구사항을 만족하지 못한다 |

---

# 2. 요약 표 읽기

구현 후 가장 먼저 보는 것은 **Design Timing Summary**입니다.

| 항목 | 이름 | 의미 |
|------|------|------|
| **WNS** | Worst Negative Slack | Setup에서 **가장 나쁜** Slack |
| **TNS** | Total Negative Slack | 음수인 경로의 Slack을 **모두 합친** 값 |
| **WHS** | Worst Hold Slack | Hold에서 가장 나쁜 Slack |
| **THS** | Total Hold Slack | Hold 위반의 합 |
| **WPWS** | Worst Pulse Width Slack | 펄스 폭 검사의 가장 나쁜 값 |

- **WNS가 음수**이면 Setup을 만족하지 못한 경로가 있습니다.
- **TNS**는 "얼마나 많은 경로가 얼마나 나쁜가"를 보여 줍니다. WNS가 같아도 TNS가 작으면 문제 경로가 **소수**이고, 크면 **넓게 퍼져** 있다는 뜻입니다.
- 이 값들은 **Setup과 Hold를 따로** 봅니다. Setup이 맞아도 Hold가 틀릴 수 있고, 둘의 해결 방법은 다릅니다.
- 요약 아래의 **"All user specified timing constraints are met"** 같은 문구로 전체 성공 여부를 확인합니다.

---

# 3. Worst Path 리포트의 구조

경로 하나를 자세히 보면 대략 이런 모양입니다. (예시)

```
Slack (VIOLATED) :        -0.350ns
  Source:                 reg_a (rising edge-triggered cell FDRE, clocked by clk)
  Destination:            reg_b (rising edge-triggered cell FDRE, clocked by clk)
  Path Group:             clk
  Path Type:              Setup (Max at Slow Process Corner)
  Requirement:            4.000ns
  Data Path Delay:        3.900ns  (logic 1.200ns (31%)  route 2.700ns (69%))
  Logic Levels:           9  (CARRY8=2 LUT4=2 LUT6=4 MUXF7=1)
  Clock Path Skew:        -0.020ns
  Clock Uncertainty:      0.100ns
```

항목별로 보는 법입니다.

| 항목 | 확인할 것 |
|------|-----------|
| **Source / Destination** | 경로의 시작과 끝 레지스터. **설계의 어느 부분인지** 알 수 있다 |
| **Path Group / Clock** | 같은 클럭 안의 경로인지, **다른 클럭 사이**인지 |
| **Requirement** | 이 경로에 허용된 시간 |
| **Data Path Delay** | 실제 걸린 시간 = **Logic Delay + Route Delay** |
| **Logic Levels** | 사이에 놓인 LUT, 캐리, MUX **단계 수** |
| **Clock Path Skew** | 시작과 끝 클럭의 도착 시간 차이 |
| **Clock Uncertainty** | 클럭 불확실성(지터 등)으로 깎이는 여유 |

---

# 4. 가장 중요한 질문: 논리가 느린가, 배선이 느린가

`Data Path Delay`를 **logic**과 **route**로 나누어 보면 해결 방향이 갈립니다.

| 상태 | 의미 | 주로 하는 대응 |
|------|------|----------------|
| **logic 비중이 크고 Levels가 많다** | 조합 로직이 **너무 길다** | 로직 단순화, **파이프라인 추가** |
| **route 비중이 크다** | 배선이 길거나 **혼잡/팬아웃**이 크다 | 팬아웃 줄이기, 레지스터 복제, 배치 구조 개선 |
| **둘 다 크지 않은데 Slack이 음수** | Skew나 Uncertainty, 클럭 관계를 의심 | 클럭 경로와 제약 확인 |

예를 들어 `Logic Levels`가 많고 중간에 **비교기, 우선순위 결정, MUX, 변수 인덱스**가 이어져 있다면, 한 클럭 안에 너무 많은 일을 시킨 것입니다. 이때는 연산을 **여러 단계로 나누는** 방향이 맞습니다.

---

# 5. 경로를 읽는 순서

## 1) 이 경로가 실제 설계의 어디인가

Source와 Destination 이름으로 **어느 기능 블록**의 경로인지 정합니다. 문제라고 짐작한 블록과 **리포트의 Critical Path가 같은지** 먼저 확인해야 합니다. 다르면 짐작한 곳을 고쳐도 소용이 없습니다.

## 2) 경로를 구성하는 요소를 나열한다

Data Path 상세 항목을 위에서 아래로 읽으며, **지연이 큰 셀과 네트**를 표시합니다.

- 하나의 네트가 **큰 배선 지연**을 가지고 있는가 (팬아웃이 큰가)
- **메모리, DSP, 캐리 체인**처럼 지연이 큰 셀을 지나는가
- **같은 신호가 여러 곳**으로 퍼지는가

## 3) 비슷한 경로가 더 있는가

Worst Path 하나만 고치면 **다음 경로**가 바로 나타납니다. 상위 N개 경로가 **같은 시작점이나 같은 종착점**을 공유하는지 보고, 공통 원인을 한 번에 해결합니다.

```tcl
report_timing -max_paths 20 -nworst 1 -sort_by group
```

# 6. 원인별 대응 방법

| 원인 | 방법 | 주의할 점 |
|------|------|-----------|
| **조합 로직이 길다** | 파이프라인 단계 추가 | **지연(latency)과 제어 신호 정렬**이 달라진다 |
| **팬아웃이 크다** | 레지스터 복제, `max_fanout` 지정 | 복제된 값들이 **같은 값**이어야 한다 |
| **큰 MUX / 변수 인덱스** | 선택 구조를 나누거나 **미리 계산**해 레지스터에 저장 | 기능이 그대로인지 재검증 |
| **메모리 출력 이후 로직이 길다** | **메모리 출력 레지스터**를 쓴다 | 읽기 지연이 한 클럭 늘어난다 |
| **배치 혼잡** | 영역과 배치 구조 확인, 불필요한 큰 버스 정리 | 도구 옵션만으로는 한계가 있다 |

> **메모리 종류만 바꾼다고 해결되지 않을 수 있습니다.** 병목이 메모리 접근이 아니라 메모리에서 읽은 값을 **비교하고 선택하는 조합 로직**에 있다면, 메모리 구현만 바꿔도 그 경로는 그대로 남습니다. Critical Path에 실제로 무엇이 있는지 먼저 확인합니다.

파이프라인을 추가하면 Slack이 좋아져도 **기능이 달라지지 않았는지** 반드시 다시 검증합니다. 데이터와 `valid`, `last`, 제어 신호가 **같은 단계 수만큼** 지연되어야 합니다.

# 7. 다른 클럭 사이의 경로

리포트의 **Source Clock과 Destination Clock이 다르면** 해석이 달라집니다.

- 의도된 **클럭 도메인 교차(CDC)** 경로라면, 일반 Setup/Hold로 맞추는 대상이 아니라 **비동기 FIFO나 동기화기**로 안전성을 확보하고, 제약에서는 그 관계를 **명시적으로** 정리합니다 (`set_clock_groups`, `set_false_path`, `set_max_delay -datapath_only` 등).
- 의도하지 않았는데 다른 클럭 사이 경로가 보인다면 **설계의 실수**일 가능성이 큽니다.

```tcl
report_clock_interaction
report_cdc
```

- **제약을 완화해서 경고를 지우는 것은 해결이 아닙니다.** 그 경로가 실제로 안전한지 먼저 확인하고, 그 근거에 맞는 제약을 둡니다.
- 제약이 빠진 경로는 **검사 자체가 되지 않습니다.** 리포트의 **Unconstrained Paths**도 확인합니다.

---

# 8. 합성 결과와 구현 결과의 차이

| 단계 | 특징 |
|------|------|
| **합성(Synthesis) 후** | 배선 지연이 **추정치**다. Logic Levels와 팬아웃을 보기에 좋다 |
| **구현(Place & Route) 후** | **실제 배치와 배선** 기준. 최종 결과 |

- 합성 후 Slack은 **낙관적**일 수 있어서, 구현 후에 더 나빠지는 경우가 흔합니다.
- 합성 단계에서 Logic Levels가 많은 경로는 구현에서도 **문제가 될 가능성이 큽니다.**
- 같은 RTL이라도 **디바이스를 바꾸면** 배치와 배선이 달라져서 결과가 달라집니다. 이때는 두 환경의 **Worst Path와 혼잡 결과를 나란히 비교**해야 무엇이 바뀌었는지 알 수 있습니다.
- 구현 시간이 갑자기 길어졌다면 기능이 아니라 **배치 혼잡**과 타이밍을 맞추기 위한 **반복 재시도**를 의심합니다.

---

# 9. 점검표

1. **Summary**에서 WNS, TNS, WHS를 확인한다. (Setup과 Hold를 따로)
2. **Worst Path**의 Source와 Destination으로 설계의 **어느 블록인지** 정한다.
3. `Data Path Delay`를 **logic과 route**로 나눈다.
4. **Logic Levels**와 **팬아웃이 큰 네트**를 표시한다.
5. 상위 경로들의 **공통 시작점/종착점**을 찾는다.
6. 다른 클럭 사이 경로라면 **의도된 CDC인지** 확인한다.
7. 수정한 뒤 **기능 검증**을 다시 한다. (파이프라인이면 제어 신호 정렬)
8. **합성 → 구현** 순서로 Slack 변화를 비교한다.

# What I Learned

- **Slack = 요구 시간 − 도착 시간**이고, 음수이면 요구를 만족하지 못한다.
- **WNS**는 가장 나쁜 경로, **TNS**는 문제의 **범위**를 보여 준다.
- `Data Path Delay`를 **logic과 route**로 나누면 대응 방향이 정해진다.
- 짐작한 블록이 아니라 **리포트의 Critical Path에 있는 로직**을 고친다.
- 파이프라인을 추가하면 **지연과 제어 신호 정렬**을 다시 확인한다.
- 다른 클럭 사이 경로는 **제약을 완화하기 전에** 설계가 안전한지 확인한다.
- 합성 후 결과는 낙관적일 수 있으므로 **구현 후 결과**로 판단한다.
