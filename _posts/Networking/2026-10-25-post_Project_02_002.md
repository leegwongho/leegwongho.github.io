# Introduction

데이터 경로가 길어질수록 "패킷이 안 나온다"는 증상만으로는 어디를 봐야 할지 알 수 없습니다. 이 글은 경로 곳곳에 **카운터를 두고 한 줄로 이어서 읽어** 멈춘 위치를 좁히는 방법을 일반 원칙 중심으로 정리합니다.

---

# 핵심 원칙

> **카운터가 멈췄다는 것은 현상이지 원인이 아니다.**

카운터는 "어디까지 왔는가"만 알려 줍니다. 원인은 **마지막으로 증가한 지점과 처음으로 증가하지 않은 지점 사이**에 있습니다. 그래서 카운터는 한 개가 아니라 **경로를 따라 여러 개**가 있어야 의미가 생깁니다.

```
[입력] → ① → [블록 A] → ② → [블록 B] → ③ → [블록 C] → ④ → [출력]

 ①=1000  ②=1000  ③=640  ④=640
         → 블록 B 안 또는 ②~③ 사이를 본다
```

앞단은 모두 같고 뒤에서 처음 줄어드는 곳이 **조사 범위**입니다.

---

# 1. 무엇을 셀 것인가

세는 단위가 다르면 비교할 수 없습니다. 먼저 단위를 정합니다.

| 단위 | 세는 시점 | 용도 |
|------|-----------|------|
| **beat 수** | `tvalid && tready` 마다 | 핸드셰이크가 일어나는지 |
| **패킷 수** | `tvalid && tready && tlast` 마다 | 패킷 단위 손실 확인 |
| **바이트 수** | 유효 beat의 `tkeep` 합 | 길이가 변형되는지 |

```verilog
wire hs = tvalid & tready;               // 핸드셰이크 성립

always @(posedge clk) begin
  if (rst) begin
    beat_cnt <= 0;
    pkt_cnt  <= 0;
  end else if (hs) begin
    beat_cnt <= beat_cnt + 1;
    if (tlast) pkt_cnt <= pkt_cnt + 1;   // 패킷은 tlast에서만 센다
  end
end
```

- **`tvalid`만 세면 안 됩니다.** `tready`가 0이면 데이터는 전달되지 않았는데 `tvalid`는 계속 1일 수 있습니다.
- 패킷 수는 **`tlast` 핸드셰이크**로 셉니다. beat 수만 비교하면 패킷이 짧아졌는지 사라졌는지 구분할 수 없습니다.
- Project 01에서 `stat_tx_total_bytes`가 누적값이 아니라 **클럭마다의 증가분**이었던 것처럼, 카운터가 **누적값인지 증가분인지** 먼저 확인합니다.

---

# 2. 어디에 둘 것인가

## 블록의 입력과 출력 양쪽에

블록 하나의 **입력과 출력에 각각** 카운터를 두면 그 블록이 **패킷을 만들거나 없애거나 잡고 있는지**가 한 번에 보입니다.

| 입력 vs 출력 | 의미 |
|--------------|------|
| 같다 | 블록은 통과시켰다. 문제는 뒤에 있다 |
| 출력이 적다 | 블록이 **버렸거나 아직 안에 잡고 있다** |
| 출력이 많다 | 블록이 패킷을 **만들어 냈다** (분할, 복제) |

## 경계마다

- 인터페이스가 바뀌는 곳 (폭 변환, 프로토콜 변환)
- **클럭 도메인이 바뀌는 곳**
- 버퍼(FIFO) 앞과 뒤
- 호스트와의 경계 (드라이버가 보는 통계)

문제가 생기기 쉬운 곳은 대개 **무언가가 바뀌는 경계**입니다.

---

# 3. 멈췄는지, 버려졌는지

카운터가 입력보다 적게 올라가는 이유는 크게 두 가지입니다.

| | **정지(stall)** | **손실(drop)** |
|---|---|---|
| 시간이 지나면 | 카운터가 **따라잡을 수 있다** | **차이가 고정**된다 |
| 원인의 위치 | 뒤쪽이 막혀 있다 | 어딘가에서 버려졌다 |
| 확인 | `tvalid`/`tready` 상태 | 버리는 조건, 오버플로 표시 |

입력을 멈춘 뒤에도 몇 초 기다려 **차이가 줄어드는지** 보면 둘을 구분할 수 있습니다.

```
입력 1000 / 출력 640 → 입력 정지 후 대기 → 출력 1000   : 정지(지연)
입력 1000 / 출력 640 → 입력 정지 후 대기 → 출력 640    : 손실 또는 버퍼에 갇힘
```

두 번째는 손실일 수도 있고 **내부 버퍼에 남은 채 안 나오는 것**일 수도 있어서, 그 블록의 점유율(occupancy)이나 FIFO 카운터를 따로 봅니다.

---

# 4. 핸드셰이크 상태로 읽는 막힘의 방향

멈춘 경계에서 `tvalid`와 `tready`의 조합은 **어느 쪽이 문제인지**를 알려 줍니다.

| `tvalid` | `tready` | 해석 |
|----------|----------|------|
| 1 | 1 | 전송 중. 정상 |
| 1 | **0** | 보내는 쪽은 준비됐는데 **받는 쪽이 막혔다** → 뒤(하류)를 본다 |
| **0** | 1 | 받는 쪽은 준비됐는데 **줄 데이터가 없다** → 앞(상류)을 본다 |
| 0 | 0 | 둘 다 정지. 양쪽 모두 의심 |

```
 상류 ──(tvalid)──▶ 하류
      ◀──(tready)──
```

- `tvalid=1, tready=0`이 **계속** 이어지면 하류가 이 데이터를 받지 못하는 것입니다. 그다음 경계로 같은 질문을 반복하면 막힌 지점을 **하류 쪽으로 따라가며** 찾을 수 있습니다.
- 반대로 `tvalid=0`이 계속되면 데이터가 이 앞에서 오지 않는 것이므로 **상류 쪽으로** 올라갑니다.
- **역압(back-pressure)** 은 하류의 막힘이 `tready`를 타고 상류로 번지는 현상입니다. 맨 끝이 막히면 앞쪽 경계들이 줄줄이 `tvalid=1, tready=0`으로 보일 수 있습니다. 이때는 **가장 하류에서 처음 `tready=0`이 된 경계**가 출발점입니다.
- 단, Project 01에서 본 CMAC RX처럼 **`tready`가 없는 인터페이스**도 있습니다. 이런 곳은 막히는 대신 **데이터가 사라질 수** 있으므로, 직전에 버퍼가 있는지부터 확인합니다.

---

# 5. 마지막으로 성공한 핸드셰이크

카운터 값과 함께, **"마지막으로 핸드셰이크가 일어난 때"** 를 알 수 있으면 원인을 훨씬 좁힐 수 있습니다.

- 정지 후 카운터가 **몇 번째 패킷에서** 멈췄는지 (매번 같은 값인지, 달라지는지)
- 멈추기 직전 **마지막 beat의 `tlast`, `tkeep`** 이 정상이었는지
- 멈추는 시점에 **다른 경계의 상태**(버퍼 가득 참, 크레딧 소진 등)가 어땠는지

**매번 같은 위치에서 멈춘다면** 특정 자원(버퍼, 크레딧, 디스크립터)이 한도에 도달했을 가능성을 의심합니다. **매번 다른 위치에서 멈춘다면** 타이밍, 경쟁 조건, 리셋 문제 쪽을 먼저 봅니다. 다만 숫자가 같다고 원인이 확정되는 것은 아니므로, 후보로 적고 **확인 시험을 따로** 설계합니다.

---

# 6. 카운터 자체를 믿을 수 있게

카운터가 틀리면 디버깅이 더 어려워집니다.

- **같은 시점에 읽는다.** 여러 카운터를 소프트웨어가 하나씩 읽으면 그 사이에 값이 변해서 차이가 생깁니다. 읽기 전에 **스냅샷(래치)** 으로 한 번에 얼려 두는 방식이 안전합니다.
- **클럭 도메인을 확인한다.** 카운터가 속한 클럭과 읽는 쪽(레지스터 인터페이스)의 클럭이 다르면, 여러 비트의 값을 그냥 건네면 중간값이 읽힐 수 있습니다.
- **폭이 충분한가.** 카운터가 가득 차서 돌아가면(wrap) 값이 줄어든 것처럼 보입니다. 시험 시간과 속도로 계산해 폭을 정합니다.
- **리셋 기준을 맞춘다.** 시험 전에 모든 카운터를 같이 지워야 비교할 수 있습니다.
- **카운터가 증가하는 조건이 같은 의미인가.** 어떤 곳은 beat, 어떤 곳은 패킷을 세면서 숫자를 비교하지 않도록 이름에 단위를 적어 둡니다.

---

# 7. ILA와 카운터를 같이 쓴다

| 도구 | 잘하는 것 | 약한 것 |
|------|-----------|---------|
| **카운터(상시)** | 긴 시험에서 누적 흐름, 손실률 | 순간의 파형 |
| **ILA(트리거)** | 문제 순간의 신호 파형 | 오래 걸리는 현상, 드문 현상 |

권장 순서는 이렇습니다.

1. 카운터로 **어느 구간에서 줄어드는지** 먼저 찾는다.
2. 그 구간 경계에 **ILA**를 붙이고, "카운터가 처음 어긋나는 순간"이나 "`tvalid=1, tready=0`이 N클럭 이상 지속"을 **트리거 조건**으로 건다.
3. 파형에서 `tdata/tlast/tkeep`과 핸드셰이크를 확인한다.

처음부터 ILA만 쓰면 어디에 붙일지 몰라서 시간이 오래 걸립니다. ILA는 카운터로 **범위를 좁힌 뒤에** 쓰는 것이 효율적입니다. ILA 프로브는 Project 01에서 한 것처럼 **IP 포트에 연결된 네트**에 붙여야 실제 신호를 볼 수 있습니다.

---

# 8. 호스트 쪽 카운터까지 연결한다

FPGA 내부 카운터가 정상이어도 호스트에서 안 보일 수 있습니다. FPGA 끝과 **호스트 통계**를 함께 비교합니다.

```
FPGA 내부 경계들 → DMA 경계 → 드라이버 통계(ethtool, testpmd 등)
```

- FPGA 쪽은 증가하는데 호스트는 증가하지 않으면 **DMA, 디스크립터, 완료 처리, 드라이버** 쪽을 봅니다. (PCIe / QDMA Study 004, 007)
- FPGA 쪽부터 증가하지 않으면 **호스트를 의심하기 전에 FPGA 앞단**을 봅니다.

---

# 9. 점검표

멈췄을 때 이 순서로 봅니다.

1. 모든 카운터를 **지우고** 같은 조건으로 다시 시험한다.
2. 경로를 따라 **처음으로 줄어드는 경계**를 찾는다.
3. 그 경계 전후의 **정지인지 손실인지** 구분한다. (입력을 멈추고 기다려 본다)
4. 그 경계에서 `tvalid/tready` 조합으로 **상류인지 하류인지** 정한다.
5. 멈춘 **패킷 번호, 마지막 beat**를 기록한다.
6. 그 구간 **ILA**로 파형을 확인한다.
7. 원인 후보를 적고, **각 후보를 가리는 시험**을 하나씩 한다.
8. 확인된 것과 후보인 것을 **구분해서 기록**한다. (001의 6번 절)

# What I Learned

- 카운터가 멈춘 것은 **현상**이고, 원인은 **마지막으로 증가한 곳과 처음으로 증가하지 않은 곳 사이**에 있다.
- 세는 **단위(beat, 패킷, 바이트)와 조건(`tvalid && tready`, `tlast`)** 을 먼저 정해야 비교할 수 있다.
- 블록의 **입력과 출력**, 그리고 **무언가 바뀌는 경계**마다 카운터를 둔다.
- **정지인지 손실인지**는 입력을 멈추고 차이가 줄어드는지로 구분한다.
- `tvalid/tready` 조합이 막힘의 방향(**상류 또는 하류**)을 알려 준다.
- 카운터는 **카운터로 범위를 좁히고 ILA로 확인**하는 순서가 효율적이다.
- 카운터 자체의 **스냅샷, 클럭 도메인, 폭, 리셋**을 확인해야 믿을 수 있다.
